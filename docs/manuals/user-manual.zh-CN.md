# kaze-sync 用户手册

[English](user-manual.md) | [简体中文](user-manual.zh-CN.md)

借助 kaze-sync, 你可以通过自己的服务器在多台 Linux 和 Windows 电脑之间同步文件夹, 并在误改或误删时随时找回历史版本. 本手册是日常使用与维护 kaze-sync 的完整参考, 涵盖安装服务端和客户端, 注册设备, 映射文件夹, 编写排除规则, 控制谁可以在哪里写入并处理同时写入, 恢复旧版本, 备份, 升级, 卸载以及排查问题.

阅读本手册假定你会使用终端, `ssh` 和 `scp`. 如果你只想用几条命令先把第一套部署跑起来, 请先看 [README](../../README.zh-CN.md), 跑通之后再回到本手册按需查阅具体操作.

全书遵循两个约定:

- Web UI 提供简体中文, 繁体中文, 英文, 日文和韩文五种界面语言 (见第 4 节的设置页); 手册中提到的按钮, 菜单项和提示均与简体中文界面上的文字完全一致.
- 在服务端执行的命令标注 `# server`, 在客户端电脑上执行的命令标注 `# client`. 请把命令中的 `<...>` 替换为你自己的实际值.

所有环境通用的系统级部署细节 (例如给只有一块盘的 OpenWrt 路由器划分数据分区, systemd 加固配置, 内存预算细则) 写在 [`docs/operations.md`](../operations.md) 中, 本手册在相关位置直接指向对应章节, 不再重复抄录.

## 1. 各部分如何配合

在动手安装之前, 先了解 kaze-sync 的几个核心概念如何配合, 后面看每条命令和每个界面都会更清楚:

- **服务端** (`kaze-syncd`): 一个独立的后台进程, 负责保存全部同步文件及其历史版本, 并提供 Web UI. 它运行在 OpenWrt 上, 或使用 systemd 或 OpenRC 的 x86-64 Linux 机器上 (例如 VPS 或家用服务器).
- **客户端** (`kaze-syncc`): 运行在每台 Linux 或 Windows 电脑上的后台 agent. 它负责监视本地文件夹, 上传本机改动, 并下载其他设备的改动. 客户端只主动向外连接服务端, 不需要开放任何入站端口, 因此在 NAT 之后无需端口映射即可工作.
- **设备**: 已在服务端注册的一台电脑, 每台设备有一个唯一名称.
- **文件夹**: 服务端上一组有名称的文件集合; 在所有同步该文件夹的设备上, 它的内容保持一致.
- **映射**: 服务端上的一个文件夹与某台设备上一个本机目录路径之间的对应关系. 例如文件夹 `Docs` 在 Windows 笔记本上映射为 `D:\Docs`, 在 Linux 台式机上映射为 `/home/me/Docs`. 全部配置 (文件夹, 映射, 排除规则, 版本保留期) 都在服务端的 Web UI 中完成, 并自动推送给在线客户端, 通常一秒内生效.
- **版本**: 每次覆盖或删除文件时, 服务端都会把旧内容保留若干天 (默认 30 天), 供你随时恢复.

Web UI 的所有操作均由唯一的管理员完成, 凭一个随机生成的密码登录.

**文件放在哪里.** 弄清 kaze-sync 在磁盘上的文件布局, 后续升级, 备份和查日志都会顺手得多. 凡是操作系统或平台已有标准默认位置的, kaze-sync 直接沿用默认位置:
- Linux 客户端状态目录: `~/.local/state/kaze-sync/` (XDG)
- Linux systemd 用户单元目录: `~/.config/systemd/user/`
- Linux 用户程序目录: `~/.local/bin/`
- Windows 客户端状态与自启动: `%LOCALAPPDATA%\kaze-sync\` 与注册表 `Run` 项
- Linux 上 root 安装的服务端数据目录: `/var/lib/kaze-sync`
- OpenWrt 上的服务端数据目录: 已挂载的数据盘

其余由你自己指定位置的内容 (例如手动启动的测试服务端传给 `--data` 的目录, 或保存管理员密码这类私有文件), 建议统一放在 `~/.kaze-sync/` 一个目录下 (例如 `--data ~/.kaze-sync/server` 和 `~/.kaze-sync/config/`), 免得散落在家目录各处.

## 2. 安装服务端

因为客户端需要连接服务端来完成注册和拉取配置, 所以第一步是获取服务端程序并装好服务端.

### 2.1 下载并校验服务端发布包

项目的 [GitHub Releases](https://github.com/pellorao/kaze-sync/releases) 页面仅提供 x86-64 (`amd64`) 架构 Linux 与 Windows 的预编译发布包. 安装服务端时, 请把 `kaze-sync-0.3.5-linux-amd64.tar.gz` (把 `0.3.5` 换成你要安装的版本号) 和 `SHA256SUMS` 下载到同一个目录下 (可以直接下载到服务器, 也可以先下载到工作站再复制过去). 这份 Linux 归档里包含两个静态链接, 无外部依赖的二进制文件: 服务端 `kaze-syncd` 和 Linux 客户端 `kaze-syncc`. 如果你的机器没有预编译包 (例如使用非 x86-64 CPU 的 OpenWrt 路由器), 或你想自己从源码编译, 请参见[附录 A: 从源码编译](#附录-a-从源码编译).

解压前请先用 `SHA256SUMS` 校验归档的 SHA-256 校验和, 确认文件下载完整且未被篡改:

```bash
sha256sum -c SHA256SUMS
```

如果你只下载了 `kaze-sync-0.3.5-linux-amd64.tar.gz`, 没有同时下载 Windows 的 `.zip` 归档, `sha256sum` 会提示缺少那个 `.zip` 文件; 只要 `kaze-sync-0.3.5-linux-amd64.tar.gz` 这一行显示 `OK`, 就可以继续.

由于该归档把 `kaze-syncd` 和 `kaze-syncc` 直接放在根目录而没有外层文件夹, 请先建一个专用目录再解压:

```bash
mkdir -p kaze-sync-0.3.5
tar -xzf kaze-sync-0.3.5-linux-amd64.tar.gz -C kaze-sync-0.3.5
```

两个二进制文件都在构建时嵌入了发布版本号: 执行 `kaze-syncd --version` 和 `kaze-syncc --version` 会分别输出 `kaze-syncd 0.3.5` 和 `kaze-syncc 0.3.5` (以 `0.3.5` 版为例). 登录 Web UI 后, 左上角 `Kaze Sync` 旁也会显示当前服务端的版本号 (登录页不显示).

### 2.2 OpenWrt

如果服务端运行在 OpenWrt 路由器上, 数据目录必须放在已挂载的独立数据盘上, 不能放在根文件系统 (overlay) 上. `install` 会拒绝根文件系统上的路径, 因为路由器的闪存很小, 很快就会被同步文件写满, 而且升级固件时根文件系统上的数据会被抹掉. 如果路由器只有一块磁盘, 请先在这块盘上划分并挂载一个数据分区, 具体步骤见 [`docs/operations.md`](../operations.md) 的 "OpenWrt 只有一块盘: 新建数据分区" 一节.

[2.1 节](#21-下载并校验服务端发布包)的预编译发布包只适用于 x86-64 架构的 OpenWrt 路由器, 其他 CPU 架构的 OpenWrt 没有预编译包 (见[附录 A](#附录-a-从源码编译), 且[第 18 节](#18-kaze-sync-不做什么)说明服务端不支持 x86-64 以外的架构). 挂载好数据盘后, 把 [2.1 节](#21-下载并校验服务端发布包)解压出的 `kaze-syncd` 复制到路由器上 (或直接在路由器上解压校验后的归档), 以 root 执行 (`install` 会把 `kaze-syncd` 复制到 `/mnt/data/kaze-sync/kaze-syncd`):

```bash
./kaze-syncd install --data /mnt/data/kaze-sync        # server
/mnt/data/kaze-sync/kaze-syncd admin-password          # server: 只显示一次管理员密码
```

执行 `install` 会一步完成服务端的全部初始化:
- 把自身二进制复制到 `<data>/kaze-syncd`, 并创建系统用户 `kaze-sync`.
- 创建并迁移数据库.
- 生成自签名 TLS 证书 (若带上 `--ca`, 则生成本地 CA 以及由它签发的服务端证书).
- 在 20000 到 59999 之间随机选定一个 TCP 端口 (后续再次执行时保持不变).
- 写入并启用 `procd` 服务 `/etc/init.d/kaze-sync` 并立即启动, 同时把服务文件加入 `/etc/sysupgrade.conf`, 确保 OpenWrt 执行 `sysupgrade` 升级固件时保留服务配置.

最后, `install` 会在终端打印监听端口和证书指纹 (`sha256:...`). 请把这两项记下来, 接下来登录 Web UI 和注册客户端都要用到.

`install` 支持以下选项:

| 选项 | 含义 |
|---|---|
| `--data DIR` | 必填. 绝对路径, 只能由字母, 数字和 `. _ - /` 组成 |
| `--listen :PORT` | 指定监听地址以代替随机端口; 之后再次执行会自动沿用 |
| `--cert FILE --key FILE` | 使用你自己的证书代替自签名证书 (2.4 节) |
| `--ca [--san NAMES]` | 使用本地 CA 和由它签发的证书, 浏览器可以信任它 (2.4 节) |
| `--wan` | 只用于 OpenWrt: 添加名为 `kaze-sync` 的防火墙规则, 允许从 WAN 区域访问该端口. 升级时既不带 `--data` 也不带 `--wan` 会保留已有的规则; 带上 `--data` 时, 除非同时带 `--wan`, 否则会删除该规则 |
| `--new-epoch` | 只在从备份还原服务端之后使用 (第 14 节) |

### 2.3 普通 Linux (systemd 或 OpenRC)

在普通 x86-64 Linux 服务器上, 根文件系统空间充足且升级系统不会抹掉数据, 因此数据目录可以选在任意位置 (包括根文件系统上). 在你解压出 `kaze-syncd` 的目录下 ([2.1 节](#21-下载并校验服务端发布包)), 以 root 执行 (`install` 会把 `kaze-syncd` 复制到 `/var/lib/kaze-sync/kaze-syncd`):

```bash
./kaze-syncd install --data /var/lib/kaze-sync         # server
/var/lib/kaze-sync/kaze-syncd admin-password           # server
```

`install` 会自动识别系统的服务管理器 (依次检测 OpenWrt, systemd, OpenRC; 其余初始化系统一律拒绝). 它会创建系统用户 `kaze-sync` (使用 `useradd`, Alpine 上使用 busybox `adduser`), 写入服务定义文件 (systemd 下为 `/etc/systemd/system/kaze-sync.service`, OpenRC 下为 `/etc/init.d/kaze-sync`), 设为开机自启并立即启动服务.

与 OpenWrt 不同, 普通 Linux 上的 `install` **不会**改动任何防火墙配置, 也不接受 `--wan` 选项. 请在云厂商的安全组或本机防火墙中放行打印出的 TCP 端口 (例如执行 `ufw allow <端口>/tcp` 或 `firewall-cmd --add-port=<端口>/tcp --permanent`; 见 2.6 节).

日常启停服务和查看日志使用各平台自带的工具:

| | systemd | OpenRC | OpenWrt |
|---|---|---|---|
| 启动, 停止, 重启, 状态 | `systemctl start\|stop\|restart\|status kaze-sync` | `rc-service kaze-sync start\|stop\|restart\|status` | `/etc/init.d/kaze-sync start\|stop\|restart` |
| 日志 | `journalctl -u kaze-sync` | syslog, 标签 `kaze-sync` (Alpine 在 `/var/log/messages`) | `logread` |

如果服务进程意外崩溃, 服务管理器会在 5 秒后自动重启它. 如果开机时数据盘尚未挂载, 服务会直接启动失败退出, 而不会在未挂载的目录里悄悄新建一个空数据库.

systemd 下的单元文件带有安全加固选项 (限制服务只能写入 `<data>/var` 目录). 如果你需要自定义单元配置, 请使用 drop-in (`systemctl edit kaze-sync`), 不要直接修改单元文件本身, 因为下一次执行 `install` 会重写单元文件. 加固细节与 systemd 版本要求见 [`docs/operations.md`](../operations.md) 的 "普通 Linux (systemd 或 OpenRC)" 一节.

注意 `install` 必须以 root 身份执行, 服务端没有受支持的非 root 安装方式. 把安装权限与运行权限分开是有意为之: `install` 会创建非特权用户 `kaze-sync`, 写入服务文件, 将二进制文件和数据目录的属主设为 root (防止服务进程被攻破后替换自身代码), 并将 CA 私钥设为仅 root 可读; 而实际运行的服务端进程则以非特权用户 `kaze-sync` 的身份工作, 且只能在 `<data>/var` 下写入.

### 2.4 端口, 证书与防火墙

Web UI 与客户端同步协议共用同一个 HTTPS 端口, 所有通信全程加密. 默认情况下 `install` 会随机选定端口以避免被全网扫描发现; 如果需要固定端口, 可以用 `--listen :PORT` 指定 (见 2.6 节).

在证书配置上, 你可以根据自己的使用习惯和是否拥有域名证书, 在以下三种模式中选择一种:

- **自签名证书 (默认).** 无论公网还是局域网都能开箱即用, 有效期 100 年. 客户端按 SHA-256 指纹固定证书, 因此通过什么 IP 或主机名连接都不受影响. 浏览器第一次打开 Web UI 时会弹出证书警告; 把浏览器显示的指纹与 `install` 打印的指纹核对一致后, 接受一次例外即可.
- **自己的证书.** 如果你有公认 CA (例如 Let's Encrypt) 签发的域名证书, 安装时传入 `--cert /path/fullchain.pem --key /path/key.pem` (都必须是绝对路径, `install` 在安装时会检查文件存在). 此后浏览器和客户端都会按系统根证书校验服务端, 客户端注册命令中也不再带 `--fingerprint`.
  需要注意权限问题: 服务以非特权用户 `kaze-sync` 运行, 并在启动时自己读取这两个文件, 因此用户 `kaze-sync` 必须有权限读取证书和私钥, 且有权限进入它们上层的每一级目录. `install` 以 root 运行, 自己总能读到这些文件, 所以它改为按用户 `kaze-sync` (含主组和附加组; 不检查 ACL) 核对两个文件及其上层每一级目录的权限位: 如果服务用户读不到证书或私钥, 或无权进入某一级上层目录, `install` 会输出一行以 `warning:` 开头的警告, 写明是哪个文件或目录以及修复命令, 然后继续安装. 不要忽略这条警告: 否则服务每次启动都会立刻退出, 日志里报错 `permission denied` (服务管理器可能还会短暂显示为已启动). 遇到这种情况时, 用例如 `chgrp kaze-sync key.pem && chmod 640 key.pem` 赋予读取权限 (若上层目录对其他用户关闭, 再执行 `chgrp kaze-sync <目录> && chmod 750 <目录>`), 然后重启服务.
  服务端不会监视外部证书文件的变化, 因此每次证书续期后都要重启服务 (使用 `acme.sh` 时可把重启命令写进 `--reloadcmd`). 后续再次执行 `install` 会自动沿用证书模式, 且不能切回自签名模式.
- **本地 CA (浏览器信任, 恢复自动填充密码).** 浏览器因为把自签名证书视为不安全连接, 默认会弹出警告且拒绝在登录页自动填充已保存的密码. 如果你没有公网域名但希望浏览器完全信任 Web UI 并自动填充密码, 可以用 `--ca` 模式: 服务端会生成自己的私有证书颁发机构 (CA) 以及由该 CA 签发的服务端证书. 只要在你的电脑上导入并信任这个 CA 证书, Chrome, Edge 和 Firefox 就会把页面视为安全连接, 恢复密码自动填充.
  服务端证书默认覆盖的名称包括 `localhost`, `127.0.0.1`, `::1`, 服务器主机名以及 `--listen` 中指定的主机; 你在浏览器地址栏里实际输入的 IP 或域名请通过 `--san` 追加 (多个名称用逗号分隔, 例如 `--san 192.168.1.1,nas.example.org`; 以后想增删名称时重新执行一次 `install` 即可). 请只用证书覆盖的名称打开 Web UI, 否则浏览器仍会警告.
  CA 私钥和证书保存在 `<data>/ca/` 下, 仅 root 可读, 运行中的同步服务本身读不到 CA 私钥. 客户端固定的是这个 CA 的指纹 (`install` 打印的指纹, Web UI 的注册对话框里也会自动带上), 因此客户端所在的电脑不需要往系统里导入任何证书.
  要让浏览器信任这个本地 CA, 只需在你用浏览器打开 Web UI 的每台电脑或手机上导入一次公开的 CA 证书 (只运行客户端的设备不需要导入). 先在服务器上导出公开的 CA 证书:

  ```bash
  /mnt/data/kaze-sync/kaze-syncd ca --data /mnt/data/kaze-sync --export ca.pem     # 在服务器上
  ```

  `ca.pem` 只包含公开证书而不含私钥机密, 因此可以用 U 盘, 网盘等任意方式复制到其他设备上. 导入前请先核对它的 SHA-256 指纹, 确认与 `install` 打印的 CA 指纹一致: 在 Linux 和 macOS 上执行 `openssl x509 -in ca.pem -noout -fingerprint -sha256`; 在 Windows 上执行 `certutil -dump ca.pem` 并查看 "证书哈希(sha256)" (英文版 Windows 显示为 "Cert Hash(sha256)"). 核对无误后, 按设备平台导入系统或浏览器:

  - **Windows (Chrome 和 Edge)**: 执行 `certutil -user -addstore Root ca.pem`. Windows 会弹出一次确认安装根证书的对话框, 选 **是**. 证书会装入当前用户的存储区, 不需要管理员权限. 装好后重启浏览器.
  - **Linux 系统存储**: 执行 `sudo cp ca.pem /usr/local/share/ca-certificates/kaze-sync-ca.crt && sudo update-ca-certificates`. Linux 上的 Chrome 和 Chromium 使用独立的 NSS 证书库, 需执行 `certutil -d sql:$HOME/.pki/nssdb -A -t "C,," -n kaze-sync -i ca.pem` (工具在软件包 `libnss3-tools` 中).
  - **Firefox**: 依次打开 设置 -> 隐私与安全 -> 证书 -> 查看证书 -> 证书颁发机构 -> 导入, 选择 `ca.pem`, 并勾选 "信任由此证书颁发机构来标识网站". (Windows 上的 Firefox 也可以直接读取系统证书库: 在 `about:config` 中把 `security.enterprise_roots.enabled` 设为 `true` 即可.)
  - **macOS**: 双击 `ca.pem` (或在 "钥匙串访问" 中将它导入 "登录" 钥匙串), 打开该证书, 展开 "信任" 部分, 在弹出式菜单中选择 "始终信任"; 或者在命令行执行 `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain ca.pem`.
  - **Android**: 依次打开 设置 -> 安全 (部分厂商为 安全与隐私 -> 更多安全设置, 具体菜单名因厂商而异) -> 加密与凭据 -> 安装证书 -> CA 证书, 选择 `ca.pem` 并确认警告. Android 上的 Chrome 使用这个用户安装的证书库; 部分应用虽会忽略用户安装的 CA, 但不影响在 Chrome 中使用 Web UI.
  - **iPhone 和 iPad**: 把 `ca.pem` 传到设备上 (通过隔空投送, "文件" 应用或下载链接) 并打开它. iOS 提示已下载描述文件后, 按 "设置" 中的提示安装该描述文件 (也列在 设置 -> 通用 下, 具体名称因 iOS 版本而异). 最后依次打开 设置 -> 通用 -> 关于本机 -> 证书信任设置, 为该证书开启完全信任.

  **在手机 (Android) 上导入 CA.** 手机需要它, 才能在 Chrome 里无警告地打开 Web UI, 并收到 Web Push (9.1 节). 先运行上面的导出命令, 把 `ca.pem` 传到手机 (网盘, USB 数据线或临时下载链接均可), 并核对它的 SHA-256 指纹与 `install` 打印的 CA 指纹一致. 在手机上打开 设置, 找到 "安装证书" (见上面 Android 一项), 选择 **CA 证书**, 确认警告后选中 `ca.pem`. 然后彻底关闭并重新打开 Chrome, 访问 `https://<服务器>:<端口>/`, 确认地址栏的锁没有警告. 如果你使用 `--san` 或更换了输入的地址, 服务端证书必须覆盖该地址 (见上文).

  谁拿到 `ca-key.pem`, 谁就能签发你的电脑会无条件信任的网站证书, 因此请妥善保护 `<data>/ca/` 目录, 并在备份服务端时把它一并纳入备份 (第 14 节). 本地 CA 签发的服务端证书有效期为两年, 剩余有效期不足 90 天时会自动续期: 可以通过执行 `install`, 或以 root 执行 `kaze-syncd ca --data <data>` 完成续期; 服务本身不会续期, 因为它读不到 CA 私钥. 运行中的服务会在一分钟内自动加载续期后的新证书, 无需重启. 因为默认情况下 CA 归 root 所有, 请配置一条每月执行一次的 cron 定时任务来负责续期 (`0 4 1 * * /mnt/data/kaze-sync/kaze-syncd ca --data /mnt/data/kaze-sync`); 如果忘了配, 服务在证书到期前最后 30 天内会在日志里持续发出警告. 后续执行 `install` 会自动沿用 CA 模式. 从自签名模式或外部证书模式切到本地 CA 模式只需执行 `install --ca`.

无论在哪两种证书模式之间切换, 切换后所有客户端都必须重新注册 (如果你是切到 `--ca` 模式且能直接编辑客户端配置文件, 也可以把新的 CA 指纹直接填入客户端 `device.json` 的 `fingerprint` 字段并重启客户端).

如果日后忘记了服务端的端口或证书指纹, 请以 root 身份重新执行一次 `kaze-syncd install` (可安全重复执行, 会再次打印这两项), 或者去服务端日志里查找带 `listening` 的那一行即可.

### 2.5 首次登录与管理员密码

服务端启动并放行端口后, 用现代浏览器 (Chrome 或 Edge 114 以上, Firefox 125 以上, Safari 17 以上) 打开 `https://<服务器>:<端口>/`, 输入刚才 `admin-password` 打印的密码登录. 登录会话保持 7 天有效.

`admin-password` 命令随时可以再次执行 (例如忘记了密码或登录失败过多被锁定时). 它会生成一个新的随机密码 (不支持自定义密码), 在终端显示一次, 并自动重启服务端; 重启会同时清除所有已登录会话和所有 IP 失败锁定. 执行方式为 `<data>/kaze-syncd admin-password`, 或使用另一处的二进制文件加上 `--data DIR`.

**资源占用.** 服务端的常驻内存在小数据量下约 24 MB, 在维护者自己约 37000 个文件的部署上约 35 到 65 MB. 每日垃圾回收 (第 13 节) 另需额外内存, 大小与文件数和历史版本的保留量成正比, 第 13 节的 "内存估算" 给出对照表. 简单地说: 文件数在 100 万以内, 保留期用默认的 30 天, 垃圾回收额外需要约 100 MB 以内的内存, 512 MB 内存的机器一趟就能完成. 数据量超出内存预算允许的范围时, 垃圾回收会拆成多趟扫描, 只是耗时更长, 不会失败, 也不会占用更多内存.

### 2.6 端口与防火墙规则

服务端 (`kaze-syncd`) 通过同一个 HTTPS 监听套接字同时提供 Web UI 和客户端同步协议, 不开启任何明文 HTTP 端口, 本地管理端口或 UDP 套接字, 因此防火墙配置只需一条规则: **在服务端开放一个入站 TCP 端口**, 让浏览器和客户端能够访问 `https://<server>:<port>/`.

客户端 (Linux 和 Windows 上的 `kaze-syncc`) 完全不开启任何监听套接字. 所有连接都由客户端主动向外发起到服务端, 因此客户端电脑不需要任何入站防火墙规则, 在 NAT 之后无需端口转发即可工作. 如果你还限制出站流量, 客户端只需要到服务端端口的出站 TCP 连接; 此外只有当你启用 Web Push (9.1 节) 时, 服务端才需要向浏览器厂商的推送服务发起出站 HTTPS 连接 (还需要 DNS); 两个程序都不会发起任何其他出站连接.

**开放哪个端口以及如何查看端口.** 首次执行时, `install` 会在 20000 到 59999 之间随机选定一个 TCP 端口并保存在服务端数据库中, 后续再次执行 `install` 时保持该端口不变. 如果想自己指定端口, 请传入 `--listen :<port>` (或指定具体地址和端口, 如 `--listen 127.0.0.1:<port>`). 使用默认的 `:<port>` 形式时, 服务端会在所有网卡接口上同时绑定 IPv4 和 IPv6, 因此如果客户端或浏览器通过 IPv6 连接, 请在 IPv4 和 IPv6 防火墙中都放行该端口. 因为 `kaze-syncd` 没有 `status` 子命令, 日后要查看端口可通过以下任一方式: 以 root 身份重新执行一次 `kaze-syncd install` (可安全重复执行, 会打印 `installed in <data>, listening on :<port>` 以及证书指纹), 查看服务端日志中的 `listening addr=... fingerprint=...` 行 (systemd 下用 `journalctl -u kaze-sync`, OpenRC/Alpine 下看 `/var/log/messages` 中标签为 `kaze-sync` 的 syslog, OpenWrt 下用 `logread`), 在服务端执行 `ss -ltnp`, 或查看已注册客户端上使用的 `https://<server>:<port>` 地址.

**放行端口.** 如果服务器运行在云平台上, 请在云厂商的安全组中添加一条入站规则, 允许你的客户端和浏览器所使用的地址访问 TCP `<port>` (如果客户端和浏览器的来源地址固定, 可以限制来源 IP, 不过该端口本身已有 TLS 证书指纹固定, 设备令牌, 随机管理员密码和失败后 IP 锁定多重保护). 对于服务器本机上的防火墙, 请在对应平台的命令中把 `<port>` 替换为你的监听端口:

**Ubuntu / Debian (`ufw`)** 或 **RHEL / Rocky / Fedora (`firewalld`)**:

```bash
ufw allow <port>/tcp                               # server (ufw)

firewall-cmd --add-port=<port>/tcp --permanent     # server (firewalld)
firewall-cmd --reload
```

**Alpine Linux (使用 `iptables` / `ip6tables` 的 OpenRC)**: 如果尚未安装 `iptables` 和 `iptables-openrc` 请先安装 (`iptables-openrc` 提供 `iptables` 和 `ip6tables` 的初始化脚本), 然后添加规则, 保存规则集并启用开机自启服务 (如果使用 IPv6, 请一并执行 `ip6tables` 各行):

```bash
apk add iptables iptables-openrc                   # server: 若尚未安装
iptables -A INPUT -p tcp --dport <port> -j ACCEPT  # server (IPv4)
rc-service iptables save
rc-update add iptables
ip6tables -A INPUT -p tcp --dport <port> -j ACCEPT # server (IPv6)
rc-service ip6tables save
rc-update add ip6tables
```

如果 `INPUT` 链中已经有 `REJECT` 或 `DROP` 规则, `-A` 会把新规则追加在它后面而永远不会命中; 此时请改用 `iptables -I INPUT -p tcp --dport <port> -j ACCEPT` (以及 `ip6tables -I INPUT -p tcp --dport <port> -j ACCEPT`), 把规则插入到链的顶部. `rc-service iptables save` (以及 `rc-service ip6tables save`) 可以在服务尚未启动时执行: 用 `iptables` 添加的规则已经生效, 保存下来的规则集会在开机时由 `rc-update add` 启用的服务自动恢复.

**OpenWrt**: 执行 `install` 时加上 `--wan` 会自动创建 WAN 防火墙规则. 也可以用 `uci` 手动创建同一条 `kaze-sync` 规则. 不带 `--data` 的升级会保留已有的规则; 如果带上了 `--data`, 请再加 `--wan` 以保留 WAN 访问.

```bash
./kaze-syncd install --data /mnt/data/kaze-sync --wan    # server: 自动配置

uci set firewall.kaze_sync=rule                          # server: 等效的手动命令
uci set firewall.kaze_sync.name=kaze-sync
uci set firewall.kaze_sync.src=wan
uci set firewall.kaze_sync.proto=tcp
uci set firewall.kaze_sync.dest_port=<port>
uci set firewall.kaze_sync.target=ACCEPT
uci commit firewall
/etc/init.d/firewall reload
```

## 3. 安装并注册客户端

登录 Web UI 之后, 下一步就是把你的各台电脑接入服务端.

注册客户端需要先在 Web UI 中生成一条注册命令. 在总览页点 **添加设备**, 输入设备名称 (只能含字母, 数字, `-` 和 `_`, 至多 32 个字符, 且不能与现有设备重名; 该名称会出现在指明设备的通知里), 再点 **生成注册码**. 弹出的对话框会显示一个有效期 15 分钟的一次性注册码, 以及可直接复制的 Linux 和 Windows 注册命令 (当服务端使用自签名证书或本地 CA 时, 命令末尾会自动带上 `--fingerprint`):

```text
kaze-syncc enroll https://sync.example.org:41873 K7QF-M2XD-9PLA --fingerprint sha256:...
```

请确认命令中的服务端地址是客户端电脑实际能访问到的域名或 IP 加端口, 且必须以 `https://` 开头.

### 3.1 Linux 客户端

在 x86-64 (`amd64`) Linux 电脑上, 从 [GitHub Releases](https://github.com/pellorao/kaze-sync/releases) 页面下载 `kaze-sync-0.3.5-linux-amd64.tar.gz` (选用与服务端兼容的版本) 和 `SHA256SUMS` 到同一个目录. 该归档内含 `kaze-syncc` 和 `kaze-syncd` 两个程序. (如果你的 Linux 电脑使用其他 CPU 架构, 没有对应的预编译发布包; 请参见[附录 A: 从源码编译](#附录-a-从源码编译).)

解压前先核对校验和:

```bash
sha256sum -c SHA256SUMS                                # client
```

(如果你没有同时下载 Windows 的 `.zip` 归档, `sha256sum` 会提示缺少该文件; 确认 `kaze-sync-0.3.5-linux-amd64.tar.gz` 这一行显示 `OK` 即可.)

接下来把 `kaze-syncc` 解压到一个**固定**目录 (例如 `~/.local/bin/`), 因为 `enroll` 会把当时二进制文件所在的路径写入自启动服务, 之后移动文件会导致自启动失效 (归档中同时带有 `kaze-syncc` 和 `kaze-syncd`, 这里只提取 `kaze-syncc`):

```bash
mkdir -p ~/.local/bin                                  # client
tar -xzf kaze-sync-0.3.5-linux-amd64.tar.gz -C ~/.local/bin kaze-syncc
```

然后在终端执行 Web UI 对话框里复制的命令 (如果 `~/.local/bin` 不在 `PATH` 中, 请直接运行 `~/.local/bin/kaze-syncc`):

```bash
kaze-syncc enroll https://sync.example.org:41873 <CODE> --fingerprint sha256:<HEX>    # client
```

`enroll` 会把设备令牌保存到 `~/.local/state/kaze-sync/`, 写入 systemd 用户单元文件 `~/.config/systemd/user/kaze-sync.service`, 启用开机自启并立即启动后台 agent. 你可以用 `systemctl --user status kaze-sync` 查看运行状态.

Linux 客户端要求系统提供 systemd 用户会话, 不支持其他初始化系统. 默认情况下 systemd 用户服务只在用户登录期间运行; 如果你希望未登录时 agent 也在后台同步, 请执行 `loginctl enable-linger` 开启 linger. 如果执行注册时加上 `--no-autostart`, 则只完成设备注册而不配置或启动服务, 之后需要时可执行 `kaze-syncc run` 在前台运行 agent.

### 3.2 Windows 客户端

在 x86-64 (`amd64`) Windows 电脑上, 从 [GitHub Releases](https://github.com/pellorao/kaze-sync/releases) 页面下载 `kaze-sync-0.3.5-windows-amd64.zip` (选用与服务端兼容的版本) 和 `SHA256SUMS`. 该 `.zip` 归档包含 `kaze-syncc.exe` 和无控制台窗口的 `kaze-syncc-agent.exe`. (如果你的 Windows 电脑使用其他 CPU 架构, 没有对应的预编译发布包; 请参见[附录 A: 从源码编译](#附录-a-从源码编译).)

解压前在 PowerShell 中计算归档的 SHA-256 哈希, 并与 `SHA256SUMS` 中 `kaze-sync-0.3.5-windows-amd64.zip` 那一行比对 (PowerShell 输出大写十六进制而 `SHA256SUMS` 为小写, 大小写不影响校验):

```powershell
Get-FileHash .\kaze-sync-0.3.5-windows-amd64.zip -Algorithm SHA256
```

把归档解压到一个**固定**目录 (`<安装目录>`), 让 `kaze-syncc.exe` 和 `kaze-syncc-agent.exe` 一起放在自启动将要记录的目录里:

```powershell
Expand-Archive .\kaze-sync-0.3.5-windows-amd64.zip -DestinationPath <安装目录>
```

在 `<安装目录>` 中打开终端, 执行对话框里的注册命令 (`kaze-syncc.exe enroll ...`).

`enroll` 会把设备令牌保存到 `%LOCALAPPDATA%\kaze-sync\`, 在注册表 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 下以名称 `kaze-sync` 注册无窗口的 `kaze-syncc-agent.exe` (无需管理员权限), 并立即启动它. 此后每次登录 Windows 时 agent 都会自动在后台启动.

### 3.3 注册之后

注册命令执行成功后, 这台电脑就会出现在 Web UI 总览页的设备表中, 在线时显示绿点. 新注册的设备还不会同步任何文件, 接下来需要在第 5 节中把文件夹映射给它.

如果日后需要重新注册同一台电脑 (例如重装操作系统之后), 因为设备名称不能重复, 请先在 Web UI 中吊销旧设备, 或者换一个新名称添加设备, 然后生成并执行新的注册命令.

## 4. Web UI

服务端和客户端连通后, 日常所有配置与状态查看都在 Web UI 中完成.

每个页面顶部都有同一条导航栏: 左侧是 **kaze-sync** 标志 (点击回到总览页), 右侧依次是通知铃铛 (第 9 节), 齿轮图标 (设置) 和退出按钮. 页面主标题采用路径形式展示你当前所在的位置 (例如 `总览 / Docs / projects`).

| 页面 | 地址 | 用途 |
|---|---|---|
| 登录 | `/login` | 输入管理员密码 |
| 总览 | `/` | 查看文件夹表和设备表; 提供 **新建文件夹**, **添加设备** 按钮 |
| 文件夹 | `/folders/<id>` | 浏览文件, 恢复历史版本, 设置写入控制 (5.1 节), 处理待处理改动 (第 8 节), 编辑文件夹排除规则, 删除文件夹 |
| 设备 | `/devices/<id>` | 查看与增删该设备的文件夹映射, 给设备改名或吊销设备 |
| 设置 | `/settings` | 配置时区, 界面语言, 版本保留天数, 单端写入时间窗, 全局排除规则 |

在 **总览** 页上, 两张表格集中展示整套系统的运行状态:
- **文件夹表** 显示每个文件夹的当前状态 (已同步, 同步中并附带待上传文件数, 有错误, 未映射, 设备离线), 映射了该文件夹的设备列表, 文件总数与总大小, 以及当前的错误数和提醒数.
- **设备表** 显示每台设备的操作系统, 最近连接时间, 该设备上各文件夹的同步状态, 客户端发布版本 (`x.y.z`; 客户端不上报时显示 `-`; 客户端过旧时旁边以红色显示 "过旧", 见第 15 节) 以及该设备是否已收到最新配置.

**页面如何自动更新.** 状态摘要会自动刷新: 每当后台状态发生变化, 几秒之内 (最快每 5 秒一次) 通知铃铛和总览页的两张表格就会自动更新. 但文件夹页里的文件列表不会自动刷新, 这样在大批量同步时你正在浏览的列表不会不停跳动重绘; 只有当你当前打开的这一层目录里直接发生变化 (该目录下的文件改变, 或直接子目录出现或消失; 子目录深处的变化不会触发) 时, 页面才会提示 **内容有更新, 刷新**. 同样为了避免文件改写后快速重扫造成状态闪烁, 只有同步工作持续超过约 3 秒时, 文件夹状态才会显示为 **同步中**.

在文件夹页浏览文件列表时, 每一行目录都会显示其下所有文件的总大小, 以及其中最近一次修改的时间 (已删除的文件不计入; 如果目录下只有已删除的文件, 则这两项留空). 这些统计数字是在读取列表时顺手累加出来的, 不增加额外开销.

界面上的时间默认按当前浏览器的时区显示为 `2026-11-03 22:48:27` 格式, 鼠标悬停在时间上可以看到具体时区名. 页面上的菜单, 对话框和实时更新依赖 JavaScript, 页面布局在手机屏幕宽度下同样可以正常操作.

**设置页.** 点击顶栏的齿轮图标可以调整五项全局设置:
- **时区**: 可选跟随浏览器, 或为所有浏览器固定一个 IANA 时区. 下拉列表中每个时区后面都标有它当前的 UTC 偏移 (如 `+09:00`, 已计入夏令时), 按偏移数值从 `-12:00` 到 `+14:00` 升序排列, 偏移相同的再按名称字母升序排列. 该设置只影响 Web UI 显示的时间以及你在输入框中填写的时间.
- **语言**: 可选跟随浏览器的语言列表 (默认项; 浏览器首选语言都不在支持的五种语言内时回退到英文), 或固定为五种语言之一. 语言选择只保存在当前浏览器本地, 因此手机和电脑可以用不同语言; 无论哪种语言, 时间统一保持 `2026-11-03 22:48:27` 格式.
- **版本保留**: 被覆盖或删除的旧版本保留的天数, 范围 1 到 3650, 默认 30.
- **单端写入时间窗**: 单端与不限模式下写入时间窗的分钟数, 范围 0 到 60, 默认 1 (含义见 5.1 节). 保存后在服务端立即生效, 无需重启任何客户端.
- **全局排除规则**: 对所有设备上的所有文件夹生效的排除规则 (见第 7 节).

## 5. 文件夹与映射

要让多台电脑同步同一批文件, 先在服务端新建一个文件夹, 再到每台要参与同步的设备页面上, 把这个文件夹映射到该电脑的一个本地目录.

**新建文件夹.** 在总览页点 **新建文件夹**, 输入至多 64 字节的唯一名称. 新建的文件夹最初是空的, 也没有关联任何设备, 同时通知铃铛里会出现一条写入控制提醒 (见 5.1 节), 请你决定谁可以写入该文件夹; 在你做出选择前提醒会一直保留.

**映射到设备.** 打开某台设备的页面, 点 **添加映射**: 从下拉框选择文件夹 (只列出这台设备上尚未映射的文件夹), 输入该电脑上的本机路径, 并决定是否允许接管非空目录:

- 路径必须是该设备操作系统下的绝对路径, 例如 Windows 上的 `D:\Docs`, Linux 上的 `/home/me/Docs`. 同一台设备上的两个映射路径不能互相包含.
- 如果本机目录还不存在, 客户端会自动创建它; 如果目录已存在且为空, 客户端直接开始同步.
- 如果本机目录已存在, 不为空, 而且以前从未同步过, 默认情况下客户端会拒绝同步并上报 `folder` 错误 (见第 9 节), 除非你勾选了 **允许接管非空目录**. 这道保护可以防止你不小心把路径填成 `C:\Users\me`, 导致把整个家目录全传上服务器. 勾选允许接管后, 客户端会把目录里已有的文件与服务端逐一对账: 内容完全相同的文件直接采纳而不重复传输 (从其他同步工具迁移过来, 或接入另一台已经有这批文件的电脑时就用这种方式); 两边内容不同的文件则会成为待处理改动, 等你决定 (第 8 节).
- 开始同步后, 客户端会在该本机目录根下放一个标记文件 `.syncroot`. 如果日后 `.syncroot` 消失了 (例如移动硬盘未挂载, 或目录被意外移走), 客户端会立即停止同步该文件夹并报错, 绝不会把目录消失误判成 "所有文件都被删除了". 请不要手动删除 `.syncroot`.

**修改映射.** 在设备页每行映射末尾点 **⋯** 菜单, 可以选择 **编辑映射…** 或 **删除映射…**. 修改本机路径在内部等同于先删除旧映射再新增映射: 旧路径下的本地文件原样保留在原处, 新路径则从头与服务端对账.

**删除映射.** 选择 **删除映射…** 后, 客户端停止同步该文件夹, 并删除该文件夹对应的本地状态库和 `.syncroot` 标记文件. 电脑上的本地文件原封不动, 服务端上的文件夹及其历史版本也完整保留.

**删除文件夹.** 如果要从服务端彻底删掉一个文件夹, 打开该文件夹页, 点标题行的 **⋯** 菜单, 选择 **删除文件夹…**. 为防止误删正在使用的文件夹, 只有当没有任何设备映射它时该项才可点击 (菜单项上会注明当前还有几台设备在映射它, 需先去设备页删掉这些映射). 删除文件夹会永久清除服务端上的这个文件夹及其全部历史记录, 它占用的数据块会在下一次垃圾回收时释放 (第 13 节). 各客户端电脑上的本地文件不会被删除.

同一台设备上映射的多个文件夹彼此独立运行: 某一个文件夹正在上传大文件时, 不会拖慢其他文件夹的同步.

### 5.1 写入控制: 谁可以在哪里写入

大多数时候你的几台电脑改的是不同的文件, 同步自然顺畅; 只有当两台电脑差不多同时改写同一个地方时才会出问题. 对单份文档来说, 这只是普通的冲撞; 对 Git 仓库就严重得多: 如果两台电脑都在同一个工作区里运行 `git`, 它们会各自改写 `.git/index` 等内部文件, 两边混在一起就会把仓库搞坏. kaze-sync 既不尝试自动合并这类写入, 也不生成第二份文件, 而是遵循一条规则: **先到达服务端的电脑获胜, 后到的电脑停止同步文件夹的这一部分, 直到你决定怎么处理它的改动.** 等待期间不会丢失任何数据: 它的修改作为待处理改动留在它自己的磁盘上, 由你在对话框里决定如何处理 (第 8 节).

**"冻结" 是什么意思.** 像这样暂停下来的设备称为被冻结. 它对受影响的目录双向停止同步: 既不上传本地在该目录的改动, 也不把服务端在该目录的改动写入本地文件; 其他设备和其他目录则照常同步. 冻结状态在 agent 重启后依然保留, 因此重启客户端不会解除冻结. 等你把该目录下的每一条待处理改动都处理完后, 冻结才会结束, 设备随后从服务端重新读取该目录并恢复同步.

**三种写入模式.** "这一部分" 的范围正是通过写入控制来划定的. 每个文件夹, 目录和文件都处于三种写入模式之一, 由模式决定谁可以写入, 以及两台设备相撞时冻结多大范围:

| 模式 | 允许谁写 | 两台设备同时写入时 |
|---|---|---|
| 不限 | 每台设备都可以写, 每个文件各自判断. | 只冻结后到设备上两边都改过的那个文件, 它的其他文件继续同步. |
| 单端 | 同一时刻由一台设备写整个目录. 最近一次写入到达服务端的设备是当前写入者. | 后到的设备在整个目录上被冻结, 不只是那个文件. |
| 独占 | 只有你指定的那台设备可以写. | 其他设备的任何改动都会冻结它在该目录的同步. |

在单端模式下, 一次写入会不会冻结设备取决于到达时机以及本机内容是否过时, 因此需要先弄清服务端把什么算作 "同时".

**单端模式下什么算 "同时".** 服务端使用自己的时钟和版本号来判断设备改动到达的先后, 各台电脑上的系统时钟无关紧要. 另一台设备的写入只要满足以下任一条件, 就算作同时写入:

- 它在当前写入者最后一次写入之后的**单端写入时间窗**内到达 (默认 1 分钟, 见第 4 节设置页). 这一条针对的是某台设备正在写入, 而一次 `git commit` 分几批到达服务端的情形.
- 它基于过时的内容, 即这台设备上次同步该目录之后, 其他设备已经在目录里写过内容. 这一条针对的是笔记本离线时改了仓库, 重新联网时台式机早已改过该仓库的情形.

把时间窗设为 0 即可关闭第一条判断, 只保留第二条. 不限模式同样使用这个时间窗, 但只按单个文件判断: 如果另一台设备在不到一个时间窗前改过同一个文件, 后到的写入同样算作同时写入.

**设置在哪里生效.** 新文件夹的根目录默认设为**单端**, 而且整个文件夹不必只用同一种模式. 设在某个目录上的模式会管辖该目录及其下的全部内容, 直到更深层的子目录定义了自己的设置; 没有单独设置的目录自动继承上一层. 更深层的设置既可以放宽也可以收紧上层模式: 例如根目录设为不限, `scratch/` 设为单端, `scratch/repo/` 设为独占. 单个文件也可以设为独占, 但不能设为不限. 如果日后你吊销了持有独占的设备, 或删除了它对该文件夹的映射, 它独占的目录会自动退回单端模式.

**该选哪种模式.** 选择的依据是目录里的文件必须整体一起变化, 还是可以各自独立修改:

- **Git 仓库, 或任何需要整体保持一致的目录.** 将仓库所在目录设为单端; 如果固定只在某一台电脑上工作, 则设为独占. 使用独占时请只在所有者设备上运行 `git`: 就连 `git status` 也会改写 `.git/index`, 在其他设备上这同样算作一次写入, 会冻结那台设备上的仓库. 使用单端时, 如果另一台设备在不到一个时间窗前刚写入过, 或第二台设备尚未完全同步, 在第二台设备上运行 `git` 会冻结那里的仓库; 否则写入会被接受, 同时第二台设备在一个时间窗内成为当前写入者, 这期间若在第一台设备上运行 `git` 就会冻结第一台设备.
- **文件夹根目录.** 根目录默认用单端最稳妥, 但也有一个需要注意的代价: 如果笔记本离线时改了一个文件, 而期间台式机改了同一文件夹里的任何其他文件, 笔记本重新联网时整个文件夹都会被冻结, 哪怕两边改的文件毫无关系. **如果文件夹里的文件彼此独立 (例如文档, 照片, 笔记), 建议把根目录设为不限, 只把代码仓库这类子目录设为单端或独占.** 这样两台设备只有改到同一个文件时才会相撞.

**设置写入控制.** 确定某个目录要用哪种模式后, 在文件夹页按以下步骤设置:

1. 在 Web UI 中打开文件夹.
2. 点目标目录或文件所在行的 **⋯** 菜单, 选择 **写入控制…** (也可以点页面标题行的 **⋯** 菜单, 它作用于当前正在浏览的目录, 在顶层时即文件夹根目录).
3. 选择 **继承**, **不限**, **单端** 或 **独占**. 若选择独占, 还要在下拉列表中选择所有者设备 (列表只包含映射了该文件夹的设备, 并标出是否在线).
4. 点 **保存**.

如果当前有设备在这个目录里 (或受本次修改影响的上级, 下级目录里) 有待处理改动 (第 8 节), 点 **保存** 时会先弹出确认框, 列出待处理改动的数量及所在设备, 并提示保存后这些改动会按新规则重新提交 (例如目录改为不限后会作为普通改动提交), 且有可能再次成为待处理. 如果点取消, 原有设置保持不变.

在文件列表中, 写入控制通过名称前的图标而非文字展示: 灰色普通图标代表不限, 蓝色 `1` 代表单端, 紫色锁代表独占; 直接设在该路径本身时图标为实心, 从上层继承时只有轮廓; 图标上若有红色三角则表示其下有待处理改动. 同样的图标也会显示在总览页的每个文件夹名称前 (不用点进文件夹就能看到根目录的设置), 以及文件夹页标题行的当前目录前. 把鼠标悬停在图标上, 点按图标, 或按 `Tab` 聚焦名称, 会弹出提示框, 用文字说明当前生效的设置 (**不限**, **单端** 或 **独占 · 设备名**) 及其含义 (不限目录下的文件仍显示灰色图标, 提示框会补充说明该文件自成一个单端范围, 因此两台设备改同一个文件只冻结这一个文件; 设置是直接指定还是继承由实心或轮廓区分, 写入控制对话框中也会写明来源路径); 按 `Esc` 关闭提示. 文件夹主标题下方的一行摘要也会始终写明当前所看目录适用的设置, 继承自哪里, 以及在单端模式下当前写入者是谁. 你还可以直接访问 `/folders/<id>?wc=<路径>` 打开对应路径的写入控制对话框, 下文的新文件夹提醒正是使用这个链接.

**新文件夹的提醒.** 因为根目录的默认模式决定了文件夹多久会冻结一次, Web UI 对每个新建文件夹都会提醒你确认一次 (升级到本版本前已有的文件夹也会提醒一次). 通知铃铛里会显示一条黄色提醒 "还没有设置写入规则, 根目录按默认单端", 说明三种模式并提供两个链接: **设置写入规则…** 直接打开根目录的写入控制对话框, **保持默认** 则确认根目录采用单端模式. 只要为该文件夹保存过任意一项写入设置, 这条提醒也会自动消失; 一旦消失就不会再出现, 即使日后把所有写入设置都删掉也不会恢复, 且这条提醒不会推送到手机.

**恢复与旧版客户端.** 还有两项操作与写入控制相关:

- **从 Web UI 恢复** (第 11 节) 总是会被接受并同步到所有设备. 因为恢复本身算作一次写入, 此后一个时间窗内, 或在尚未收到恢复文件的设备上修改单端目录, 改动都会成为待处理. 如果恢复范围里包含独占目录, 或当前写入者在不到一个时间窗前刚写入过的单端目录, 恢复对话框会提示: 恢复照常进行并同步到所有设备, 此后修改该范围的其他设备会被冻结 (单端目录为时间窗内, 独占目录为所有者以外的任何设备).
- **旧版客户端.** 协议版本对服务端来说太旧的客户端会停止同步, 直到你升级它 (第 15 节), 以防它绕过写入控制规则写入.

## 6. 设备

设备完成注册 (第 3 节) 并开始同步后, 你可以在 Web UI 中随时查看它们的在线状态, 给设备改名, 或在淘汰电脑时吊销设备.

设备表中的 **在线** 状态表示该设备当前正与服务端保持着挂起的长轮询连接, 或者在最近 90 秒内刚结束过一次长轮询. 如果某台已注册设备连续 3 天没有连接服务端, 系统会产生一条提醒通知 (第 9 节), 方便你及时发现某台电脑上的后台 agent 是否停止了运行.

**设备改名.** 打开设备页, 点标题行的 **⋯** 菜单, 选择 **设备改名…**. 新名称的规则与添加设备时相同 (字母, 数字, `-` 和 `_`, 至多 32 个字符), 且不能与其他设备重名. 设备继续用原有的令牌和映射同步, 不需要重新注册. 当前文件, 待处理改动和通知立即显示新名称, 版本历史中较早的条目保留设备写入它们时的名称. 客户端 agent 在下一次取得配置时改用新名称并记在本地 (比本版本旧的客户端在升级前仍使用注册时的名称).

**吊销设备.** 当某台电脑遗失, 淘汰或准备重装时, 打开它的设备页, 点标题行的 **⋯** 菜单, 选择 **吊销设备…**. 该设备的认证令牌会立即失效, 它在服务端上的所有文件夹映射也会一并删除, 而电脑磁盘上的本地文件原样保留. 如果被吊销电脑上的客户端 agent 还在运行, 它会在日志中记录 `sync is stopped, the server does not accept this device`, 并把重试间隔放慢到大约每十分钟一次. 随后要清理这台电脑上的客户端程序, 请按 16.1 节操作.

## 7. 排除规则

同步文件夹里往往会有编辑器临时文件, 构建产物或本地缓存, 把它们传上服务端既浪费流量又白白制造大量历史版本. 排除规则用来指定哪些路径不参与同步.

排除规则全部保存在服务端, 分上下两层 (没有绑定到单台设备的规则):

1. **全局规则**: 在设置页的 **全局排除规则** 中编辑, 对所有设备上的所有文件夹生效. 安装时会写入一份默认规则列表 (见下文).
2. **文件夹规则**: 在每个文件夹页的顶层点 **排除规则** 按钮 (按钮上会显示当前规则条数) 进行编辑. 文件夹规则会追加在全局规则之后计算.

**规则语法.** 语法与 `.gitignore` 一致, 每行写一条规则, 匹配的是相对于文件夹根目录的路径, 路径分隔符统一用 `/`:

- 空行自动忽略; `#` 开头表示注释; `!` 开头表示取反 (重新包含); 以 `/` 结尾只匹配目录; 开头或中间含有 `/` 的模式固定从文件夹根目录开始匹配, 不含 `/` (结尾的 `/` 除外) 的模式则匹配任意目录层级下的同名项.
- `*` 和 `?` 匹配除 `/` 外的字符; `[a-z]`, `[!a-z]`, `[[:alpha:]]` 为字符类; `**/x`, `x/**`, `a/**/b` 可以跨多层目录匹配.
- 同一路径命中多条规则时, **最后一条匹配的规则决定结果**. 但要注意: 一旦某个目录本身被排除, 客户端就不会再进入该目录扫描, 因此不能直接用一条 `!` 规则只把该目录下的某个文件重新包含回来. 如果想保留被排除目录下的某一个文件, 必须先重新包含该目录本身, 再排除该目录下的全部内容, 最后重新包含那个目标文件.
- 在 Windows 设备上匹配不区分大小写, 在 Linux 设备上区分大小写.
- 不支持花括号展开 `{a,b}`, 也不读取同步目录内部的 `.gitignore` 文件.

常用示例:

| 规则 | 含义 |
|---|---|
| `node_modules/` | 任意层级下名为 `node_modules` 的目录 |
| `/Videos/` | 只排除文件夹根目录下的 `Videos` 目录 |
| `*.iso` | 任意层级下的所有 `.iso` 文件 |
| `Projects/**/bin/` | `Projects` 下任意深度的 `bin` 目录 |
| `/*` 后接 `!/Docs/` | 排除根目录下的所有内容, 只同步 `Docs` 目录 |

因为文件夹规则接在全局规则之后计算, 且最后匹配的一条生效, 你可以用 `!` 在单个文件夹里抵消某条全局规则. 例如当全局规则排除了 `build/` 时, 在某个文件夹规则里加上下面三行, 就能在该文件夹中唯独同步 `build/keep.txt`:

```text
!/build/
/build/*
!/build/keep.txt
```

在规则编辑框中输入时, 注释行显示为灰色, 语法无效的行显示为红色; 把鼠标悬停在红色行上可以看到具体报错, 所有错误也会汇总列在文本框下方. 只要存在任何无效行, 保存都会被拒绝, 原有规则不会被改动.

**内置排除与默认全局规则.** 有三类内部文件始终由系统内置排除, 无法被任何规则覆盖: 同步根标记文件 `.syncroot`, 下载过程中的临时文件 `.syncpart-*` (超过一天未变动的残留临时文件会在下一次扫描时自动清理), 以及 SQLite 数据库的旁文件 `-wal`, `-shm`, `-journal` (第 10 节).

此外, 首次安装时系统会在 **全局排除规则** 中写入一份默认规则, 排除各平台常见的临时文件与元数据:
- Office 和 Windows 的遗留文件 (`~$*`, `*.tmp`, `Thumbs.db`, `desktop.ini`, `$RECYCLE.BIN/`, `System Volume Information/` 等)
- 编辑器备份和锁文件 (`*~`, `.~lock.*`, `.*.sw?`, `*.kate-swp`)
- 浏览器未下载完的临时文件 (`*.part`, `*.filepart`, `*.crdownload`)
- macOS 元数据 (`.DS_Store`, `._*`, `.Trashes/` 等)
- Linux 桌面与文件系统遗留文件 (`.Trash-*/`, `.directory`, `.fuse_hidden*`, `.nfs*`)
- 其他同步工具的元数据目录 (`.stfolder/`, `.stversions/`, `.stignore` 等)

打开设置页即可查看和修改完整列表; 默认规则只在安装时写入一次, 之后完全以设置页里保存的文本为准. 至于项目自身的依赖目录 (如 `.venv/`, `node_modules/`), 缓存目录, 或每隔几秒就改写一次从而会让服务端积累海量版本的文件, 默认规则有意不包含它们, 请按自己的目录结构手动添加.

**规则修改后会发生什么.** 保存新规则后, 在线客户端会在一秒内收到更新:
- 当某个路径**新变为被排除**时, 客户端只是停止跟踪它, 各台电脑上的本地文件原样保留; 客户端自己永远不会因为排除规则而删除任何本地文件. 相反, 服务端上已经存有的同名文件会在你保存规则时由服务端统一删除 (并转入版本历史, 详见下一段).
- 当你**取消某条排除规则**时, 客户端会重新扫描此前被忽略的路径并与服务端对账, 两边如有差异则成为待处理改动, 等你决定 (第 8 节).

**在 Web UI 中预览并保存规则.** 因为新增排除规则会把服务端上已经同步且命中规则的文件删掉, Web UI 要求在保存前先预览命中的文件:
1. **预览.** 文件夹页的排除规则对话框以及设置页的全局排除规则卡片都只有一个主操作按钮. 当文本框里的内容与已保存的规则不同, 且还没有预览过时, 该按钮显示为 **预览**. 点击 **预览** 不会保存任何修改, 而是列出服务端现有文件中会被当前规则命中的文件, 并标明 "尚未生效" (显示真实命中总数和前 50 条路径, 全局规则预览中还会附带所属文件夹名); 如果没有任何已同步文件命中, 则提示 "没有命中服务端文件".
2. **用过滤框筛选预览列表 (可选).** 如果命中的服务端文件很多, 可以用预览区顶部的单行 glob 过滤框缩小显示范围: 不含 `/` 的写法匹配文件名, 含 `/` 的匹配整条路径, `*` 不跨 `/`, `**` 可跨 `/`, `?` 匹配单个字符, 且不区分大小写. 过滤后同样最多列出 50 条路径, 列表下方会写明 "命中的服务端文件: N 个, 过滤后 M 个, 目前仅显示 K 个". 注意过滤只改变界面上列出的条目, 保存时仍会删除全部 `N` 个命中的服务端文件.
3. **保存.** 看完预览后, 如果没有命中任何文件, 主按钮会变成 **保存**; 如果有命中文件, 则变成红色的 **保存并删除 N 个文件**. (要是预览之后你又改动了规则文本, 预览区会收起, 按钮重新变回 **预览**.) 点击保存按钮后会立即生效, 不再二次弹窗确认. 如果在你查看预览的这段时间里, 恰好有命中规则的文件被上传或删除, 本次保存会中止, 界面刷新为最新预览并提示 "命中文件有变化, 请再核对", 核对无误后再点一次按钮即可完成保存.

保存规则所删除的服务端文件按普通删除处理, 会进入版本历史, 在版本保留期内随时可以恢复. 所有设备上的本地文件副本 (包括当时离线或还没拉取新规则的设备) 都会原样保留在磁盘上, 只是此后不再同步; 以后新产生的命中文件则从一开始就不同步, 更不会被删除.

如果浏览器禁用了 JavaScript, 在有命中文件时点击保存会先返回预览页面, 再点页面上的红色按钮才真正保存. 点击 **取消** 会直接丢弃未保存的修改并关闭对话框, 不再询问; 用其他方式 (例如按 `Esc`) 关闭对话框时, 若有未保存的修改会先询问是否放弃.

## 8. 同时写入与处理对话框

日常使用时, 一台设备上的修改在几秒内就会传到服务端并同步给其他设备, 因此你很少会看到本节介绍的对话框. 它们主要在两台设备失联期间改了同一个地方, 或目录的写入模式 (5.1 节) 拒绝某次写入时才会派上用场. 即便遇到这种情况, kaze-sync 也绝不丢数据, 绝不依赖系统时钟, 也不会生成带冲突后缀的副本: 先到达服务端的设备获胜, 后到那台设备想写入的内容会暂存为**待处理**, 等你决定如何处理.

**哪些会成为待处理.** 什么情况算冲撞取决于改动所在路径的写入模式, 但下表中的文件级情形在后到的设备上总会成为待处理 (唯一的例外是第一行, 因为两台设备改成了完全相同的内容):

| 本设备 | 服务端现状 | 结果 |
|---|---|---|
| 修改 | 修改, 内容相同 | 直接采纳, 不传输数据, 不待处理 |
| 修改 | 修改, 内容不同 | 待处理 |
| 修改 | 已删除 | 待处理 |
| 删除 | 修改 | 待处理 |
| 新建 | 已存在, 内容不同 | 待处理 |
| 文件 | 同名的目录 (或相反) | 待处理 |

即使没有任何单个文件相撞, 写入模式本身也可能让一次写入成为待处理, 即单端目录里后到的写入者, 或独占目录里非所有者的改动. 此外, 接管非空目录 (第 5 节) 或还原服务端备份 (第 14 节) 时与服务端内容不一致的本地文件, 也会同样成为待处理. 即使某个服务端文件最终被你选择覆盖, 被替换的旧内容也依然保存在版本历史中.

**怎么看到待处理的改动.** 只要设备上有待处理改动, 通知铃铛里就会为每台受影响的设备和目录列出一行错误, 例如 `"laptop 上有 3 个改动待处理: /repo (与 desktop 同时写入)"`. 括号里注明原因, 可能为 `"与 <设备> 同时写入"`, `"<设备> 独占"`, `"与服务端版本冲突"`, `"文件与目录同名"` 或 `"服务端历史已重置"` (9.1 节的 Web Push 消息只报告设备名, 文件夹名和待处理条数). 同时, 文件夹页的文件列表各行会显示红色的 **待处理** 标签 (每台设备一个), 设备页上也会显示 `"待处理 N"`. 点击通知里的链接或文件行上的 **待处理** 标签 (或者直接访问 `/folders/<id>?held=<设备 id>`) 即可打开处理对话框. 如果该设备当前离线, 对话框会注明这一点, 并在设备重新上线后执行你的决定.

**处理对话框.** 对话框按被冻结的目录分组列出一台设备上的全部待处理改动. 因为一次 `git` 操作往往会同时改动几百个彼此关联的文件, 通常你会用每组上方的两个按钮对整组一次性做出决定:

- **全部丢弃**: 丢弃该设备在这一组里的全部待处理改动, 将本地文件替换成服务端的当前版本.
- **全部上传并覆盖**: 先请你确认, 然后把该设备在这一组里的改动全部上传并取代服务端版本; 被取代的服务端旧内容会转入版本历史, 随时可以恢复. 只有该设备实际改过的文件会被覆盖, 它没动过的文件仍保持先到设备留下的状态.

如果某一组需要逐个文件斟酌, 可以点整组按钮下方的 **逐个选择**, 展开一张逐行明细表: 每行对应一个路径, 列出本机改动 (修改, 新增或删除, 附带大小和时间), 该改动所基于的版本, 服务端当前版本 (及写入该版本的设备) 以及动作下拉框. 为需要处理的行选好动作 (其余行可以留空暂不处理), 再点 **执行所选**:

| 动作 | 何时可选 | 结果 |
|---|---|---|
| 上传 | 服务端在设备那个版本之后没有改过该路径 | 设备的改动进入服务端, 再同步给其他设备 |
| 上传并覆盖 | 总可选 | 同样上传, 取代服务端现在的内容; 服务端旧内容保存在版本历史中 |
| 丢弃 | 总可选 | 丢掉设备的版本, 下载服务端当前的版本 |

当文件与目录同名时, 只提供 **上传并覆盖** 和 **丢弃** 两个选项. 请注意不要在同一个代码仓库或需要整体一致的目录里混用不同动作, 否则服务端可能会留下两边版本拼凑在一起的内容 (直接用整组按钮处理就能避免这一点). 一旦同一组里的各行选了至少两种不同的动作, 表格上方就会弹出警告: `"同一范围内采取不同动作, 可能导致服务端混杂两台设备的版本. 建议对整个范围采取同一动作."` 这只是一条警告, 不会阻止你应用所选动作. 要给很多行设同一个动作, 勾选这些行 (表头的复选框全选), 再点 **把勾选的行设为** 后面的按钮; 不能采取该动作的行保留原来的选择, 并提示 "N 行保留原动作". 没有任何一行能用某个动作时 (例如只列出目录行时的 **上传**), 该按钮禁用, 按钮旁的一行文字说明原因. 每组表格最多展示 2000 行. 超过时按目录折叠: 每个目录合为一行 (`"N 个改动"`), 它的动作 (**上传并覆盖** 或 **丢弃**) 作用于其下的全部待处理改动, 表格下方会注明. 无法这样折叠时 (例如全部改动都在同一个目录里), 表格只展示前 2000 行并注明剩余条数, 超出部分请用整组按钮处理. 对话框打开期间不会自动刷新, 如需查看最新进展请关闭后重新打开.

**被丢弃的文件去哪里: `.syncsaved`.** 选择丢弃并不意味着本地改过的那份文件直接消失. 对话框里的 **丢弃时把本机那一份保存到 .syncsaved** 默认处于勾选状态: 客户端在下载服务端版本之前, 会先把本机文件移到同步根目录下的 `.syncsaved/<YYYYMMDD-HHMMSS>/<原路径>`. 同一次决定丢弃的所有文件都会归在同一个带时间戳的目录里, 方便你随时手动拷回. 如果想直接删掉本机文件, 取消勾选该复选框即可 (但当本机目录与服务端同名文件相撞时, 本机目录总是会被移入 `.syncsaved`, 绝不会直接删除). `.syncsaved` 本身永远不会参与同步, 客户端扫描文件夹时会自动清理其中超过 30 天的时间目录. 如果你希望本机版本直接成为服务端上的最新版本, 请改选 **上传并覆盖**.

**保护措施.** 从你打开对话框到设备真正动手执行之间存在时间差, 期间本机文件或服务端版本都可能再次变化. 因此客户端只有在确认两边都没有新变化时才会执行决定; 一旦期间发生了变化, 该路径的动作就会中止并保持待处理状态, 同时在行内提示原因:

- `"本机又改过, 请重新选择"`: 本机文件的大小或修改时间已与对话框展示时不同, 确保绝不上传或丢弃你未曾核对过的新改动.
- `"服务端又变了, 请重新选择"`: 对话框打开后又有人改写了服务端上的该路径, 该行会随之更新显示服务端的新状态.
- `"执行失败, 请重试"`.

整组按钮同样受此保护: 它们只作用于自你打开对话框以来服务端未曾变动过的路径, 期间服务端发生过变化的路径会继续保持待处理, 留给你逐个查看.

**做出决定之后.** 点击执行按钮会把你的决定排入服务端内存中, 等该设备下一次联系服务端时执行 (通常在几秒之内). 在设备执行完毕并使该行消失之前, 各行会在最多 10 分钟内显示 `"等待 laptop 执行"` (即该设备的名称). 如果超过 10 分钟设备仍未回报, 该标签会隐去, 各行恢复显示动作菜单, 看起来像尚未决定, 但刚才的决定依然在服务端排队, 设备一连上来就会执行 (此时重新选择动作会替换排队中的决定). 因为排队中的决定只保存在服务端内存里, 而待处理改动保存在客户端设备上, 如果服务端在设备执行之前重启了, 设备会重新上报待处理改动, 你只需再点一次按钮即可.

当一个目录下的所有待处理改动都执行完毕后, 设备会从服务端重新读取该目录并解除冻结. 如果在仍有待处理改动时修改了目录的写入控制模式 (例如改为不限), 设备会按新模式重新提交这些待处理改动.

**其他文件系统情形与边界情况.** 并非所有意外都来自两台设备同时写入. 下面这些情形来自改名, 来自 Windows 和 Linux 处理方式不同的名称与链接, 以及文件夹不同步的内容:

- **改名或移动.** 改名或移动文件在同步时表现为旧路径删除加上新路径新增, 且内容哈希不变. 因此其他设备会直接在本地磁盘上复制已有数据块, 不会重新从服务端下载. 如果一台设备移动了整个目录, 而同时另一台设备修改了该目录里的某个文件, 被修改的文件会保留在旧路径下, 确保修改不丢失.
- **文件名大小写.** 因为一个文件夹可能同时被 Windows 和 Linux 映射, 服务端在同一个文件夹内对路径名不区分大小写. 如果 Linux 客户端在同一个目录下同时创建了 `A.txt` 和 `a.txt`, 先上传的那个成功, 后到的那个会被服务端拒绝 (`被拒绝`) 并在通知中显示为错误; 请在客户端上把其中一个改名. 在 Windows 上仅改变字母大小写的改名 (`a.txt` 改为 `A.txt`) 可以正常同步.
- **Windows 非法名称.** 为了保证任何文件夹都能在 Windows 上正常同步, 服务端在所有设备上都会拒绝 Windows 不允许的文件名: 包含 `<>:"\|?*` 或控制字符的名称, 以点号 `.` 或空格结尾的名称, 以及 Windows 保留设备名 `CON`, `PRN`, `AUX`, `NUL`, `COM1` 到 `COM9`, `LPT1` 到 `LPT9`. 请在创建该文件的设备上把它改名, 或用排除规则忽略它.
- **文件与目录同名.** 如果一台设备创建了文件, 而另一台设备在完全相同的路径创建了目录, 后到达服务端的一方的改动成为待处理, 对话框只提供覆盖和丢弃.
- **符号链接.** 符号链接只同步链接本身, 从不跟随链接去读写目标: 服务端把链接目标按字面原样保存为文本 (无论是相对路径, 绝对路径, 悬空链接, 还是指向同步文件夹外部的链接都会原样同步; 至于链接目标在另一台设备上是否存在, 由你自己决定). 程序绝不会通过符号链接去同步目标文件的内容, 也绝不会穿过符号链接读写任何东西, 因此指向文件夹外部目录的符号链接不可能诱使客户端把下载的文件写到同步目录之外. 链接目标长度超过 4096 字节的符号链接会被跳过 (上报为 `skipped`, `已跳过`).
  如果接收端的设备无法创建符号链接 (最常见的是未开启开发人员模式的 Windows), 该符号链接会安全地保留在服务端, 而那台 Windows 电脑上不会创建任何文件. 为了避免大量报警刷屏, 通知铃铛里每台设备只会折叠显示一行提醒 (`win: 3 个符号链接未建立 (Windows 需开启开发人员模式)`), 文件夹页则把这些链接列为灰色的 **未同步** 行. 当你在 Windows 上开启开发人员模式 (设置 -> 系统 -> 开发者选项) 后, 客户端会自动把这些符号链接建出来, 无需重启进程. 铃铛里的那行提醒只在受影响的符号链接集合变化时才会更新.
- **不同步的内容.** Windows 联接点 (junction) 既不跟随也不同步 (上报为 `已跳过`). 空目录, 除可执行位以外的文件权限, 文件所有者和扩展属性都不同步. 文件内容一律按字节原样复制, 不做换行符转换.

## 9. 通知

因为客户端 agent 在电脑后台静默运行, 不设托盘图标也不弹窗打扰, 所以所有需要你留意的异常都集中在 Web UI 顶栏的通知铃铛里展示 (如果你希望不打开网页也能收到提醒, 见 9.1 节的 Web Push 消息推送).

点击顶栏的铃铛图标即可打开通知浮窗. 铃铛图标上的数字代表当前未解决的事项总数: 存在错误时显示为红色, 只有提醒时显示为黄色, 超过 99 条时显示 `99+`. 浮窗内部按文件夹分组展示; 长期离线的设备则归在 **设备** 分组下. 每一条通知都包含问题描述, 文件路径 (点击可直接跳转到文件夹页对应的文件行, 并高亮显示 2 秒), 涉及的设备, 问题起始时间以及处理提示. 如果同一台设备在同一个文件夹下有超过 5 条同类通知, 会自动折叠成一行摘要, 点击即可展开.

通知完全由系统当前状态实时算出, 因此界面上没有 "忽略" 或 "清除" 按钮: 只要你把问题原因处理掉, 对应的通知就会自动消失. 客户端上报的异常保存在服务端内存中, 所以服务端重启后要等客户端再次上报才会重新显示; 而长期离线的设备直接由数据库状态算出, 不依赖客户端重报; 待处理改动存放在设备上, 服务端重启后各设备会在片刻内重新上报.

| 来源 | 级别 | 处理 |
|---|---|---|
| 有待处理改动 ("N 个改动待处理") | 错误 | 用通知里的链接打开处理对话框, 决定保留哪些内容 (第 8 节) |
| 新文件夹还没有设置写入规则 | 提醒 | 用 **设置写入规则…** 选择谁可以写, 或用 **保持默认** 接受根目录为单端 (5.1 节) |
| `rejected` (被拒绝): 大小写冲突, 非法名称 | 错误 | 在该客户端上改名, 或用排除规则忽略该路径 |
| `io` (读写错误): 其他本地读写错误 | 错误 | 按报错消息检查该客户端的磁盘状态和文件权限 |
| `folder` (文件夹错误): 同步根缺失, 或非空目录未获准接管 | 错误 | 挂载磁盘, 或在设备页修正路径或勾选允许接管非空目录 |
| `in_use` (占用中): 文件被锁定, 正在写入, 或是打开着的 SQLite 数据库 | 提醒 | 关闭正在占用它的程序 (第 10 节) |
| `skipped` (已跳过): 本设备无法建立的符号链接 (见第 8 节), 目标超过 4096 字节的链接, Windows 联接点, 非 UTF-8 文件名 | 提醒 | 不想看到这条提醒时可用排除规则忽略它 |
| `report` (待处理改动未上报): 本设备无法把待处理的改动告知服务端 | 提醒 | 无需处理, 会自动重试; 请确认本设备能连上服务端 |
| 设备 3 天没有连接 | 提醒 | 让该设备重新上线, 或在设备页吊销它 |
| 设备的客户端协议过旧, 同步已停止 | 错误 | 升级该设备上的客户端 |
| 服务端数据盘剩余空间低于 256 MB | 错误 | 释放数据盘空间 |
| 每日垃圾回收清理失败 | 错误 | 查看服务端日志; 下一次成功后该条消失 |
| 服务端证书无法续期或即将过期 | 错误 | 查看服务端日志和证书文件 (2.4 节) |
| 某个推送订阅已失效 | 提醒 | 在设置页删除它, 再在该浏览器里重新开启推送 (9.1 节) |

客户端上报为 `已跳过` 或 `被拒绝` 的文件并没有传到服务端上; 为了让你在浏览目录时也能直观看到它们, 文件夹页会把这些条目作为灰色的 **未同步** 行列在所在目录中, 打开行菜单点 **详情** 即可查看具体消息, 设备名和起始时间. 此外, 文件夹页和设备页的主标题下方都有一行状态摘要: 点击其中的问题小结 (例如 `1 个错误, 2 个提醒`) 可直接打开通知浮窗, 查看设备数 (`2 台设备`) 的提示则会列出具体设备名. 在文件夹页中, 这行摘要里的文件数, 总大小, 错误数和提醒数统计的是当前所看目录及其各级子目录; 而同步状态词 (同步中, 错误, 设备离线等) 描述的是整个文件夹, 因此只在文件夹顶层显示, 进入子目录后不显示.

### 9.1 用 Web Push 推送消息

如果你想在不打开 Web UI 的情况下及时获知异常, 服务端可以用 Web Push 向你手机或电脑的浏览器发送简短的推送消息. 推送只由服务端发出, 客户端不发送任何推送, 也不需要设置. 旧的 ntfy 推送 (`ntfy.json`) 已删除: 留下的 `ntfy.json` 不再被读取 (服务端和客户端各记一行 info 日志), 请删掉它并改用 Web Push.

推送默认关闭, 要在某个浏览器里开启:

1. 使用本地 CA 证书模式 (2.4 节) 或你自己的证书. 浏览器只在受信任的证书上允许推送, 所以默认的自签名证书不能用, 点过证书警告也不行. 使用本地 CA 时, 先在手机或电脑上导入 CA (2.4 节).
2. 在 Web UI 中打开 **设置**, 在 **推送通知** 卡片里打开 **在本浏览器接收推送** 开关, 并在浏览器询问时允许通知. 每个要收提醒的浏览器各做一次 (最多 10 个订阅). 卡片还列出所有订阅, 每行有 **发送测试** 和 **删除** 按钮. 某个浏览器开不了推送时 (例如设备不信任服务端的证书), 卡片会说明原因和下一步.
3. 支持 Android 和桌面的 Chrome, Edge, Firefox; 不支持 iPhone 和 iPad.

- **推送什么**: 每条推送都是通知铃铛 (第 9 节) 里一条通知的转发, 铃铛里没有的问题不会推送, 也没有 "已恢复" 消息: 原因消除后, 该条会从铃铛里消失. 点开推送会打开 Web UI 并展开铃铛. 以下情况会推送: 设备上有待处理改动满 2 分钟; 设备上报错误满 5 分钟 (先让客户端自己重试); 设备的客户端协议过旧, 同步已停止; 设备已 3 天未连接; 数据盘剩余空间低于 256 MB; 每日垃圾回收清理失败; 服务端证书无法续期或即将过期.
- **隐私**: 一条推送只有一行简短文字, 写明设备名, 文件夹名 (用订阅该推送的浏览器的语言) 和问题类型, 从不包含文件名, 路径, 错误原文, 文件内容或密码. 消息在服务端与浏览器之间端到端加密, 浏览器厂商的推送服务读不到内容.
- **防刷屏**: 同一个问题在持续期间对每个浏览器只推送一次; 消除后又出现时, 距上一次推送不满 1 小时则等到满 1 小时再推; 所有推送合计每小时最多 20 条. 连不上推送服务时, 服务端 1 分钟后重试, 之后每小时重试, 文件同步照常进行.
- **失效的订阅**: 推送服务回复某个订阅已不存在 (例如你重置了浏览器) 时, 卡片会把它标为 **已失效**, 铃铛里出现一条提醒, 直到你删除该订阅.

## 10. 正在使用的文件与 SQLite 数据库

日常办公时, 同步目录里的文件经常正被其他软件打开或持续写入. 为了避免把写到一半的文件传上去, 或与正在运行的软件争抢文件锁, kaze-sync 做了以下保护:

- **Windows 上被锁定的文件.** Word, Outlook 等程序在打开文档时会锁定文件, 导致其他程序无法读取, 改名或删除. 在 Windows 上, 每当客户端因为文件被其他程序锁定而操作失败时, 会将该文件上报为 `in_use` (在通知铃铛中显示为提醒), 并依次在 30 秒, 2 分钟, 10 分钟后自动重试, 之后在每次扫描时继续重试; 如果当时正在下载新版本准备覆盖它, 下载好的临时文件会先保留在本地磁盘上, 免得重下. 等你关闭占用该文件的程序后, 同步会自动完成.
- **刚修改完的文件.** 客户端只上传修改时间已经过去至少 5 秒, 且在读取全过程中修改时间没有再次变化的文件, 从而避免把程序刚写到一半的文件上传到服务端.
- **SQLite 数据库.** 如果一个 SQLite 数据库正在进行事务写入, 把主数据库文件与它的预写日志 (`-wal`) 或回滚日志 (`-journal`) 拆开同步会直接损坏数据库. 因此, 旁文件 `<name>-wal`, `<name>-shm` 和 `<name>-journal` 始终被内置排除, 永远不会同步; 同时只要 `<name>-wal` 或 `<name>-journal` 存在且非空, 客户端就会把主数据库文件 `<name>` 视为正在使用 (`in_use`), 既不上传它, 下载时也不覆盖它. 在 WAL 模式下, 这意味着只有当应用程序正常关闭数据库后 (或者你主动执行了 `PRAGMA wal_checkpoint(TRUNCATE)` 清空了 WAL), 数据库文件才会开始同步. 请注意不要在两台电脑上同时打开并修改同一个 SQLite 数据库, 否则两边各自的修改会成为待处理 (见第 8 节), 只能在两个版本中保留一个.
- **虚拟机磁盘镜像与 Linux 普通文件.** 虚拟机磁盘镜像只有在虚拟机关机后才能可靠同步. 另外在 Linux 系统上, 内核没有提供通用的强制锁查询机制来判断其他进程是否正以写入方式打开某个普通文件, 因此在 Linux 上只有上面提到的 "修改后静置 5 秒" 规则为你提供保护.

## 11. 恢复旧内容

任何设备上被覆盖或被删除的文件内容, 在版本保留期内都保存在服务端上 (第 13 节). 出于精简与安全考虑, Web UI 只展示文件名和元数据, 不提供浏览器直接下载; 恢复操作总是把你选中的历史版本重新作为当前最新版本写回服务端, 随后各台在线客户端像接收普通修改一样把它同步回本地. 同时, 恢复前的当前内容本身也会转入版本历史, 因此任何一次恢复操作本身也都可以撤销, 绝不会改写或抹掉已有的历史记录.

根据误操作的范围, 你可以恢复单个文件的某个历史版本, 找回已删除的文件, 或者把整个目录乃至整个文件夹恢复到过去的某一时刻:

**恢复单个文件的某个版本.** 在文件夹页找到该文件, 打开行菜单 (在行上单击右键, 点击行尾的 **⋯** 按钮, 在触屏上长按, 或用键盘按 `Shift+F10`), 选择 **版本历史…**. 弹出的表格会列出该文件每个历史版本的时间, 大小和产生该版本的设备, 第一行是当前状态. 在你想找回的那个版本行上点 **恢复**, 该行会高亮, 表格下方出现确认面板, 在面板里点 **恢复** 确认即可 (点 **取消** 放弃).

**恢复已删除的文件.** 打开文件夹页右上方的 **显示已删除** 开关, 已删除的文件就会以灰色显示在列表中并带有 **已删除** 标签. 打开该文件的行菜单, 点 **恢复最后的内容…** 即可直接恢复它被删前的最后一个版本; 如果想恢复更早的版本, 则打开 **版本历史…** 进行挑选.

**把文件, 目录或整个文件夹恢复到某一时刻.** 如果一批文件被错误覆盖, 或者不小心删掉了整个目录, 可以打开目标文件或目录的行菜单, 选择 **恢复到某一时刻…**; 如果要恢复当前正打开浏览的这个目录, 则打开标题行的菜单 (或在文件列表空白处单击右键), 选择 **恢复此目录到某一时刻…** (当位于文件夹最顶层时, 该菜单项显示为 "恢复整个文件夹到某一时刻…"). 在弹出的对话框中按三步操作:

1. **选择目标时刻.** 你可以在上下两条时间轴上用鼠标选时间, 也可以直接在时间输入框中填写, 格式如 `2026-11-03 22:48:27` (秒可以省略). 对话框刚打开时默认停在今天的 "现在":
   - **两条时间轴如何配合.** 上面一条是**日期轴**, 左端是可恢复到的最早时刻 (版本保留期的起点, 或下文说明的首次导入完成时刻, 取两者中较晚的一个), 右端是标在轴外的 "现在". 日期轴上的蓝色竖线只停在每天的 0 点 (`00:00`, 最早那一天停在最早可恢复时刻, 最晚停在今天 0 点); 拖动竖线或在轴上任意位置点一下, 竖线就会跳到最近的那一天. 日期轴上默认只标注日期数字 (如 `30`, `1`, `2`), 当保留期超过 30 天时改标 `MM-DD` (如 `12-01`), 并根据轴的宽度自动抽稀以免重叠.
     下面一条是**时刻轴**, 固定展示你在日期轴上所选那一天的完整 24 小时 (`00:00` 到 `24:00`, 选今天时也一样), 左端 `00:00` 为高刻度, 右端标 `24:00`, 中间为小时刻度 (屏幕越宽刻度越细, 窄屏上自动变疏). 在时刻轴上拖动蓝色竖线或点击任意位置即可选定当天的具体分钟 (如果需要精确到秒, 请直接在输入框里修改). 当天无法选择的时段 (即今天 "现在" 之后的未来时段, 以及范围第一天里早于最早可恢复时刻的时段) 都会画成斜线底纹, 竖线无法移入. 上下两条轴彼此独立, 互不联动: 拖动下面的时刻轴绝不会改变上面日期轴所停的那一天, 拖动上面的日期轴也只按整天移动.
   - **黄色改动标记与淡蓝色保留区.** 两条时间轴基线下方的黄色短线标出了所选文件或目录实际发生改动的时刻: 日期轴上每次改动对应一条黄色短线, 画在该改动发生的时刻位置 (同一天内的多次改动会画出多条短线, 落在同一个像素列上的多次改动则合成为一条更长的短线); 时刻轴上则在发生过改动的每一分钟处画出短线. 蓝色竖线左侧的淡蓝色区域代表恢复后仍会保留的历史范围, 竖线右侧则是将被回滚撤销的范围. 虽然拖动蓝色竖线时不会强制吸附到黄色短线上, 但文件状态只在黄色短线处真正发生变化: 把竖线停在某条黄色短线上或它的右侧, 恢复结果就包含那次改动.
   - **用按钮或键盘逐次移动.** 想直接按改动点一步步前后跳动, 可以点 `‹` 和 `›` 按钮 (可以跨天连续跳动), 或者让下面的时刻轴获得焦点后按左右方向键 (仅在当天范围内跳动; 按 `PageUp`/`PageDown` 每次移动一小时, 按 `Home` 和 `End` 跳到当天的两端). 当焦点在上面的日期轴时, 左右方向键每次移动一天 (`PageUp`/`PageDown` 每次移动七天, `Home` 跳到最早时刻, `End` 跳到现在). 直接在输入框里输入时间则会让上下两条竖线同时跳到该时刻. 在你按住鼠标拖动竖线的过程中, 只有竖线位置和时间文字 (包括输入框上方提示距今多久的文字) 实时跟随变化; 等松开鼠标后 (用键盘或按钮移动时则是略停顿一下后), 且该时刻对应的文件状态确实发生了变化, 下方的文件预览才会刷新. 当竖线停在 "现在" 或最后一次改动之后时, 没有任何差异可比, 预览区会提示你先选哪一天, 再选当天的时刻.
   - **时区, 保留期与最早记录边界.** 预览区下方会注明当前使用的时区 (可在设置页更改), 版本保留期以及最早可恢复到的时间. 如果你输入的时间早于版本保留期, 对话框会提示那时的历史内容可能已被清理. 如果所选时间早于整个文件夹的第一条历史记录, 服务端会按该文件夹**首次导入完成**时的状态来计算 (首次导入即第一台设备接入后的第一次全量上传, 服务端把第一批文件到达后第一次出现连续 2 分钟无新上传的安静时刻记为首次导入完成), 并在对话框中写明: "所选时间早于最早记录, 按首次导入完成时的状态计算: 首次导入完成于 <时间>". 首次导入完成之后才新建的文件在那时并不存在, 因此不会被触动 (恢复操作从不删除文件). 如果你只针对某个在首次导入之后才新建的目录或文件执行恢复, 且所选时间早于它自己的创建时间, 则改用该目录或文件自己的第一条记录作为基准, 提示 "所选时间早于最早记录, 按最早记录计算: 最早记录为 <时间>". 无论哪种情况, 预览展示的内容都与最终恢复结果完全一致. 如果目标完全没有任何历史记录, 对话框会显示 "这里没有任何历史记录".
2. **核对预览列表.** 对话框会预览在所选时刻存在, 且与现在状态不同的文件: 预览区顶部有一行 glob 过滤框 (语法同第 7 节, 仅用于筛选界面显示, 真正执行恢复时仍会恢复全部命中的文件), 下方最多列出 50 条路径, 每条按它现在的状态标为 "已删除" 或 "已改变" (用两种不同的淡色底纹区分). 列表下方汇总写明 "该时刻存在而现在不同的文件: N 个, 过滤后 M 个, 目前仅显示 K 个" (N 为真实总数, 后两段仅在启用了过滤或超出 50 条省略显示时出现). 预览区保持固定高度, 因此来回拖动时间轴时对话框不会忽高忽低跳动; 如果所选时刻与现在没有任何差别, 恢复按钮保持禁用.
3. **点击恢复.** 确认无误后点 **恢复**, 完成后页面提示条会告知成功恢复了几个文件, 有几个失败 (例如遇到名称冲突, 或文件恰好在同一刻被并发修改).

对每一个受影响的路径, 按时刻恢复都会把该时刻有效的版本重新写回为当前版本. 请记住它**只恢复内容而不删除后来新增的文件**: 该时刻之后新建的文件一律保留不动, 而恢复前的文件内容也会存入版本历史. 这样一套机制同时覆盖了 "误删了整个目录" 和 "一批现有文件被错误覆盖" 两种常见场景.

**恢复与写入控制.** 恢复操作总是会被接受 (5.1 节). 如果恢复范围包含独占目录, 或当前写入者在不到一个时间窗前刚写入过的单端目录, 对话框会显示一条提示: 恢复照常进行并同步到所有设备, 此后修改该范围的其他设备会被冻结 (单端目录为时间窗内, 独占目录为所有者以外的任何设备).

## 12. 导出为普通文件

每台客户端电脑上都有同步文件夹的普通目录树, 但服务端自身保存的是去重后的数据块和 SQLite 数据库, 并不是直接展开的目录树. 如果你需要直接从服务端提取普通文件 (例如做灾难恢复或迁出到其他工具), 请在服务端以 root 身份执行 `kaze-syncd export` (因为 `var/` 下的数据归服务用户 `kaze-sync` 所有):

```bash
kaze-syncd export DIR [--data DIR] [--folder NAME|ID] [--at "2026-11-02 12:00[:00]"]     # server
```

- **导出目录 (`DIR`) 与 `--folder`**: 不带 `--folder` 时, 每个文件夹会分别导出到 `DIR/<文件夹名>` 子目录下; 带 `--folder NAME|ID` 时, 则把指定的那个文件夹直接导出到 `DIR` 下.
- **按历史时刻导出 (`--at`)**: 不带 `--at` 时导出最新当前状态; 带 `--at` 时导出指定时刻的历史状态, 注意这里的参数时间按 **UTC** 解释.
- **`--data`**: 默认取当前执行的 `kaze-syncd` 二进制所在的目录.

`export` 命令直接读取磁盘上的数据库文件和数据块, 因此无论服务端服务正在运行还是已经停止都能执行, 也可以直接对着解压出来的备份目录执行. 每个文件写出后都会重新计算哈希进行完整性校验, 同时还原文件内容, 可执行权限位和修改时间; 如果某个文件缺失数据块或校验损坏, 命令会报错并跳过该文件, 继续导出其余所有正常文件, 最后以非零状态码退出. 执行前请确保目标磁盘预留了足够的空闲空间, 因为导出会把所选文件夹的完整内容全部写出一遍.

## 13. 保留期与垃圾回收

如果把每次覆盖和删除产生的旧版本无限期保存下去, 服务端磁盘迟早会被塞满, 因此 kaze-sync 会在后台定期清理过期历史并回收磁盘空间:

- **版本保留期.** 每次覆盖或删除文件时, 被替换下来的旧版本会保留 `keep_days` 天 (在设置页的 **版本保留** 中配置, 默认 30 天, 范围 1 到 3650). 如果你想缩短保留天数以腾出磁盘空间, 在设置页保存新值后会立即触发一次清理, 无需重启服务.
- **垃圾回收何时运行.** 垃圾回收在服务端启动一分钟后首次检查运行, 之后每 24 小时自动运行一次; 此外每次在设置页保存版本保留天数后也会立即运行一次. 回收过程先删除超出保留期的历史版本记录, 再删除不再被任何当前文件或历史版本引用, 且创建时间已超过 1 小时的数据块, 最后清理 `var/tmp/` 目录下的残留临时文件. 其中 1 小时的宽限期是为了保护客户端刚刚上传, 但尚未完成提交的新数据块. 垃圾回收全程在后台运行, 不会阻塞正常同步.
- **磁盘空间何时真正释放.** 因为未引用的数据块是在垃圾回收时才从磁盘删除的, 所以删除文件或删除文件夹后, 磁盘占用要等到下一次垃圾回收完成时才会下降. 每次回收结束后都会在日志里记录一行摘要 (`msg=gc`), 包含本次删除的版本数, 块数, 扫描趟数和总耗时; 在 OpenWrt 上可以用 `logread | grep 'msg=gc '` 查看.
- **内存占用上限.** 垃圾回收占用的内存有固定预算 (机器内存的 3/8, 最少 64 MB); 数据量特别庞大时只是拆成更多趟扫描. 多少文件需要多少内存, 见下面的 "内存估算".
- **频繁变化的文件.** 每隔几秒就改写一次的文件每次写入都会产生一个新版本. 如果这些历史版本没有保留价值, 请用排除规则把它们忽略掉 (第 7 节).

### 内存估算

垃圾回收在内存里为每个块引用保存一个 32 字节的哈希. 数组按实际的引用数分配, 数据少时占用很小, 并且不会超过预算: 预算是机器内存 (如果服务运行在容器或服务单元的内存限额之内, 则取限额, 二者取小) 的 3/8, 最少 64 MB. 因此 512 MB 内存的机器预算为 192 MB, 一趟约可处理 600 万个引用. 引用数超过预算时, 垃圾回收自动拆成所需的趟数 (最多 256 趟), 只是耗时更长, 不会失败. 这里说的是垃圾回收运行期间额外占用的内存; 服务端的常驻内存 (见 2.5 节 "资源占用") 另外计算.

引用数是每个当前文件和每个保留中的历史版本的块数之和 (块大小 256 KiB, 小于一块的文件算 1 块, 多个文件或版本共用的块每次都计入). 所以:

```text
引用数       ~  文件数 x (1 + v) x 每个文件的平均块数
垃圾回收内存  =  min(引用数 x 32 字节, 预算)
```

其中 `v` 是保留期内每个文件平均拥有的历史版本数. 文件每被覆盖或删除一次就多一个版本, 版本超过 `keep_days` 天后被清掉, 所以 `v` 同时随保留期和文件的改动频率增大: 保留期用默认的 30 天时, 每周改一次的文件约有 4 个历史版本, 从不改动的文件没有, 每天改写的文件约有 30 个. 对经常改动的文件, `keep_days` 翻倍, `v` 大致也翻倍 (从不改动的文件不受影响). 下表假设 `v = 2`, 每个文件 1 块, 这是对一般文档和源码目录的假设, 不是实测值; 换成自己的数据时, 乘以 `(1 + v) / 3` 和平均块数即可. 每次垃圾回收的 `msg=gc` 日志行都带有 `block_refs=<n>`, 跑过一次后用它除以文件数, 就得到自己数据的 `(1 + v) x 块数` 的实际值.

| 文件数 (v = 2, 每个 1 块) | 引用数 | 垃圾回收额外内存 | 512 MB 机器 (预算 192 MB) |
|---|---|---|---|
| 1 万 | 3 万 | 约 1 MB | 一趟 |
| 10 万 | 30 万 | 约 10 MB | 一趟 |
| 100 万 | 300 万 | 约 96 MB | 一趟 |
| 500 万 | 1500 万 | 需要约 480 MB, 受预算限制 | 3 趟, 只多花扫描时间 |

大文件按块计: 1 GB 的文件每个版本有 4096 块, 30 天里每天改一次, 约增加 12.7 万个引用 (约 4 MB). 综合常驻内存和垃圾回收内存, 512 MB 的机器在默认保留期下管理 100 万个文件是宽裕的; 调大 `keep_days`, 或同步很多经常改动的大文件时, 需要留意的是 `msg=gc` 日志行里的趟数.

## 14. 服务端的备份与还原

虽然每台客户端电脑上都保有所映射文件夹的普通文件副本, 但服务端本身并不是备份: 当前文件元数据与全部历史版本都存在服务端的同一块磁盘上. 为了防止服务端磁盘损坏导致历史版本和设备配置丢失, 请定期把服务端数据备份到另一块磁盘或另一台机器上.

**需要备份哪些文件.** 一份完整的服务端备份包含以下目录和文件:
- `<data>/var/meta.db` 与 `<data>/var/folders/` (全局数据库与各文件夹数据库)
- `<data>/var/blobs/` (全部文件数据块)
- `<data>/var/tls/` 以及本地 CA 模式下的 `<data>/ca/` (服务端证书与本地 CA 密钥; 如果漏掉了它们, 还原后的服务端会重新生成新证书或新 CA, 导致证书指纹改变, 所有客户端都必须重新注册, 浏览器也必须重新信任新 CA)

因为 `meta.db` 与 `folders/` 下的各个文件夹数据库必须严格取自同一时刻, 复制它们之前**必须先停止服务几秒钟** (并避开每日垃圾回收正在删除数据块的时刻). 而 `blobs/` 下的数据块一旦写入就永不改变, 因此可以在服务重新启动后在线复制, 也很适合用 `rsync` 做增量备份.

完整备份命令如下 (以 systemd 为例, OpenWrt 或 OpenRC 请替换为各自的停止和启动命令):

```bash
systemctl stop kaze-sync                                                          # server
cd /var/lib/kaze-sync/var && tar cf /backup/meta.tar meta.db folders tls
systemctl start kaze-sync                                                         # 停机只有几秒钟
tar cf /backup/blobs.tar blobs
tar cf /backup/ca.tar -C /var/lib/kaze-sync ca                                     # 仅本地 CA 模式
```

**从备份还原.** 无论是迁移到新服务器还是在原机回滚, 请使用相同版本或更新版本的 `kaze-syncd` 二进制文件, 并将所有备份归档完整解压 (切勿只还原其中一部分文件).

在原机回滚时, **请先停止服务** (新服务器上还没有服务, 无需停止), 并删除数据库旁残留的 `-wal` 和 `-shm` 文件; 在服务正打开着数据库时解压覆盖会损坏它们. 命令以 `systemd` 为例, 与上文相同:

```bash
systemctl stop kaze-sync                                                           # server; 新服务器上跳过
mkdir -p /var/lib/kaze-sync/var
rm -f /var/lib/kaze-sync/var/meta.db-wal /var/lib/kaze-sync/var/meta.db-shm /var/lib/kaze-sync/var/folders/*.db-wal /var/lib/kaze-sync/var/folders/*.db-shm
tar xf /backup/meta.tar  -C /var/lib/kaze-sync/var
tar xf /backup/blobs.tar -C /var/lib/kaze-sync/var
tar xf /backup/ca.tar    -C /var/lib/kaze-sync                                     # 仅本地 CA 模式
./kaze-syncd export /tmp/check --data /var/lib/kaze-sync                           # 可选: 先确认数据可读
./kaze-syncd install --data /var/lib/kaze-sync --new-epoch                         # 修正属主, 更换历史标识, 启动服务
```

任何备份还原之后执行 `install` 时都**必须**加上 `--new-epoch` (日常升级则切勿使用 `--new-epoch`). 因为还原备份会让服务端的历史状态退回到过去, `--new-epoch` 会更换服务端的历史标识, 通知每一个连上来的客户端放弃各自缓存的已知服务端状态, 重新与服务端从头对账一次:
- 客户端电脑不需要做任何手动操作.
- 只要证书 (`tls/` 及 `ca/`) 与 `meta.db` 一起还原了, 管理员密码, 已注册设备和映射关系都会原样恢复, 客户端会自动重连.
- 对账时, 客户端上与备份内容不同的文件会成为待处理改动, 等你在第 8 节的对话框里决定 (绝不丢数据); 备份时间点之后在客户端上新建的文件会重新上传到服务端; 备份时间点之后在客户端上删除的文件则会从服务端重新下载回来. 如果漏了 `--new-epoch`, 客户端只能察觉一部分回退, 可能会静默地与服务端保持不一致.

带 OpenWrt 具体命令的逐步备份与还原说明见 [`docs/operations.md`](../operations.md) 的 "备份与还原" 一节.

## 15. 升级

升级 kaze-sync 时, 请务必遵循**先升级服务端, 再升级客户端**的顺序.

**为什么顺序重要.** 某些版本升级会改动同步协议 (当前协议版本为 6; 版本 6 新增了写入控制, 并将服务端要求的最低客户端协议版本也提升到了 6, 因此服务端升到该版本后所有客户端都必须跟着升级; 版本 5 新增的是符号链接支持). 如果反过来先升级了客户端, 新客户端向旧服务端发起成批下载时会失败. 而先升级服务端时, 比服务端最低要求更旧的客户端会收到 HTTP 426 并安全暂停同步: 客户端日志大约每分钟记录一条 `client too old, sync is stopped until kaze-syncc is upgraded`, 同时 Web UI 设备表中该设备的版本旁显示红色的 "过旧" (过旧到不上报发布版本的客户端, 版本显示为 `-`). 此时客户端本地数据毫发无损, 按下面步骤升级客户端二进制后即可自动恢复同步. (只有会让旧客户端无法正常工作的协议改动才会提高最低版本要求, 因此大多数升级并不强制同时升级客户端.)

按以下四步完成升级:

1. **下载并校验新版本发布包**: 从 [GitHub Releases](https://github.com/pellorao/kaze-sync/releases) 获取新版本的 `kaze-sync-<version>-linux-amd64.tar.gz`, `kaze-sync-<version>-windows-amd64.zip` 和 `SHA256SUMS`, 按 [2.1 节](#21-下载并校验服务端发布包)和[第 3 节](#3-安装并注册客户端)的步骤校验并解压 (若自行从源码编译, 见[附录 A](#附录-a-从源码编译)).
2. **升级服务端**: 把新的 `kaze-syncd` 复制到服务器上, 以 root 执行 `./kaze-syncd install` (OpenWrt 和普通 Linux 相同). 它会从已安装的服务定义中读取数据目录, 并保留当前的监听端口, TLS 设置, 管理员密码和 OpenWrt WAN 规则. 你也可以显式传入 `--data <同一个目录>`; 这样做时, 若要保留 OpenWrt 的 WAN 访问, 还需同时传入 `--wan`. `install` 会拒绝用更旧的服务端二进制替换更新的版本. 它会迁移数据库, 把新二进制复制进 `<data>/`, 并重启服务. 在 systemd 系统上它还会重新加载单元定义并重写 `/etc/systemd/system/kaze-sync.service`, 所以自定义的单元设置请放在 systemd drop-in 中. OpenWrt 的 `sysupgrade` 会保留数据盘和服务.
3. **升级 Linux 客户端**: 停止用户级 agent, 覆盖原路径下的二进制文件, 再重新启动:

```bash
systemctl --user stop kaze-sync                    # client
cp kaze-syncc ~/.local/bin/kaze-syncc
systemctl --user start kaze-sync
```

4. **升级 Windows 客户端**: 如果 Windows 二进制是你自己从源码编译的 (或想在替换前再核对一次), 请先检查 `kaze-syncc-agent.exe` 确实带上了 `-ldflags -H=windowsgui`; 执行下面这行命令应输出 `2` (图形子系统), 如果输出 `3` (控制台子系统) 说明每次登录 Windows 都会弹出一个黑框窗口, 不能直接部署:

```
python3 -c "import struct,sys; d=open(sys.argv[1],'rb').read(4096); print(struct.unpack_from('<H', d, struct.unpack_from('<I', d, 60)[0]+92)[0])" kaze-syncc-agent.exe
```

   因为运行中的 `kaze-syncc-agent.exe` 会被 Windows 锁定而无法覆盖, 请先在 PowerShell 中停止进程, 复制两个 `.exe` 文件覆盖原文件, 再启动 agent:

```powershell
Stop-Process -Name kaze-syncc-agent
Copy-Item kaze-syncc.exe, kaze-syncc-agent.exe <安装目录>
Start-Process "<安装目录>\kaze-syncc-agent.exe" -ArgumentList run
```

**发布客户端安装包.** 如果你手上有某个版本的 Linux 和 Windows 客户端安装文件, 请以 root 身份在服务端执行 `kaze-syncd client-pkg <linux-installer.sh> <windows-setup.exe>`. 两个平台可以只发布其中一个. 该命令会检查每个安装包, 无需重启服务即可立即提供下载. 需要比服务端支持的同步协议更新的安装包会被拒绝. 要发布这些安装包, 请先升级服务端.

**数据库自动迁移与回滚方法.**
- **服务端数据库.** 服务端每次启动时 (包括执行 `install` 时) 都会自动把数据库升级到新版本的结构, 先迁移全局库 `meta.db`, 再逐个迁移文件夹库; 如果结构没有变化则什么也不做. 在修改任何一个数据库文件之前, 服务端会先把原文件完整备份到 `<data>/var/backups/` 下, 命名为 `meta-v<旧版本>-<UTC 时间>.db` 或 `folder-<id>-v<旧版本>-<UTC 时间>.db` (每个数据库最多保留最近 3 份备份; 删除文件夹时会一并清理它的备份). 因为备份文件与原数据库一样大, 升级前请确保磁盘上有同样大小的空闲空间. 如果备份或迁移过程中某一步失败, 服务端会中止启动并在报错中指明是哪个数据库以及具体原因; 该数据库保持原样未动, 排除故障 (例如腾出磁盘空间) 后重新启动服务即可.
  如果数据库迁移完成之后你想**回退到旧版本服务端**, 旧版 `kaze-syncd` 遇到被新版迁移过的数据库会主动拒绝启动并打印原因, 而不会损坏数据库. 正确的回滚步骤是: 停止服务端, 换回旧版 `kaze-syncd` 二进制, 把 `var/backups/` 下升级时自动生成的最新一份备份复制回 `var/meta.db` 和各个 `var/folders/<id>.db` (同时删掉各库旁边的 `-wal` 和 `-shm` 文件), 然后按第 14 节的还原步骤执行 `install --data ... --new-epoch`.
- **客户端数据库.** 客户端状态目录下的各文件夹状态库 (`folder-*.db`, Linux 在 `~/.local/state/kaze-sync`, Windows 在 `%LOCALAPPDATA%\kaze-sync`) 也会随某些版本升级而改变表结构. 如果你打算把客户端二进制降级回旧版本, 请在替换二进制前先停止 agent 并备份这些 `folder-*.db` 文件, 回滚时与旧二进制一起还原. 如果旧版客户端发现某个 `folder-*.db` 是由更新版本创建的, 它会停止同步该文件夹, 并在该文件夹的错误通知中说明原因, 而不会在每次扫描时反复报错失败.

## 16. 卸载

淘汰某台电脑或停用整套服务时, 按以下步骤即可干净地移除后台服务与运行状态.

### 16.1 客户端

卸载客户端时先在 Web UI 中解除设备注册, 让服务端不再等待它, 然后再清理本机文件. 无论怎么卸载, 已同步在电脑上的本地文件都会完整保留.

1. **在 Web UI 中**: 打开该设备的页面, 点 **吊销设备…** (如果只是想停用某个目录而保留设备, 只删除映射也可以).
2. **Linux 客户端**: 执行 `systemctl --user disable --now kaze-sync`, 删除 `~/.config/systemd/user/kaze-sync.service` (随后执行 `systemctl --user daemon-reload`), 删除状态目录 `~/.local/state/kaze-sync` (内含设备令牌, 日志和本地同步状态), 最后删除二进制文件 `~/.local/bin/kaze-syncc`.
3. **Windows 客户端**: 结束 `kaze-syncc-agent.exe` 进程 (`Stop-Process -Name kaze-syncc-agent`), 删除注册表 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 下的 `kaze-sync` 值, 删除 `%LOCALAPPDATA%\kaze-sync` 目录, 最后删除 `kaze-syncc.exe` 和 `kaze-syncc-agent.exe`.
4. **可选清理**: 之后可以手动删掉各同步目录根下的隐藏标记文件 `.syncroot`.

### 16.2 服务端

服务端没有一键卸载命令. 下面的步骤会彻底删除服务端程序以及**服务端保存的全部同步文件与历史版本**; 拿不准时请先做好备份或用 `export` 导出普通文件. 卸载服务端之前, 请先把所有客户端吊销并卸载 (16.1 节), 否则客户端还会在后台不断尝试重连.

**systemd** 环境:

```bash
systemctl disable --now kaze-sync                  # server
rm /etc/systemd/system/kaze-sync.service
systemctl daemon-reload
userdel kaze-sync
rm -r /var/lib/kaze-sync                           # 你传给 --data 的数据目录, 内含全部数据
```

**OpenRC (Alpine)** 环境:

```bash
rc-service kaze-sync stop                          # server
rc-update del kaze-sync default
rm /etc/init.d/kaze-sync
deluser kaze-sync                                  # 同时删除同名组
rm -r /var/lib/kaze-sync                           # 你传给 --data 的数据目录
```

**OpenWrt** 环境:

```bash
/etc/init.d/kaze-sync stop                         # server
/etc/init.d/kaze-sync disable                      # 删除 /etc/rc.d/S99kaze-sync
rm /etc/init.d/kaze-sync
sed -i '/^\/etc\/init.d\/kaze-sync$/d;/^\/etc\/rc.d\/S99kaze-sync$/d' /etc/sysupgrade.conf
uci -q delete firewall.kaze_sync; uci commit firewall; /etc/init.d/firewall reload   # --wan 添加的规则; 没有也无妨
rm -r /mnt/data/kaze-sync                          # 你传给 --data 的数据目录, 内含全部数据
```

在 OpenWrt 上, 删除 `/mnt/data/kaze-sync` 只是删掉数据盘上的这一个文件夹并释放空间; 磁盘本身, 分区和挂载配置都是你自己的, 不会被改动 (如果想把整块盘挪作他用, 请用惯常工具卸载并重新分区). OpenWrt 没有 `deluser` 命令: 系统用户 `kaze-sync` 没有登录 shell, 留着也无妨; 想彻底删掉它可以执行 `sed -i '/^kaze-sync:/d' /etc/passwd /etc/group /etc/shadow`.

最后, 如果你之前手动在防火墙或云安全组里放行过服务端端口, 请把对应规则关掉.

## 17. 排查问题

遇到同步异常时, 先看 Web UI 顶栏的通知铃铛 (第 9 节), 再按下面的位置查看服务端或客户端日志.

**日志在哪里.**

| 组件 | 位置 |
|---|---|
| 服务端, systemd | `journalctl -u kaze-sync` |
| 服务端, OpenRC | syslog, 标签 `kaze-sync` (Alpine 在 `/var/log/messages`) |
| 服务端, OpenWrt | `logread` |
| Linux 客户端 | `~/.local/state/kaze-sync/kaze-syncc.log` (设置了 `$XDG_STATE_HOME` 时在 `$XDG_STATE_HOME/kaze-sync/`) |
| Windows 客户端 | `%LOCALAPPDATA%\kaze-sync\kaze-syncc.log` |

默认情况下, 客户端日志只记录启动信息, 警告和错误; 日志文件一旦超过 10 MB 就会立即轮转改名为 `kaze-syncc.log.old` (agent 运行过程中也会实时轮转, 最多保留一份旧日志).

**客户端的调试时间线.** 如果你想查明某次文件改动为什么同步得慢, 可以在客户端的状态目录 (即上表中的目录) 下新建一个名为 `debug` 的空文件, 然后重启 agent. 开启后日志里会多出 `level=DEBUG` 级别的行, 详细记录每一次本地文件事件, 扫描, 拉取以及每个发往服务端的请求与耗时. 排查完毕后请删掉 `debug` 文件并重启 agent.

**常见提示与问题.**

| 现象 | 原因与处理 |
|---|---|
| `enroll` 提示 `invalid or expired code` | 注册码只能使用一次, 且有效期只有 15 分钟. 请在 Web UI 中重新生成一个, 并确认复制了完整命令 |
| `enroll` 提示 `too many failures` (HTTP 429), 或登录页返回 429 | 同一 IP 在一小时内认证失败达 10 次会被锁定一小时. 可以等待一小时自动解封, 或在服务端执行 `admin-password` 重启服务并立即清除所有锁定 |
| `enroll` 提示 `cannot register device` | 服务端上已有同名设备. 请先吊销旧设备, 或换一个名称添加新设备 |
| `enroll` 报证书错误 | 指纹不匹配: 请从注册对话框重新复制最新命令 (`install` 的输出和服务端日志的 `listening` 行里也有指纹); 或者服务端已改用你自己的公认 CA 证书, 此时必须去掉命令里的 `--fingerprint` |
| 浏览器警告证书, 或不自动填充已保存的密码 | 使用默认自签名证书时的正常现象; 核对指纹一致后接受一次例外即可. 如果想去掉警告并恢复密码自动填充, 请改用本地 CA 模式 (2.4 节); 若启用了 `--ca` 仍弹出警告, 说明当前电脑还没导入并信任该 CA, 或浏览器地址栏里的名称不在 `--san` 列表中 |
| 忘记管理员密码, 端口或指纹 | 重置密码见 2.5 节 (`admin-password`), 查看端口或指纹见 2.4 节 (重跑 `install` 或查服务端日志) |
| 服务启动后马上退出, 日志里报证书或私钥 `permission denied` | 服务用户 `kaze-sync` 无权读取你指定的 `--cert`/`--key` 文件或无权进入其上层目录 (运行 `install` 时会就此给出警告), 请按 2.4 节修改权限 |
| 服务器重启后服务端没有启动 | 开机时外接数据盘尚未挂载. 服务端此时会主动退出, 避免在未挂载目录里新建空库; 挂载数据盘后再启动服务即可 |
| `sync is stopped, the server does not accept this device` | 该设备已在 Web UI 中被吊销. 请按 3.3 节把它作为新设备重新注册 |
| `client too old` | 服务端升级后要求更高版本的客户端协议; 请按第 15 节升级该客户端的二进制文件 |
| 某个文件夹显示有错误, 铃铛里有 `folder` 条目 | 本地目录或 `.syncroot` 缺失 (例如移动硬盘未挂载), 或者本地目录非空但没有在设备页勾选 **允许接管非空目录** (见第 5 节) |
| 文件修改后过几秒才同步过去, 不是瞬间到达 | 属于正常设计: 客户端会先收集本地文件事件 2 秒 (文件持续变化时最多攒够 10 秒), 且要求文件修改时间已满 5 秒才上传, 对端再通过长轮询获知更新. 通常端到端延迟在 5 到 10 秒之间 |
| 首次同步耗时很久 | 首次接管或同步时, 客户端需要把每个文件完整读一遍并计算哈希. 参考耗时: 一次含 19000 个文件, 共 1.6 GiB 的测试耗时约 4.5 分钟 |
| 某台设备上的一个文件夹或目录停止同步, 铃铛里有 "个改动待处理" | 该设备与另一台设备同时写入, 基于过时的内容写入, 或向不属于它的独占目录写入, 因此在那里被冻结, 等你决定. 请打开处理对话框 (第 8 节). 如果彼此毫无关系的文件也经常遇到这种情况, 请把文件夹的根目录设为不限 (5.1 节) |
| 铃铛里有待处理改动, 但我什么都没改 | 那台设备上有程序改写了文件, 这同样算作一次写入. 在独占目录里, 只要在所有者以外的设备上运行 `git status` 就足以触发冻结, 因为它会改写 `.git/index`. 在单端目录里, 只有当那台设备的内容不是最新, 或另一台设备在最近一个时间窗内写入过时才会触发冻结; 否则改写会被接受, 并让那台设备在一个时间窗内成为当前写入者. 请只在写入者设备上运行 `git`, 或将模式改为不限 |
| 一个决定一直显示 "等待 ... 执行" | 设备会在下一次联系服务端时执行决定, 而它目前离线或后台 agent 已停止. 10 分钟后这个标签会隐去, 各行看起来又像尚未决定, 但决定仍在服务端排队, 设备重新连上后就会立即执行 (再点一次按钮只是替换排队中的决定). 只有当服务端在设备重连之前重启过, 排队中的决定才会丢失, 此时请再点一次按钮 |
| 某个文件一直没有同步过去 | 查看文件夹页是否有灰色的 **未同步** 行并点开顶栏铃铛: 常见原因包括本设备无法建立符号链接 (例如未开启开发人员模式的 Windows), Windows 非法文件名, 大小写冲突, 文件正被程序占用 (`in_use`), 或命中了排除规则 |
| 服务端磁盘占用增长很快 | 频繁变化的文件每次写入都会保留一个历史版本. 请用排除规则忽略这些文件 (第 7 节), 或缩短版本保留天数 |

## 18. kaze-sync 不做什么

为了在 512 MB 内存的路由器上保持低资源占用与简单可靠, kaze-sync 有意不做以下超出个人多设备文件夹同步范畴的功能:
- 不做文件分享, 多用户体系和多人协作编辑
- Web UI 中不提供文件在线预览和文件下载
- 不同步空目录, Windows 联接点, 除可执行位以外的文件权限, 文件所有者和扩展属性
- 不做端到端加密, 传输压缩和带宽限速
- 不设绑定到单台设备的排除规则 (如果某一部分文件只想在一台设备上同步, 请把它们拆成单独的文件夹)
- 没有双因素登录验证
- 客户端在电脑桌面上不设通知弹窗或状态栏图标
- 没有 macOS 和移动端客户端, 服务端不支持 x86-64 以外的架构
- 没有自动更新
- 单个文件超过 128 GiB 时服务端会拒收 (因为服务端需要把单个文件的完整块列表放在内存中处理)

以上各项取舍的设计原因见 [`docs/design.md`](../design.md).

## 附录 A: 从源码编译

如果你的客户端运行在 [GitHub Releases](https://github.com/pellorao/kaze-sync/releases) 未提供预编译包的 CPU 架构上, 或者你希望自己从源码编译, 可以在任意装有 Go 的机器上编译二进制文件 (Go 版本见 `go.mod`, 当前为 1.27.3). 编译产物是静态链接的二进制文件, 没有任何外部依赖, 因此可以在开发机上一次编好再复制到服务器和各台电脑上:

```bash
CGO_ENABLED=0 GOOS=linux   GOARCH=amd64 go build -o kaze-syncd ./cmd/kaze-syncd
CGO_ENABLED=0 GOOS=linux   GOARCH=amd64 go build -o kaze-syncc ./cmd/kaze-syncc
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -o kaze-syncc.exe ./cmd/kaze-syncc
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -ldflags -H=windowsgui -o kaze-syncc-agent.exe ./cmd/kaze-syncc
```

第四行命令用同一份客户端源码编译出无控制台窗口的版本, 供 Windows 登录自启动时在后台静默运行. 请务必把 `kaze-syncc-agent.exe` 与 `kaze-syncc.exe` 放在同一个目录下. 为非 x86-64 架构的客户端交叉编译 `kaze-syncc` 时请按目标 CPU 调整 `GOARCH`; 注意服务端 (`kaze-syncd`) 只支持 x86-64 架构 (因此非 x86-64 的 OpenWrt 路由器及其他非 x86-64 服务端主机不受支持).

两个二进制文件都在构建时嵌入了发布版本号: 执行 `kaze-syncd --version` 和 `kaze-syncc --version` 会分别输出 `kaze-syncd 0.3.5` 和 `kaze-syncc 0.3.5` (以 `0.3.5` 版为例). 登录 Web UI 后, 左上角 `Kaze Sync` 旁也会显示当前服务端的版本号 (登录页不显示).

编译完成后, 把 `kaze-syncd` 复制到服务器并按 [2.2 节](#22-openwrt) (OpenWrt) 或 [2.3 节](#23-普通-linux-systemd-或-openrc) (普通 Linux) 执行 `install`, 把客户端二进制复制到每台电脑的固定目录并按[第 3 节](#3-安装并注册客户端)执行注册.
