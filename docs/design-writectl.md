## 0. 结论摘要

- 单端和独占是同一个机制: 范围有一个 "所有者", 只有所有者可以写. 区别只在所有者怎么来, 何时失效: 独占由用户指定, 不失效; 单端由第一个写入到达服务端的终端自动获得, 它最后一次写入后 N 分钟 (默认 1, 服务端可配) 没有新写入即失效, 之后别的终端基于最新内容的写入就自动成为所有者 (用户 #78). 不限没有所有者, 不判断. 所有者有效期内其他终端的写入就是 "同时写入" (单端) 或 "非法写入" (独占), 处理相同 (2.3).
- 同时写入由服务端在提交时按两个条件判断, 任一成立即是 (2.3): (1) 范围版本: 提交带上终端在该范围开始改动时已应用到的游标 `since`, 范围内有 `seq > since` 的他端写入, 即基于过时内容的写入 (D8 选 A, 含离线很久后上线); (2) 时间窗: 范围的当前所有者 (最后一次被接受的写入者) 是别的终端, 且那次写入到达服务端不足 N 分钟 (服务端时间), 管 "所有者一次 `git` 操作分几批到达". 范围版本就是范围内最大的 `seq`, 文件夹全局的 `seq` 已有, 不另存计数器. 先后只按到达服务端的顺序, 终端不报告时刻或时长 (去掉了第二版的 `age`). 不限目录中的文件各自是单文件范围, 版本条件就是现有的逐文件 base 检查.
- 不加 "开始写入" 和 "写完" 的消息, 服务端不加状态: 所有者和范围版本都从 `files` 推出, 重启不丢 (2.3, 2.4).
- 发生同时写入时只冻结后到服务端的一端在该范围的同步 (D1, D8 例中冻结后上线的笔记本); 用户在 Web UI 中把待处理改动逐个或整范围处理为 "上传", "上传并覆盖" 或 "丢弃" (默认把本机那份移到本地的 `.syncsaved`, 可选直接丢弃, D2), 只剩一份才算解决, 不再生成冲突副本 (D3). 所有操作只在 Web UI 上 (D4).
- 新的待定问题: 根目录默认单端时, 版本条件使 "离线期间改了任何文件, 而别的终端也改过该文件夹" 冻结整个文件夹 (D9).
- 小文件共用存储块另开专题 `kaze-sync/blocks` (D6), 第 6 节未改. 设计稳定并实测之前不发布 (D5, 第 10 节).
- 工作量约新增 720 行, 删除约 480 行非测试 Go 代码 (第 9 节).

## 1. 需求与对应

- 写入不被阻止, 发现非法或同时写入后该范围停止同步, 推送警告, 用户处理完才恢复 (#59): 2.5 到 2.8.

- 目录三态, 文件二态, 从父目录继承, 根默认单端 (#59): 2.2.

- 用户和账号只有一个, 没有权限高低 (#59): Web UI 中的恢复是用户本人的写入, 作为一个特殊终端 `web` 参与所有权判断 (2.3).

## 2. 模型

### 2.1 术语

- **终端**: 已注册的设备, 以及 Web UI 中的恢复 (`files.device` 为 `web`). 排除规则造成的删除 (`web:rules`) 不是写入, 不参与判断.
- **范围**: 一个显式设置及其覆盖的路径 (2.2).
- **所有者**: 单端或独占范围在某一时刻允许写入的那个终端 (2.3).
- **时间窗 N**: 服务端设置 `write_window`, 默认 1 分钟.
- **范围版本**: 范围内最大的 `seq` (含删除留下的墓碑). 文件夹的 `seq` 全局递增 (`meta.next_seq`), 每次被接受的改动都取新值, 所以范围内任一对象被修改, 范围版本就前进; 不另存计数器.
- **`since`**: 终端在某范围开始改动时已应用到的游标 (2.6), 即它的改动基于的范围版本 (偏小).
- **待处理改动** (held): 本机上没有上传, 等用户决定的改动, 一个路径一条.
- **冻结**: 某设备上某范围 (或单个文件) 的同步暂停: 本机改动不上传, 服务端的改动也不写入. 只影响这一台设备.

### 2.2 状态, 继承与范围

- 存储: 每个文件夹的设置是若干 (路径, 状态, 独占所有者) 行; 没有行的路径继承. 根路径 `""` 没有行时为单端.
- 生效状态 = 路径本身或最近祖先上的显式设置 (最长前缀, 按 `pp.Key` 比较). 子设置可以放宽或收紧父设置, 例如根为单端, `scratch/` 为不限, `scratch/repo/` 为独占.
- 范围互不重叠: 一个范围覆盖它的设置路径之下, 除去其中更深的显式设置所在的子树. 所有权只在同一个范围内判断, 独占的 `repo/` 里的写入不影响根范围的所有者.
- 文件可以显式设为独占 (只含该文件的范围), 不能设为不限. 不限目录中的每个文件各自是单端, 自成一个范围, 所以不同文件可以由不同终端同时改, 同一个文件仍按单端判断.
- 独占所有者被吊销, 或删除了它在该文件夹的映射: 该行在同一事务中改为单端 (删除会退回父设置, 可能变成不限). 删除文件夹时删除其全部行.
- 设置记的是路径字符串, 不跟踪改名. 跨范围的移动是 "旧范围删除 + 新范围新增", 各自判断.
- 被排除的路径不同步, 写入控制对它们没有意义.

### 2.3 所有者与同时写入

用户定义 (11-06): 不限不判断; 单端从某终端开始写入到写完后 N 分钟都算它独占, 其间其他终端写入即同时写入; 独占时其他终端任何时候写入都是非法写入. 按 #78, 两者统一为所有者; 按 D8 (选 A) 与用户 11-06 对 `age` 的意见, 先后只由服务端按到达顺序决定, 另加范围版本的条件:

| | 单端 | 独占 |
|---|---|---|
| 所有者从哪里来 | 范围内最后一次被接受的写入者 | 用户在 Web UI 指定 |
| 何时失效 | 那次写入到达后 N 分钟 | 不失效, 只能由用户转移或改设置 |
| 非所有者写入 | 有效期内, 或基于过时的范围版本: 同时写入; 否则接受, 写入者成为新所有者 | 任何时候: 非法写入 |

判定 (服务端, 每批每个范围一次, 在 base 检查和缺块检查之前):

- 独占: 提交者不是指定所有者即拒绝, 原因 `owner`; 所有者自己只受逐文件 base 检查.
- 单端: 提交者 D, 该批在范围 S 内的操作带 `since` (取其中最小的). 下限 `L = max(since, D 在 S 中最近一次被接受的写入的 seq)`. 以下任一成立即同时写入, 该批在 S 内的操作全部被拒, 原因 `owner`; 否则全部接受, D 成为 (或继续是) 所有者:
  - 版本: S 中有其他终端被接受的写入 `w`, `w.seq > L`. D 开始改动时还没收到 `w`, 它的改动基于过时内容 (D8). 离线很久后上线的终端带的是离线前的 `since` (2.6), 由这一条判断.
  - 时间窗: S 中最后一次被接受的写入 `w` 是其他终端的, 且 `0 <= 服务端现在 - w.created_at < N`. 即所有者还在写 (一次 `git` 操作的改动分几批到达, 中间插进别人的提交).
- 下限取 `max` 的原因: D 自己被接受的写入在当时已判过, 更早的他端写入不再算. 这也让用户处理完 (D 用 `resolve` 上传) 之后, 不会因同一批旧写入再被冻结.
- 先到者胜 (D1): 谁被冻结只由到达顺序决定, 不论谁在本地先开始. 后到者在提交时被拒并冻结. D8 的例子中, 台式机 9:00 的写入先被接受, 笔记本 14:00 上传时被拒并冻结.
- 不需要 "开始写入" 消息, 终端也不报告时刻或时长: 时间窗只用服务端收到提交的时刻 (`files.created_at`), 开始改动的位置由 `since` 表达, 它是服务端自己发出的游标, 不涉及终端时钟.
- 服务端时钟倒退 (没有电池时钟的路由器在 NTP 同步前, 或 NTP 向回校正): `服务端现在 - w.created_at` 为负时当作时间窗已过 (少报, 并记一条警告日志), 而不是一直算在时间窗内直到时钟追上 (那样可能整天误冻结); 先后只按 `seq`, 不受时钟影响. 漏掉的只有 "收到了但对方还没写完" 的情况, 基于过时内容的写入仍由版本条件抓到. 向前跳只会让一个有效期提前结束. 第二版的 "服务端时钟不倒退" (取已有最大 `created_at`) 不再需要: 它挡不住有效期变长, 而且只为换算 `age`.
- 查询: 从该文件夹最新的 `seq` 沿 `seq` 索引向前读 (`seq`, `path`, `device`, `created_at`), 跳过其他范围的行和 `web:rules` 的行. 遇到 S 中的行即可定论: 是他端写入且 `seq > since`, 或者是 S 中第一行 (最后一次写入) 且在时间窗内, 即同时写入; 是 D 自己的写入即通过 (之前的行都低于下限); 其他情况 (他端写入, `seq <= since`, 不在时间窗内) 也通过. S 中没有行时, 读到 `seq <= since` 且 `created_at < 现在 - N` 即停 (通过). 平时只读几行; 离线很久的终端最多读它离线期间整个文件夹的变更一次 (S 中有他端写入时在第一处停). 被覆盖的旧写入在 `versions` 中, 不必查: 覆盖它的是同一路径上更晚的写入, `seq` 更大, 也在 S 中. 唯一的漏洞是旧写入随后被排除规则删除, 罕见, 接受.
- 不限目录中的文件 (单文件范围): 版本条件就是现有的逐文件 base 检查 (`base_seq` 即该范围的 `since`); 时间窗只看该路径的当前行: 他端写的且在时间窗内即同时写入, 只冻结该文件.
- 恢复 (`web`) 不受判断约束, 总是成功, 但它是一次写入: 单端范围中它在 N 分钟内是所有者, 而且对开始改动时还没收到它的终端同样触发版本条件, 期间改该范围的设备被冻结. 处理动作的提交 (`resolve`, 2.7) 跳过所有权判断, 但同样算一次写入: 执行它的设备随之成为所有者, 它的下限也随之前进.
- `files.device` 存设备名, 设备改名后它改名前的行算作他端写入, 只会多报一次.

所有者模型与用户定义不完全等价的地方:

- 用户定义中所有权从 "开始写入" 起; 服务端只在写入到达时才知道, 所以重叠时按到达顺序而不是开始顺序决定所有者 (与 D1 一致).
- 时间窗从所有者最后一次写入到达时起算, 不回溯后到者的开始时刻. B 在 A 写完后 N 分钟内开始改, 但 N 分钟之后才提交: 若 B 开始时还没收到 A 的全部写入, 由版本条件抓到; 若已收到且 A 之后没再写, 不算同时写入. 后一种是 B 在 A 的完整内容上改, 无害 (用户 11-06 同意去掉 `age` 时接受).
- 版本条件比用户定义多报 (D8 选 A): 时间上不重叠, 但基于过时内容的写入也算同时写入. 范围越大, 多报越多; 根目录默认单端时的影响见 D9.
- 所有权只由被接受的写入延续. 所有者 A 有一个很大的文件上传了一个小时, 期间所有权可能失效, B (已收到 A 之前的写入) 写入成为所有者, A 上传完成时因版本条件被冻结. 按用户定义 A 一直在写, B 才是同时写入的一方; 按先到者胜被冻结的是 A. 两种结果都让用户处理, 不丢数据.
- 独占所有者在终端离线期间被转移: 按提交时的设置判断, 不按改动时. 原所有者离线时的改动上线后被拒, 成为待处理.
- 服务端时钟倒退期间时间窗少报 (见上).

#### 2.3.1 基于过时内容的写入 (D8, 已定)

时间上不重叠的写入在用户定义下不算同时写入, 常见的离线场景因此漏掉: 笔记本 8:00 离线, 台式机 9:00 在单端的仓库里提交 (9:01 所有权失效), 笔记本 10:00 离线改同一仓库, 14:00 联网. 只按时间窗, 笔记本的提交被接受; 两端都改过的文件由逐文件 base 检查变成待处理, 只有笔记本改过的文件直接上传, 仓库在服务端成为两端的混合, 这正是单端要防止的. 用户选 A: 笔记本带的 `since` 是 8:00 离线前的游标, 台式机 9:00 的写入 `seq` 更大, 笔记本被冻结, 台式机照常.

- 比的是整个范围的版本, 不是单个文件的版本 (用户 11-06 同意): 否则混合仓库 (两端各改各的文件) 抓不到. 不限目录中的文件各自是范围, 所以那里仍是逐文件比.
- 实现代价: 服务端不加写入, 只在判断时读 `since` 之后的行 (上面的查询); 客户端每个有未上传改动的范围在本地库记一个整数 (2.6).
- 两个条件互补: 版本条件管离线, 慢同步, 慢上传; 时间窗管 "收到了但对方还没写完".

### 2.4 检测点

| 范围状态 | 服务端提交时 | 结果 |
|---|---|---|
| 不限 (目录) | 该文件的所有权 + 逐文件 base 检查 | 后到者该文件待处理, 只冻结该文件 |
| 单端 | 所有权判断 + 逐文件 base 检查 | 后到者该范围的全部本地改动待处理, 冻结该范围 |
| 独占 | 非所有者拒绝; 所有者逐文件 base 检查 | 非所有者该范围的全部本地改动待处理, 冻结该范围 |

- 客户端不预先判断, 一律提交: 所有权在缺块检查之前判断, 被拒的提交不上传块, 只多一个很小的请求; 客户端因此不需要知道所有者. 例外是超过 `proto.MaxCommitBlocks` 的大文件, 它的块列表在提交前已分段暂存, 块已上传; 用户之后选 "上传" 时这些块正好可用, 选 "丢弃" 时由 GC 清掉.
- 代价: 每批每个单端范围一次上面的查询; 范围判断是对内存中的设置行做最长前缀匹配 (通常 0 到几行).

### 2.5 冻结 (D1: 只冻结后到的一端)

- 被拒的设备冻结该范围; 先到的设备和其他设备照常同步, 通知和 ntfy 写明两端的设备名.
- 冻结的宽度 = 判断所有权的单位: 单端或独占范围整体 (多文件一致性正是设这两种状态的目的), 不限目录中只是那个文件. 想让一处冲突影响更小, 就把根设为不限, 只把需要的子目录设为单端.
- 冻结是双向的: 冻结期间该设备不上传该范围的改动 (新的本地改动也加入待处理), 也不把服务端在该范围的改动写进本地. 拉取跳过冻结范围内的条目而不停住游标; 解冻时把游标退回冻结时记下的值重读一次 (已应用的条目按 `seq` 跳过).
- 冻结记在客户端状态库 (2.6), agent 重启后继续; 服务端只从客户端上报得知 (3.6 的模式, 不加表).

### 2.6 本地记录

`local(path, seq, hash, ...)` 已记着每个路径的 base, 提交带的 `base_seq` 来自它. 本地库架构版本 2 -> 3 只补:

- `held(path, scope, reason, base_seq, kind, hash, size, mtime_ns, at)`: `reason` 为 `owner` (同时或非法写入), `conflict` (逐文件), `type` (文件与目录同名, 6.6), `reset` (5.5 的 epoch 重置与 3.5 的接管); `kind` 为修改, 新增, 删除; `hash/size/mtime_ns` 是上报时本地那一份的快照 (删除时为空), 处理时用来核对.
- `meta`: `frozen:<scope>` (冻结时的游标), `dirty:<scope>` (该范围的 `since`).

`since` 的记法 (客户端, 只会偏小, 偏小只会多报):

- 扫描首次发现单端范围 S 中有待上传的改动时, 把上一次扫描时 S 的已应用游标记为 `dirty:<S>`; S 中没有待上传改动后清除. 同一段改动分几批提交时各批带同一个值. 一次扫描只在 `dirty` 有变化时写 `meta`, 平时不多写盘.
- 待处理的改动算作未上传, 所以 S 冻结期间 `dirty:<S>` 不变, 全部处理完且没有别的待上传改动时才清除. "待上传" 不含当前上传不了的路径 (名称被拒 `rejected`, 读取失败): 否则一个一直传不上去的文件 (例如被别的程序长期锁住) 会让 `since` 永远停在旧值, 之后别人在 S 里的任何写入都使本机每次提交被冻结. 这类路径恢复可传时按新发现的改动记 `since`, 同一路径上的冲突仍由逐文件 base 检查兜住.
- S 的已应用游标: 平时是文件夹游标; S 冻结期间拉取跳过 S, 所以是 `frozen:<S>`; 解冻后重读 S 完成才回到文件夹游标 (2.5). 离线期间游标不动, 重新上线先扫描后拉取 (`design.md` 6.2), 所以离线改动带的是离线前的游标.
- 设置变化使范围的划分变了 (新设单端子目录, 删除设置等): 新范围的 `since` 取被它覆盖的旧范围中最小的 `dirty` 值. epoch 重置 (5.5) 时清除全部 `dirty`, 改动按 `reset` 成为待处理.
- 独占范围和不限目录不用 `since` (前者只看所有者, 后者用 `base_seq`).

- 一条待处理记录只在以下情况消失: 用户的处理动作执行成功; 本地文件又改回 base 或改成与服务端当前相同 (采纳); 配置变化使原因不存在 (例如本机成为独占所有者, 或范围改为不限, 这时按普通改动重新提交, 按新设置判断: 改为单端时带 `dirty:<S>` 的旧值, 期间有他端写入就再次成为待处理). 不会因时间过去而消失, 也不会被拉取覆盖.

### 2.7 处理动作 (D2, D3)

用户对每条待处理改动选一个动作 (Web UI, 可批量, 4.3). 冲突必须处理到只剩一份, 没有 "两份都保留". 决定里带用户看到的服务端当前 `seq` (`expect`) 和上报时的本地快照哈希:

| 动作 | 何时可选 | 本地核对 | 服务端核对 | 成功后 |
|---|---|---|---|---|
| 上传 | 服务端在 base 之后没有改过该路径 | 本地仍等于快照 | 提交带 `base_seq` 和 `resolve`: 跳过所有权判断, 逐文件 base 检查照常 | 进入服务端, 其他设备收到 |
| 上传并覆盖 | 总可选 | 同上 | 提交带 `base_seq = expect` 和 `resolve`: 服务端当前 `seq` 必须仍是用户看到的值 | 服务端旧内容进入 `versions`, 可恢复 |
| 丢弃 | 总可选 | 同上 | 下载服务端当前版本 (以服务端为准, `expect` 之后又变了也取最新) | 本地那份默认移到 `.syncsaved`, 用户可选直接丢弃; 原路径换成服务端版本 |

- 核对失败都不执行: 本机在决定后又改了文件, 决定作废, 按新快照重新上报, Web UI 显示 "本机又改过, 请重新选择"; 服务端在 `expect` 之后又变了, 该条留在待处理并刷新显示. 不会误覆盖, 也不会上传或丢掉用户没看过的内容.
- 丢弃时的保存: 本地那份移到同步根下的 `.syncsaved/<YYYYMMDD-HHMMSS>/<原路径>` (同卷 rename, 不复制; 同一次处理共用一个时间戳目录, 一次 git 操作的一组文件在一起, 可以整体拷回). `.syncsaved` 内置排除, 不同步. 全量扫描时删除其中超过 30 天的时间戳目录 (与 `.syncpart-*` 的 24 小时清理同类): 否则 D7 下反复丢弃的 `.git/index` 会一直累积.
- 文件与目录同名 (`type`): "上传并覆盖" 一次提交删除服务端另一种类型的条目再新增本地的 (删除在前, 6.4); "丢弃" 把本地的文件或整个目录按上面保存后取服务端的.
- 动作执行是普通的提交与下载, 走现有的块上传, 暂存和原子落地.
- 一个范围的待处理全部处理完 (表中该范围没有行) 时解冻, 按 2.5 重读该范围. 之后的新改动按重读后的游标记 `since` (2.6), 不会因冻结前的他端写入再被冻结: 上传类动作的 `resolve` 提交使本机的下限前进 (2.3), 丢弃不写服务端, 但重读已把那些写入应用到本地. 处理期间别的终端又写了该范围, 照常按 2.3 判断.

### 2.8 批量处理与 `.git` (D7)

- 单端和独占范围的改动通常是一组 (一次 `git commit` 改动几十到几百个文件). 逐文件混选会让该范围在服务端成为两端的混合, 所以处理框先给整范围的动作 ("全部丢弃", "全部上传并覆盖"), 再允许展开逐文件选择, 混选时提示可能不一致.
- "全部上传并覆盖" 只覆盖本机改过的文件; 先到者改过而本机没改的文件仍是先到者的版本. 想让本机的整个范围胜出, 要先把范围恢复到冻结前的状态, 这要按 `seq` 恢复 (现有恢复按时刻), 列为后续改进.
- 产品逻辑不变 (D7): 独占范围内非所有者的任何改动都使该设备停止同步该范围. 拉取改写工作区文件后, 非所有者上的 `git status` 会重写 `.git/index`, 每次都会冻结并推送; 手册写明 "独占的仓库只在所有者上运行 git".
- 单端范围有同样的风险: 接收端在所有者的写入到达后 N 分钟内, 或在还没拉取完所有者的写入时, 运行 `git status` (或编辑器, 索引程序在文件变化后自动写状态文件), 就是同时写入 (前者是时间窗, 后者是版本条件). 缓解: 这类目录设为不限, 或把 N 调小; 实测 (第 7 节) 记录冻结次数和原因.

### 2.9 与现有机制的关系

- 冲突副本不再生成 (D3): 6.1 中内容不同的 "修改 vs 修改", "新建 vs 已存在", 以及 "修改 vs 已删除", "删除 vs 修改" 都是两端同时写入, 一律成为待处理, 由用户选; "内容相同" 与 "删除 vs 已删除" 仍直接采纳; 自冲突 (本设备自己的提交) 仍放行一次. 6.6 文件与目录同名, 5.5 的 epoch 重置, 3.5 的接管已有目录, 原来生成冲突副本的地方同样成为待处理; 后两者一次可能很多, 用整范围的批量动作处理. 冲突副本的命名, 通知和 `files.conflict` 列一并删除 (未发布, 没有兼容负担; dogfood 中已有的冲突副本当作普通文件).
- 大小写冲突, 非法名称 (`rejected`): 不变, 它们不是多端写入问题.
- 版本保留, 恢复, GC, 排除规则: 不变. "上传并覆盖" 覆盖掉的服务端内容照常进入 `versions`.
- ntfy (4.3): 客户端在出现新的待处理改动时立即推送一条 (每个文件夹一个问题键, 正文只写文件夹名, 原因 (与谁同时写入 / 谁独占), 条数, 不写路径), 全部处理完推送 `Recovered`.

## 3. 协议与存储

- 全局库架构版本 3 -> 4: 表 `locks` 改名为 `writectl(folder_id, path, key, mode, device_id, created_at)`, 主键 `(folder_id, key)`, `mode` 为 `free`, `single`, `exclusive`, 只有 `exclusive` 的 `device_id` 非 0; 已有行转为 `exclusive`. 服务端启动时载入内存, 修改时在同一事务里改库和内存. 全局 `meta` 加 `write_window` (秒, 默认 60, 0 到 3600), 只影响服务端, 不改变 `config_version` (与 `keep_days` 相同).
- 文件夹库架构版本 3 -> 4: 删除 `files.conflict`, `versions.conflict` 和对应的部分索引.
- 下发配置: `FolderConfig.readonly` 删除, 改为 `writectl: [{"path": "", "mode": "single"}, {"path": "scratch", "mode": "free"}, {"path": "scratch/repo", "mode": "exclusive"}]`; 客户端只用它划分范围 (算 `since`, 冻结和待处理的单位), 不需要所有者. 设立, 修改, 转移都使 `config_version` 加一并广播 (3.3).
- 提交操作新增字段: `since` (整数, 单端范围内的操作带, 同一批中同一范围的操作带同一个值, 2.6), `resolve` (布尔, 2.7). 不限目录和独占范围的操作不带 `since`. 拒绝原因 `owner` 取代 `locked`, 附范围路径, 状态, 对方设备名, 以及命中的条件: `stale` (版本, 附那次他端写入的 `seq`) 或 `window` (时间窗, 附所有权的失效时刻), 独占时为 `exclusive`. 通知 (4.3) 据此写原因.
- 待处理清单上报: `POST /api/v1/held` `{folder, items: [...]}`, 只在清单变化时发送 (一次 git 操作可能有数千条, 不放进长轮询的状态里; 长轮询状态只带每个范围的条数和清单的版本号). 服务端存在内存中, 重启后由客户端重新上报. 每个文件夹至多 2 万条, 超过时只报条数.
- 处理决定下发: Web UI 提交的决定存在服务端内存, 按设备排队, 随该设备的长轮询返回 (`actions: [{folder, path, action, expect, local_hash, save}]`, `save` 为丢弃时是否保存本机那份), 有新决定时唤醒长轮询. 设备执行后上报新的待处理清单, 服务端据此清除已完成的决定. 服务端重启丢失未执行的决定, 待处理记录仍在, Web UI 显示为未处理, 用户再点一次.
- 设备 API 版本: `AgentVersion` 6, `MinAgentVersion` 也升到 6: 旧客户端不带 `since`, 也不会冻结和上报待处理 (只会生成冲突副本), 放行就会绕过写入控制; 用户只有一个且所有设备一起升级, 拒绝旧客户端并提示升级 (9.3).
- 本地库架构版本 2 -> 3: `held` 表与 `meta` 键 (2.6).

## 6. 小文件共用 256 KiB 存储块

另开专题 (`kaze-sync/blocks`, D6), 未定; 本节内容是第一版草稿的分析, 未修订.

### 6.1 现状与实测

- 现在每个块是 `blobs/ab/cd/<sha256>` 一个文件, 不超过 256 KiB 的文件只有一块. 写入: 临时文件, fsync, rename, fsync 目录 (16 个并发 fsync 约每个 0.4 ms, 5.8). 删除: GC 遍历 `blobs/` 并 unlink.
- 用 dogfood 的同步树 `~/projects` (只统计大小, 不读内容; 排除 `.tmp/`, `node_modules/`) 估计: 25282 个文件, 1.80 GB; 不超过 256 KiB 的 25052 个 (99.1%), 合计 179 MB, 其中不超过 4 KiB 的 17995 个 (71.2%). 全部块约 31369 个, 小文件占 80%.
- 小文件的空间损失: 按 4 KiB 分配取整后占 251 MB, 比实际多约 72 MB (+40%, 占整个存储约 4%), 另有每个文件一个 inode.
- 两级目录的损失更大: 叶目录有 65536 个, 约 3 万到 4 万个块会落在约 2.5 万到 3 万个不同的叶目录中, 每个至少 4 KiB, 约 100 到 120 MB. 这一项不需要打包就能消除: 改成一级 (`blobs/ab/<sha256>`, 256 个目录; 400 万个块时每个目录约 1.6 万项, ext4 的哈希目录索引处理这个量没有问题). 建议 Main 在服务端数据目录上只看元数据确认 (块文件数, 目录数, `du` 与 `du --apparent-size` 之差, 不读内容).

### 6.2 打包的收益与代价

收益:

- 文件数: 平均 4 KiB 的小文件每个 256 KiB 的包约 60 个, 2.5 万个小块变成约 400 个包文件; inode, 目录项, 4 KiB 取整的损失 (上例约 72 MB) 基本消失.
- 写入: 一个块包 (`POST /blocks`, 至多 64 MiB) 的小块追加到包里, 每个包一次 fsync, 而不是每块一次. 首次导入大量小文件时这是主要耗时 (5.8); 本机估计 2.5 万个小块从约 10 秒降到约 1 秒, 路由器上的绝对值要实测.
- 读取: 下载小文件时少了每块一次 open/close, 收益小 (内容多在页缓存中).

代价:

- 索引: 内容寻址不能再靠文件名, 要一张 `hash -> (包, 偏移, 长度)` 的表 (SQLite, 每行约 60 到 80 字节; 2.5 万行约 2 MB, 400 万行约 300 MB 磁盘). 提交检查块是否存在 (`blobs.Use`) 从一次 stat 变为一次索引查询.
- 宽限期: 现在靠块文件的修改时间 (`Use` 刷新, GC 比较). 包里的块没有各自的修改时间, 要在索引里加 `used_at` 列并在提交时更新, 每次提交多写索引行 (写盘增加).
- 删除与压缩: 块不再是一个文件, 删除只能记为包内的空洞; 要按包统计存活字节, 存活率低于阈值 (例如 50%) 时把存活的块复制到新包, 改索引, 删旧包. 这是新的写盘 (用户在意 SSD 磨损) 和新的崩溃窗口 (新包 fsync, 索引事务, 删旧包, 三步要按序且可重做). GC 的内存不变 (仍是哈希数组), 但多一遍包的统计.
- 版本保留: 被覆盖和删除的小文件在 `keep_days` (默认 30 天) 内仍被 `versions` 引用, 空洞要到过期后才出现; 所以压缩量约等于 "30 天前那段时间里小文件的变动量", 平时不大, 但大目录删除或改写后会集中出现.
- 去重: 不受影响 (索引仍按哈希).
- 代码: 块存储的写, 读, 存在检查, 清扫, 导出全部改写, 加压缩和迁移, 估计 300 到 400 行非测试代码, 是本项目最核心的数据路径.

### 6.3 偏移与长度的位数

- 包为 256 KiB = 2^18 字节时, 不对齐的偏移需要 18 位; 按 8 字节对齐需要 15 位 (平均每块浪费 3.5 字节); 按 4 KiB 对齐只要 6 位, 但又回到了 4 KiB 取整的损失. 长度 1 到 2^18 存为 `长度 - 1`, 也是 18 位.
- 若把位置压成一个 64 位整数: 8 字节对齐时偏移 15 位 + 长度 18 位 = 33 位, 包编号还剩 31 位 (2^31 个包 x 256 KiB = 512 TiB), 足够. 不对齐时 18 + 18 = 36 位, 包编号 28 位 (64 TiB), 也足够.
- 但在 SQLite 里压位没有收益: 整数列按值变长存储 (1 到 8 字节), 三个整数列 (`pack`, `off`, `len`) 与一个压缩后的整数大小相近, 而且可读, 可索引. 对齐也没有收益: 读取是 `pread` 到页缓存, 8 字节对齐不会更快. 结论: 真要做时用三个整数列, 不对齐, 不必规划位数; 若将来索引放到 SQLite 之外的定长记录文件里, 才按 "不对齐, 18 + 18 + 28" 的方案.

### 6.4 建议与决定用的测量

- 现在不做打包 (D6 选项 A): 写入控制要先完成, 打包改的是最核心的数据路径, 而已知的最大一项空间损失 (两级目录) 可以用约 30 行加一次迁移 (只做 rename) 消除.
- 决定是否打包的测量: (1) 在 dogfood 服务端只看元数据: 块文件数, 目录数, 已用与表观大小之差; (2) 在 OpenWrt 测试虚拟机 (或目标路由器) 上测首次导入 2.5 万个小文件的耗时, 以及 GC 清扫 3 万到 400 万个块的耗时, 与一个打包原型的基准 (`BenchmarkPutSmall`, `BenchmarkSweep`) 对比. 判断规则: 扁平化之后空间损失仍超过存储的 15%, 或首次导入/GC 在目标机器上因每块一个文件而慢 3 倍以上且绝对时间超过数分钟, 才做打包.

## 7. 多端写入测试方案

目标是快速发现问题, 发现后容易定位和修.

### 7.1 确定性模拟 (每次提交跑, 失败时自动缩小)

扩展 `internal/client/sim_test.go` (三个客户端, 一个进程内的真服务端, 种子决定一切):

- 随机配置: 每个文件夹随机给根和若干子目录设不限, 单端, 独占 (随机所有者), 运行中随机修改和转移; N 随机取 0, 1 分钟, 10 分钟.
- 时钟: 服务端一个假时钟, 偶尔向前跳和倒退 (检验 2.3: 倒退时时间窗当作已过, 不长时间误冻结); 客户端时钟随机偏差和跳变, 检验写入控制与客户端时钟无关.
- 操作: 现有的写, 删, 改名, 加上 "一组文件的写入" (模拟 `git commit`, 随机分成几批提交, 中间可插入别人的提交), 离线 (某客户端连续 k 轮不同步, 期间照样改文件, k 可以很大), Web 恢复, 一直传不上去的文件 (名称被拒, 读取失败), 随机的处理决定 (三种动作, 丢弃时随机保存与否, 包括过时的决定: 决定后服务端又变, 或本地又改), 以及处理期间的配置变化.
- 新不变式: (1) 所有权: 每个单端范围中, 被接受的设备提交 (`resolve` 与 `web` 除外) 之前, 范围内没有比它的下限 (2.3) 更新的他端写入, 范围内上一次写入是它自己的, 或者是他端的且到达已不少于 N (按服务端假时钟; 倒退期间不查); (1b) `since` 不偏大: 模拟器知道每次改动发生时该客户端真实的已应用游标, 提交带的 `since` 不得大于其中最小的 (偏大就是漏报, 是客户端最容易错的地方, 例如解冻重读, 离线, 设置变化, 一直传不上去的文件); (2) 独占: 范围内非所有者的条目只来自 `resolve` 提交; (3) 不丢数据: 扫描见过的每份内容仍在服务端 (当前或 `versions`), 某个客户端上 (含 `.syncsaved`), 或被用户的一次 "直接丢弃" 明确放弃; (4) 冻结的范围在该设备上只被本地写入和处理动作改变, 拉取不写入; (5) 待处理记录只因决定, 改回或配置变化消失; (6) 全部处理完并同步若干轮后收敛, 且没有冲突副本名.
- 现有的 "每个调用前后注入崩溃" 扫描扩展到处理动作的执行路径.
- 发现快, 修得快: 失败时输出种子, 操作日志和该范围的服务端历史 (`seq`, 设备, `created_at`, 提交带的 `since`, 命中的条件); 自动缩小 (按操作日志重放, 逐段删去操作, 保留仍失败的最短序列), 输出一个可以直接粘进单元测试的最小用例. 平时每次 `go test` 跑默认种子数, 每日检查跑多 10 倍.

### D9: 根目录默认单端时, 离线编辑会冻结整个文件夹 (待定)

背景: 根默认单端 (#59), 所以没有显式设置的文件夹整个是一个单端范围. D8 选 A 后版本条件比的是整个范围: 一台设备离线期间在该文件夹里改了任何文件 (哪怕与别人改的毫无关系), 而别的设备在此期间也改过该文件夹的任何文件, 上线后这台设备在整个文件夹的同步就冻结, 全部本机改动成为待处理, 也收不到别人的改动, 直到用户在 Web UI 处理 (没有同文件冲突时一次 "全部上传并覆盖" 即可, 只覆盖本机改过的文件). 第二版只按时间窗时, 这种冻结只发生在写入相隔不足 N 分钟时; 现在对经常离线的笔记本几乎每次上线都会发生. 在线设备的影响小: 改动通常几秒内上传, `since` 很少落后. 本机 dogfood (WSL 写, Windows 镜像只收) 不会遇到, 实测要靠 7.2 的场景.

- A (建议): 保持根默认单端. 这正是 D8 的语义 (范围内的混合由用户确认), 处理只需一次整范围动作; 手册写明 "文件夹里各文件互不相关, 又有经常离线的设备时, 把根设为不限, 只把仓库等需要整体一致的目录设为单端". 实测 (7.2) 记录处理所需的点击, 若嫌烦再改.
- B: 新建文件夹的根默认不限, 用户自己把仓库等目录设为单端. 离线编辑只在真正改了同一文件时成为待处理 (逐文件, 只冻结该文件), 但用户忘记设置时仓库可能混合; 改变 #59 的 "根默认单端".
- C: 版本条件只用于显式设为单端的范围, 默认 (继承到根的单端) 只用时间窗. 冻结少, 但同一状态有两种判断, 违背 "能用一种机制解决的不用两种", 界面上也要区分 "默认单端" 和 "单端".
