# 设计草稿: 写入控制 (不限, 单端, 独占) 与待处理改动

状态: 草稿, 待用户决定第 11 节各项后并入 `docs/design.md` (任务 `kaze-sync/writectl`). 依据用户 2026-11-06 网页聊天 #59 (原文在总层任务文件中) 与 #64 ("独占用改为只读这个设计已经取消了"). 本草稿替换 `design.md` 2.8 的只读独占 (11-05 部署, 未启用); 2.8 中 "服务端按路径前缀判断, Web UI 设立与转移" 的部分保留, "本地只读" 与 `.syncsaved` 的部分删除 (第 8 节).

## 0. 结论摘要

- 用户的设想总体合理, 而且比只读方案更适合本项目: 不改本地权限 (只读挡不住 Windows 上的新建, 会让构建和 `git` 的写入失败, 卸载后残留), 所有判断都用服务端的 `seq`, 不用修改时间. 需要修改的有三处: "同一时间" 要定义成 "版本交接" 而不是时间窗或租约 (2.3); 冻结只冻结 "后到的那一端" 在该范围内的同步, 先到者照常 (2.5, 待决定 D1); 冲突副本不再自动生成, 改为一个处理动作 (2.9, D3).
- 本地记录文件版本可行, 而且已经有了: 客户端状态库 `local.seq` 就是每个路径上次与服务端一致时的服务端版本号, 即提交的 base. 新增的只是 "待处理" 表 (记下本地改动的快照, 供处理时核对) 和一张很小的拉取记录 (2.6).
- 检测靠两点: 服务端提交检查 (单端和独占范围的 "交接检查", 加现有的逐文件 base 检查), 客户端扫描时对独占范围的预先判断. 离线设备只能在重新上线后的第一次提交时被发现, 不丢数据.
- 小文件共用存储块: 现在不做. 更便宜的改进是把块目录从两级 (65536 个叶目录) 改为一级, 实测数据估计可省约 100 MB 的目录块, 比打包能省的 4 KiB 取整损失还多; 打包要等目标路由器上的测量 (第 6 节, D6).
- 发布: 建议 v0.1.0 照原计划发 (不早于 11-11), 只隐藏只读独占的入口与手册章节; 写入控制作为 v0.2.0 (第 10 节, D5).

## 1. 用户设想逐条评估

1. **"独占不阻止写入, 但发现写入后即进入不能同步的状态 (并记录文件版本), 并推送警告."** 合理. 只读方案的问题 (Windows 目录属性无效, ACL 代价大, 只读让构建与工具失败, 卸载残留) 全部消失; 用户在本机的改动永远不被系统动过, 只是不上传. 风险: 非独占设备上的后台写入 (尤其是 `git status` 刷新 `.git/index`: 拉取改写了工作区文件后, 索引里的 stat 信息过时, git 会重写索引) 会反复产生待处理改动, 见 2.8 与 D7. "记录文件版本" 可行, 见 2.6.
2. **"用户需要对改动过的所有文件进行处理 (丢弃/上传/上传并覆盖其他设备的改动), 处理完后才能回到可同步状态. 覆盖判断不能靠修改时间, 需要靠服务端生成的版本号."** 合理, 需要补充: (a) 每个动作都是双向的比较并交换: 服务端一侧核对用户做决定时看到的服务端 `seq`, 本地一侧核对本地文件仍是上报时的那一份 (2.7); (b) 丢弃的本地内容去向 (D2); (c) 对 `.git` 这类多文件一致的目录, 逐文件混选会造成不一致, 界面应先给整范围的动作 (2.8); (d) 建议加第四个动作 "两份都保留" (把本地那份另存为冲突副本名后上传, 即现在的自动行为), 文档类文件常用 (D3).
3. **"需要频繁实测多端写入的场景, 聚焦如何快速发现问题, 如何方便解决问题."** 合理, 方案见第 7 节: 确定性模拟器加新不变式和自动缩小失败用例; 真机用单独的测试文件夹跑脚本化场景, 并入每日检查.
4. **"默认最高级目录同一时间只能有一端写入, 但可以改成下级目录才有这个限制. 文件的最低要求是同一时间只能有一端写入. 出现多端写入且没设置独占时, 多端同时停止同步, 并发警告."** 方向合理, 两处要改:
   - "同一时间" 不能按时钟定义 (各设备时钟不同, 离线设备没有 "当时"), 也不宜用租约 (租约要在线申请和续期, 离线设备拿不到, 而本方案本来就不阻止本地写入, 租约挡不住任何东西). 改为 "版本交接": 一端在某范围内的改动, 必须是在它已经收到其他端在该范围内的全部改动之后做的, 否则就是多端同时写入 (2.3).
   - "多端同时停止同步" 若字面执行, 一台设备上一次误写 (例如编辑器保存了一个状态文件) 会让正在工作的另一台设备也停下, 直到用户处理. 建议只冻结后到的一端 (它的改动尚未进入服务端, 需要用户决定), 先到的一端照常并收到警告 (D1).
   - 根目录默认单端的风险: 两台设备上都有后台程序写同一个文件夹时 (状态文件, 缓存), 会频繁冻结. 通知里给出 "把该子目录设为不限" 的提示; 实测 (第 7 节) 记录冻结次数.
5. **"用户只有一个, 账号也只有一个, 没有权限高低之分."** 与现有设计一致 (单管理员, 设备没有权限级别). 设计中 "管理员权限最高, 独占不约束 Web UI" 的说法改为 "Web UI 的写入 (恢复) 是用户本人的写入, 计入交接检查的 '其他端'" (2.4); 文档里去掉 "用户指设备" 一类的说法.
6. **"独占和同时写入限制都针对目录设置, 一个目录有三种写入控制状态: 不限, 单端, 独占. 文件只有两种: 单端和独占. 文件的写入控制从父目录继承."** 合理. 补充继承规则: 最近的显式设置生效 (子目录可以比父目录宽, 也可以比父目录严), 各显式设置把树划分成互不重叠的 "范围" (2.2).
7. **"目录和文件的颜色要用来区分不同状态."** 合理, 补充图标形状和文字标签, 色弱时不依赖颜色 (4.2).
8. **还原图记号**: 已在 `3346873` 完成.
9. **小文件共用 256 KB 存储块**: 收益真实但比预想小, 代价集中在 GC 的压缩回收和崩溃安全; 现在不做, 先做更便宜的目录扁平化并测量 (第 6 节).

## 2. 模型

### 2.1 术语

- **写入控制状态**: 目录三种 (不限, 单端, 独占), 文件两种 (单端, 独占). 独占带一台 "独占设备".
- **范围**: 一个显式设置及其覆盖的路径. 根目录总有一个设置 (默认单端). 每个路径属于离它最近的显式设置所在的范围.
- **待处理改动** (held): 本机上没有上传, 等用户决定的改动. 一条记录对应一个路径.
- **冻结**: 某设备上某范围 (或单个文件) 的同步暂停: 本机改动不上传, 服务端的改动也不写入该范围. 只影响这一台设备.

### 2.2 状态, 继承与范围

- 存储: 每个文件夹的设置是若干 (路径, 状态, 独占设备) 行; 没有行的路径继承. 根路径 `""` 没有行时为单端 (用户 #59 的默认).
- 生效状态 = 路径本身或最近祖先上的显式设置 (最长前缀, 按 `pp.Key` 比较, 与服务端不区分大小写的命名空间一致). 子设置可以放宽或收紧父设置, 例如根为单端, `scratch/` 为不限, `scratch/repo/` 为独占.
- 范围互不重叠: 一个范围覆盖它的设置路径之下, 除去其中更深的显式设置所在的子树. 例如上例中根范围不含 `scratch/`, `scratch/` 范围不含 `scratch/repo/`. 交接检查只在同一个范围内比较, 所以独占的 `repo/` 里的写入不会让根范围冻结.
- 文件可以显式设为独占 (一个只含该文件的范围); 文件不能设为不限, 因为文件的最低要求就是单端, 这正是现有的逐文件 base 检查.
- 不限的目录不构成交接单位: 其中每个文件自己是单端 (逐文件检查), 不同文件可以由不同设备同时改.
- 原来的 "独占范围不能重叠" 规则取消 (最长前缀天然处理嵌套).
- 独占设备被吊销, 或删除了它在该文件夹的映射: 该独占行在同一事务中改为单端 (而不是删除, 删除会让它退回父设置, 可能变成不限). 删除文件夹时删除其全部行.
- 改名: 设置记的是路径字符串, 不跟踪改名 (与 2.8 相同). 跨范围的移动是 "旧范围删除 + 新范围新增", 各自检查.
- 与排除规则独立: 被排除的路径不同步, 写入控制对它们没有意义.

### 2.3 "同一时间只能有一端写入" 的定义: 版本交接

定义: 设备 D 在单端 (或独占) 范围 S 内的一次改动, 若在 D 做这次改动时, 服务端 S 中已有 D 尚未收到的其他端写入, 就是多端同时写入. 反过来, 若 D 在改动之前已经收到 S 中其他端的全部写入, 这就是一次正常的交接, 不论两次写入在时钟上相隔多近.

实现:

- 每个操作带 `since`: D 做这次改动时它已应用到的游标 (服务端 `seq`). 服务端在提交时检查: S 中是否存在 `seq > since`, 且写入者不是 D 的存活条目或墓碑 (`device` 不等于 D; 排除规则造成的删除 `web:rules` 不算写入; Web UI 的恢复 `web` 算 "其他端", 它是用户本人在 Web UI 做的写入). 存在则该操作所在范围的这一批操作全部被拒, 原因 `concurrent`.
- "做这次改动时" 由客户端估计: 变更时刻 = 文件 mtime, 夹在 [上次看到旧状态的扫描时刻, 本次扫描时刻] 之内 (mtime 可能被复制工具保留得很早, 也可能在未来); 删除没有 mtime, 用父目录的 mtime, 同样夹住. 再用 "拉取记录" (每次拉取推进游标时记 (时刻, 游标), 本机时钟, 存在状态库, 保留最近 256 次) 查出该时刻的游标. 早于最早记录时用最早记录的游标 (偏向多报, 不漏报). 这里只用本机自己的时钟和本机自己的 mtime 比较, 不跨设备比较时间; 判断 "谁覆盖谁" 仍然只用服务端 `seq`.
- 误差: mtime 在扫描与拉取之间的几秒窗口里可能略晚于真实改动, 使 `since` 偏大而漏报; 同一文件的竞争仍由逐文件 base 检查兜住. 文档写明.
- 一批之内: 同一范围内的操作取最小的 `since` 统一判断, 要么全收要么全拒, 不让一个范围的一半改动进入服务端.
- 由此得到可检验的不变式 (第 7 节): 服务端接受的每个设备提交, 在它的 `seq` 之前, 同一范围里其他端的写入都不晚于它的 `since`. 也就是说, 范围内的写入历史是一串单写者的交接, 只有用户显式的处理动作 (2.7) 例外.
- 离线设备: 离线期间什么也发现不了 (也不需要, 它的改动只是在本机排队). 重新上线后第一次提交时, 若离线期间其他端改过同一范围, 被拒并冻结, 推送警告; 若没有, 照常上传. 先 Scan 后 Pull 的顺序 (6.2) 保证它在收到其他端改动之前先提交.
- 为什么不用租约: 租约要求写入前在线申请, 离线设备拿不到也不知道别人的租约; 本方案不阻止本地写入, 租约既挡不住写入, 也不能比提交时的检查更早发现; 还要增加续期流量, 超时计时器和服务端状态. 独占可以看作用户手动设立的永久租约.
- 相同内容不算冲突: 被拒后客户端逐个比较, 本地内容与服务端当前相同的 (例如两台机器生成了相同的构建产物) 直接采纳, 不进入待处理. 只有 mtime 变了而内容相同的文件本来就不提交 (5.2).

### 2.4 检测点

| 范围状态 | 客户端扫描时 | 服务端提交时 | 结果 |
|---|---|---|---|
| 不限 | 照常提交 | 逐文件 base 检查 | 同一文件被两端改且内容不同: 后到者该文件待处理, 只冻结该文件 |
| 单端 | 照常提交 | 交接检查 + 逐文件 base 检查 | 交接失败: 后到者该范围的全部本地改动待处理, 冻结该范围 |
| 独占, 本机是独占设备 | 照常提交 | 交接检查 + 逐文件 base 检查 | 只有用户的处理动作或 Web UI 恢复会让交接失败 |
| 独占, 本机不是 | 不提交, 直接列为待处理并冻结该范围, 推送警告 | 拒绝 (`exclusive`), 兜住配置过时的情况 | 同左 |

- 服务端检查的代价: 交接检查是 `SELECT 1 FROM files WHERE seq > ? AND device <> ? AND device <> 'web:rules' AND <在范围内> LIMIT 1`, 走 `seq` 索引, 只看比 `since` 新的条目, 平时为空或几条; 范围判断是对内存中的设置行做最长前缀匹配 (通常 0 到几行). 每批每个范围查一次, 不是每个操作一次.
- Web UI 的恢复不受写入控制约束 (用户本人的操作), 但它产生的条目算其他端写入, 所以恢复期间正在改同一范围的设备会被冻结并收到警告. 这是正确的: 用户在两处同时改了同一范围.

### 2.5 冻结: 谁停, 停多宽

- 建议 (D1 选项 A): 只冻结后到的一端, 即提交被拒或按独占预先判断的那台设备; 先到的一端和其他只接收的设备照常同步, 但通知和 ntfy 告诉用户哪两台设备在同一范围同时写入. 理由: 先到者的改动已经在服务端, 是一致的; 后到者的改动还没进入服务端, 才需要用户决定. 先到者照常, 用户正在用的机器不会被另一台机器上的一次误写拖住.
- 冻结的宽度 = 发生冲突的范围: 单端或独占范围整体冻结 (多文件一致性正是设这两种状态的目的, 例如 `.git` 不能一半来自 A 一半来自 B); 不限目录中只冻结冲突的那个文件. 想让一处冲突影响更小, 就把根设为不限, 只把需要的子目录设为单端, 这正是用户说的 "可以改成下级目录才有这个限制". 其他范围, 其他文件夹完全不受影响.
- 冻结是双向的: 冻结期间该设备不上传该范围的改动 (新的本地改动也加入待处理), 也不把服务端在该范围的改动写进本地 (否则本地的 `.git` 会混入另一端的一半状态). 拉取跳过冻结范围内的条目而不停住游标; 解冻时把游标退回冻结时记下的值重读一次 (已应用的条目按 `seq` 跳过, 与 6.6 的完整对账同理).
- 选项 B (用户原话的字面做法): 范围冻结时所有写过该范围的设备都停止该范围的上传, 直到处理完. 需要服务端记录冻结 (一张小表, 或内存加重启后由客户端重新上报恢复), 先到者的新改动也要排队; 处理完后先到者排队的改动若与后到者上传的内容交叉, 会引发第二轮冻结.
- 冻结状态存在客户端状态库 (2.6), agent 重启后继续冻结; 服务端只从客户端上报得知 (与 3.6 的错误相同, 不加表).

### 2.6 本地记录: 待处理表与拉取记录

可行性: `local(path, seq, hash, ...)` 已经记着每个路径的 base (服务端 `seq` 与内容哈希), 提交带的 `base_seq` 就来自它; epoch 重置时它被清零 (5.5). 所以 "记录文件版本" 不需要新机制, 只需补两张小表 (本地库架构版本 2 -> 3):

- `held(path, scope, reason, base_seq, kind, hash, size, mtime_ns, since, at)`: `reason` 为 `exclusive`, `concurrent`, `conflict` (逐文件); `kind` 为修改, 新增, 删除; `hash/size/mtime_ns` 是上报时本地那一份的快照 (删除时为空), 处理时用来核对本地没有再变. 冻结的范围记在 `meta` (`frozen:<scope>` = 冻结时的游标).
- `pulls(at_ns, cursor)`: 环形保留 256 行, 每次拉取推进游标时写一行 (拉取本来就在写 `local` 和 `cursor`, 多一行可以忽略).
- 一条待处理记录只在以下情况消失: 用户的处理动作执行成功; 本地文件又改回 base 或改成与服务端当前相同 (采纳); 配置变化使原因不存在 (例如本机成为独占设备, 或范围改为不限: 这时它按普通改动提交, 仍受逐文件检查). 不会因时间过去而消失, 也不会被拉取覆盖.

### 2.7 处理动作与版本核对

用户对每条待处理改动选一个动作 (Web UI, 可批量; 第 4 节). 决定里带两样东西: 用户看到的服务端当前 `seq` (`expect`), 和上报时的本地快照哈希. 设备执行前后的核对:

| 动作 | 何时可选 | 本地核对 | 服务端核对 | 成功后 |
|---|---|---|---|---|
| 上传 | 服务端在 base 之后没有改过该文件 (`当前 seq = base_seq`, 新增时路径不存在或是墓碑) | 本地仍等于快照 | 提交带 `base_seq` 和 `resolve` 标记: 跳过交接检查和独占检查, 逐文件 base 检查照常 | 进入服务端, 其他设备收到 |
| 上传并覆盖 | 总可选 | 同上 | 提交带 `base_seq = expect`: 服务端当前 `seq` 必须仍等于用户看到的值, 否则返回冲突, 该条留在待处理并刷新显示 | 服务端旧内容进入 `versions`, 可恢复 |
| 丢弃 | 总可选 | 同上 | 下载服务端当前版本 (`expect` 之后又变了也取最新, 丢弃的意思是 "以服务端为准") | 本地那一份按 D2 保存, 本地换成服务端版本 |
| 两份都保留 (D3) | 服务端改过该文件时 | 同上 | 本地那一份改名为冲突副本名, 作为新增上传; 原路径下载服务端版本 | 与现在的冲突副本相同, 4.3 的冲突副本通知照常 |

- 本地核对失败 (用户在决定之后又改了文件): 决定作废, 该条按新的快照重新上报, Web UI 显示 "本机又改过, 请重新选择". 这避免把用户没看过的内容上传或丢掉.
- 服务端核对完全基于 `seq`, 不看修改时间 (用户 #59).
- 动作执行是普通的提交与下载, 走现有的块上传, 暂存 (大文件) 和原子落地, 不需要新的传输代码.
- 一个范围的待处理全部处理完 (表中该范围没有行) 时解冻, 按 2.5 重读该范围; 之后该设备在该范围的新改动照常走交接检查.
- 处理动作本身也可能与先到者的新写入交叉 (D1 选 A 时先到者没停): `上传` 在服务端已变时返回冲突, `上传并覆盖` 在 `expect` 过时时返回冲突, 都只让该条留在待处理并刷新, 用户再选一次. 不会误覆盖.

### 2.8 批量处理, 整范围处理与 `.git`

- 单端和独占范围的改动通常是一组 (一次 `git commit` 改动几十到几百个文件). 逐文件混选 (一部分上传, 一部分丢弃) 会让该范围在服务端成为两端的混合. 所以处理框先给整范围的动作: "全部丢弃 (以服务端为准)", "全部上传并覆盖", 再允许展开逐文件选择, 混选时提示 "该范围设为单端/独占, 混选可能使其中的数据不一致".
- "全部上传并覆盖" 只覆盖本机改过的文件; 先到者改过而本机没改的文件仍是先到者的版本. 想要 "本机的整个范围胜出", 需要先把范围恢复到冻结前的状态再上传, 这要按 `seq` 恢复 (现有恢复按时刻), 列为后续改进, 不在本草稿的第一版里.
- `.git` 的已知噪音: 拉取改写工作区文件后, 非独占设备上的 `git status` 会重写 `.git/index` (以及 `git fetch` 写 `FETCH_HEAD`), 每次都产生待处理改动和一条推送. 建议文档写明 "独占的仓库只在独占设备上运行 git"; 若实测中噪音大, 再考虑给独占范围加 "非独占设备的改动自动丢弃" 选项 (D7). 单端范围没有这个问题 (按交接顺序正常同步, 只是有流量).

### 2.9 与现有机制的关系

- 冲突副本: 不再自动生成 (6.1 "修改 vs 修改, 内容不同" 改为待处理). 建议保留为处理动作 "两份都保留" (D3). 冲突副本命名, 同步, 通知的代码保留.
- 6.1 的其他自动规则: "修改 vs 已删除 (修改优先)" 与 "删除 vs 修改 (删除让步)" 也是两端同时写入, 一律改为待处理, 由用户选 (规则统一, 少一类分支); "内容相同" 与 "删除 vs 已删除" 仍直接采纳. 自冲突 (6.1, 本设备自己的提交) 仍放行一次, 不进入待处理.
- epoch 重置 (5.5) 和接管已有目录 (3.5 `adopt`): 内容不同的文件原来生成冲突副本, 现在进入待处理; 可能一次很多, 用整范围的批量动作处理. 文档写明.
- 大小写冲突, 非法名称, 类型冲突 (`rejected`): 不变, 它们不是多端写入问题.
- 版本保留, 恢复, GC, 排除规则: 不变. "上传并覆盖" 覆盖掉的服务端内容照常进入 `versions`.
- ntfy (4.3): 客户端在出现新的待处理改动时立即推送一条 (每个文件夹一个问题键, 正文只写文件夹名, 范围是否为独占, 条数和另一端的设备名, 不写路径), 全部处理完推送 `Recovered`; 服务端照常对上报的错误推送.

## 3. 协议与存储

- 全局库架构版本 3 -> 4: 表 `locks` 改名为 `writectl(folder_id, path, key, mode, device_id, created_at)`, 主键 `(folder_id, key)`, `mode` 为 `free`, `single`, `exclusive`, 只有 `exclusive` 的 `device_id` 非 0. 迁移把已有行 (只读独占, 用户未设立, 通常为空) 转为 `exclusive`. 服务端启动时载入内存, 修改时在同一事务里改库和内存 (恢复 2.8 草稿原来的内存表, 因为提交检查现在每批都要用).
- 下发配置: `FolderConfig.readonly` 删除, 改为 `writectl: [{"path": "", "mode": "single"}, {"path": "repo", "mode": "exclusive", "mine": true}]` (`mine`: 本机是独占设备). 设立, 修改, 转移都使 `config_version` 加一并广播 (3.3).
- 提交操作新增字段: `since` (整数, 2.3), `resolve` (布尔, 2.7 的上传与覆盖). 新的拒绝原因: `concurrent` (交接失败, 附该范围路径和先到的设备名), `exclusive` (取代 `locked`). 冲突结果不变 (`conflict` 附服务端当前状态).
- 待处理清单上报: `POST /api/v1/held` `{folder, items: [...]}`, 只在清单变化时发送 (一次 git 操作可能有数千条, 不放进每次长轮询的状态里; 长轮询状态只带每个范围的条数和清单的版本号). 服务端存在内存中, 与 3.6 的上报一样重启后由客户端重新上报. 每个文件夹至多 2 万条, 超过时只报条数.
- 处理决定下发: Web UI 提交的决定存在服务端内存, 按设备排队, 随该设备的长轮询返回 (`actions: [{folder, path, action, expect, local_hash}]`), 有新决定时唤醒长轮询. 设备执行后上报新的待处理清单, 服务端据此清除已完成的决定. 服务端重启丢失未执行的决定, 待处理记录仍在, Web UI 显示为未处理, 用户再点一次 (罕见, 不为此加表).
- 设备 API 版本: `AgentVersion` 6, `MinAgentVersion` 也升到 6. 旧客户端不带 `since`, 服务端无法做交接检查, 若放行就会绕过单端; 用户只有一个且所有设备一起升级, 拒绝旧客户端并提示升级最简单 (9.3 已有该机制).
- 本地库架构版本 2 -> 3: `held`, `pulls` 两张表 (2.6).

## 6. 小文件共用 256 KiB 存储块

### 6.1 现状与实测

- 现在每个块是 `blobs/ab/cd/<sha256>` 一个文件, 不超过 256 KiB 的文件只有一块. 写入: 临时文件, fsync, rename, fsync 目录 (16 个并发 fsync 约每个 0.4 ms, 5.8). 删除: GC 遍历 `blobs/` 并 unlink.
- 用 dogfood 的同步树 `~/projects` (只统计大小, 不读内容; 排除 `.tmp/`, `node_modules/`) 估计: 25282 个文件, 1.80 GB; 不超过 256 KiB 的 25052 个 (99.1%), 合计 179 MB, 其中不超过 4 KiB 的 17995 个 (71.2%). 全部块约 31369 个, 小文件占 80%.
- 小文件的空间损失: 按 4 KiB 分配取整后占 251 MB, 比实际多约 72 MB (+40%, 占整个存储约 4%), 另有每个文件一个 inode.
- 两级目录的损失更大: 叶目录有 65536 个, 约 3 万到 4 万个块会落在约 2.5 万到 3 万个不同的叶目录中, 每个至少 4 KiB, 约 100 到 120 MB. 这一项不需要打包就能消除: 改成一级 (`blobs/ab/<sha256>`, 256 个目录; 400 万个块时每个目录约 1.6 万项, ext4 的哈希目录索引处理这个量没有问题). 建议 Main 在服务端数据目录上只看元数据确认 (块文件数, 目录数, `du` 与 `du --apparent-size` 之差, 不读内容).

### 6.2 打包的收益与代价

收益:

- 文件数: 平均 4 KiB 的小文件每个 256 KiB 的包约 60 个, 2.5 万个小块变成约 400 个包文件; inode, 目录项, 4 KiB 取整的损失 (上例约 72 MB) 基本消失.
- 写入: 一个块包 (`POST /blocks`, 至多 64 MiB) 的小块追加到包里, 每个包一次 fsync, 而不是每块一次. 首次导入大量小文件时这是主要耗时 (5.8); 本机估计 2.5 万个小块从约 10 秒降到约 1 秒, 路由器上的绝对值要实测.
- 读取: 下载小文件时少了每块一次 open/close, 收益小 (内容多在页缓存中).

代价:

- 索引: 内容寻址不能再靠文件名, 要一张 `hash -> (包, 偏移, 长度)` 的表 (SQLite, 每行约 60 到 80 字节; 2.5 万行约 2 MB, 400 万行约 300 MB 磁盘). 提交检查块是否存在 (`blobs.Use`) 从一次 stat 变为一次索引查询.
- 宽限期: 现在靠块文件的修改时间 (`Use` 刷新, GC 比较). 包里的块没有各自的修改时间, 要在索引里加 `used_at` 列并在提交时更新, 每次提交多写索引行 (写盘增加).
- 删除与压缩: 块不再是一个文件, 删除只能记为包内的空洞; 要按包统计存活字节, 存活率低于阈值 (例如 50%) 时把存活的块复制到新包, 改索引, 删旧包. 这是新的写盘 (用户在意 SSD 磨损) 和新的崩溃窗口 (新包 fsync, 索引事务, 删旧包, 三步要按序且可重做). GC 的内存不变 (仍是哈希数组), 但多一遍包的统计.
- 版本保留: 被覆盖和删除的小文件在 `keep_days` (默认 30 天) 内仍被 `versions` 引用, 空洞要到过期后才出现; 所以压缩量约等于 "30 天前那段时间里小文件的变动量", 平时不大, 但大目录删除或改写后会集中出现.
- 去重: 不受影响 (索引仍按哈希).
- 代码: 块存储的写, 读, 存在检查, 清扫, 导出全部改写, 加压缩和迁移, 估计 300 到 400 行非测试代码, 是本项目最核心的数据路径.

### 6.3 偏移与长度的位数

- 包为 256 KiB = 2^18 字节时, 不对齐的偏移需要 18 位; 按 8 字节对齐需要 15 位 (平均每块浪费 3.5 字节); 按 4 KiB 对齐只要 6 位, 但又回到了 4 KiB 取整的损失. 长度 1 到 2^18 存为 `长度 - 1`, 也是 18 位.
- 若把位置压成一个 64 位整数: 8 字节对齐时偏移 15 位 + 长度 18 位 = 33 位, 包编号还剩 31 位 (2^31 个包 x 256 KiB = 512 TiB), 足够. 不对齐时 18 + 18 = 36 位, 包编号 28 位 (64 TiB), 也足够.
- 但在 SQLite 里压位没有收益: 整数列按值变长存储 (1 到 8 字节), 三个整数列 (`pack`, `off`, `len`) 与一个压缩后的整数大小相近, 而且可读, 可索引. 对齐也没有收益: 读取是 `pread` 到页缓存, 8 字节对齐不会更快. 结论: 真要做时用三个整数列, 不对齐, 不必规划位数; 若将来索引放到 SQLite 之外的定长记录文件里, 才按 "不对齐, 18 + 18 + 28" 的方案.

### 6.4 建议与决定用的测量

- 现在不做打包 (D6 选项 A): 写入控制要先完成, 打包改的是最核心的数据路径, 而已知的最大一项空间损失 (两级目录) 可以用约 30 行加一次迁移 (只做 rename) 消除.
- 决定是否打包的测量: (1) 在 dogfood 服务端只看元数据: 块文件数, 目录数, 已用与表观大小之差; (2) 在 OpenWrt 测试虚拟机 (或目标路由器) 上测首次导入 2.5 万个小文件的耗时, 以及 GC 清扫 3 万到 400 万个块的耗时, 与一个打包原型的基准 (`BenchmarkPutSmall`, `BenchmarkSweep`) 对比. 判断规则: 扁平化之后空间损失仍超过存储的 15%, 或首次导入/GC 在目标机器上因每块一个文件而慢 3 倍以上且绝对时间超过数分钟, 才做打包.

## 7. 多端写入测试方案

目标是快速发现问题, 发现后容易定位和修.

### 7.1 确定性模拟 (每次提交跑, 失败时自动缩小)

扩展 `internal/client/sim_test.go` (三个客户端, 一个进程内的真服务端, 种子决定一切):

- 随机配置: 每个文件夹随机给根和若干子目录设不限, 单端, 独占 (随机设备), 运行中随机修改和转移.
- 操作: 现有的写, 删, 改名, 加上 "一组文件的写入" (模拟 `git commit`: 同一范围内若干文件一起改), 离线 (某客户端连续 k 轮不同步, 期间照样改文件), 随机的处理决定 (四种动作, 包括过时的决定: 决定后服务端又变, 或本地又改), 以及处理期间的配置变化.
- 新不变式: (1) 交接: 每个范围的服务端历史中, 被接受的设备提交之前, 其他端的写入都不晚于它的 `since`, `resolve` 提交和 `web` 恢复除外; (2) 独占: 范围内非独占设备的条目只来自 `resolve` 提交; (3) 不丢数据: 扫描见过的每份内容仍在服务端 (当前或 `versions`), 某个客户端上, 或被用户的一次丢弃决定明确放弃 (D2 选 A 时它也在 `versions`); (4) 冻结的范围在该设备上只被本地写入和处理动作改变, 拉取不写入; (5) 待处理记录只因决定, 改回或配置变化消失; (6) 全部处理完并同步若干轮后收敛.
- 现有的 "每个调用前后注入崩溃" 扫描扩展到处理动作的执行路径.
- 发现快, 修得快: 失败时输出种子, 操作日志和该范围的服务端历史 (`seq`, 设备, `since`); 加自动缩小 (按操作日志重放, 逐段删去操作, 保留仍失败的最短序列), 输出一个可以直接粘进单元测试的最小用例. 平时每次 `go test` 跑默认种子数, 每日检查跑多 10 倍.

### 7.2 真机脚本场景 (每日检查中跑, 约 5 分钟, 写入不到 10 MB)

- 用一个单独的服务端测试文件夹 (例如 `writectl-test`), 映射到 WSL 客户端和 Windows 镜像客户端的单独目录, 不碰 `~/projects` 的真实数据. 需要第三端时用 VM (按总层规则加锁, 并避开 Strata 运行时).
- 场景 (`e2e` 里一个新场景组, 也能单独运行): 顺序交接 A -> B -> A (期望不冻结); 两端同时改同一文件 (不限: 只冻结该文件); 两端同时改不同文件 (单端根: 冻结后到者; 不限: 不冻结); B 停掉 agent 离线改, A 改, B 启动 (上线后冻结); 独占范围在非独占设备上误写 (待处理, ntfy 推送); 真实 git 仓库: A `git commit`, B 同时 `git commit` 或 `git status`; 每种处理动作各一次, 包括过时的决定和批量; 冻结期间改配置.
- 每个场景记录并在报告中列出: 从写入到 Web UI 通知和 ntfy 推送的延迟, 处理需要的点击次数, 处理后两端与服务端的哈希比对; 失败时自动收集两端日志, 服务端日志和处理框内容的快照.
- dogfood 期间 (`~/projects`, WSL 写, Windows 镜像只收) 另记每天的冻结次数和原因, 用来判断根目录默认单端是否过于敏感.

## 11. 待用户决定

### D1: 发生多端同时写入时, 谁停止同步

背景: 用户 #59 说 "出现多端写入且没设置独占时, 多端同时停止同步, 并发警告". 先到服务端的那一端的改动已经进入服务端且自身一致; 后到的一端的改动还在本机, 需要用户决定.

- A (建议): 只冻结后到的一端在该范围的同步 (上传和下载都停), 先到的一端照常, 两端都在通知和 ntfy 中出现. 用户正在用的机器不会被另一台机器的一次误写拖住; 服务端不加状态.
- B: 所有写过该范围的设备都停止该范围的上传, 直到处理完. 更符合原话, 但先到者也要等用户处理, 处理后可能再起一轮冻结; 服务端要记录冻结状态.

### D2: "丢弃" 时本机那一份去哪里

背景: 被丢弃的本地内容从未到过服务端. 现有原则是 "不静默丢失".

- A (建议): 上传到服务端的版本历史 (只进 `versions`, 不成为当前版本), 保留期内可在 Web UI 中恢复. 代价是上传变化的块 (丢弃不常发生).
- B: 移到设备本地的保存目录 (类似已取消的 `.syncsaved`), 不产生流量, 但用户要自己清理, 也看不到它.
- C: 真的丢掉. 最简单, 选错了无法挽回.

### D3: 冲突副本是否保留

背景: 用户要求文件最低单端, 多端写入时停下等处理, 所以自动冲突副本不再出现. 但对文档类文件, "两份都保留" 常常就是用户想要的处理.

- A (建议): 不再自动生成, 保留为第四个处理动作 "两份都保留" (现有代码复用).
- B: 完全去掉冲突副本, 只有丢弃, 上传, 上传并覆盖三个动作.

### D4: 是否增加客户端命令行处理

背景: 设计的非目标里客户端没有本地命令 (除注册外). 处理框在 Web UI 中; 命令行适合人正在那台机器上时.

- A (建议): 先只做 Web UI, 实测中觉得需要再加 `kaze-syncc held` / `resolve` (约 80 行, 走服务端接口, 离线不能用).
- B: 第一版就加.

### D5: v0.1.0 是否等写入控制

背景: 原计划不早于 11-11 发布 v0.1.0. 写入控制改变冲突语义和协议, 实现后还需一周 dogfood.

- A (建议): 按原计划发布现有版本 (冲突副本语义), 发布前隐藏只读独占的入口并从手册和 operations 中删掉相应章节; 写入控制作为 v0.2.0.
- B: 发布前先做 W1 (删除只读独占的代码), 再发布; 代码更干净, 但删除后要再观察几天, 发布可能推迟数天.
- C: 等写入控制完成并 dogfood 一周后再发布第一个版本 (约 11 月下旬).

### D6: 小文件共用存储块

背景: 第 6 节. 打包能省 inode, 4 KiB 取整和 fsync 次数, 但要新增索引, 压缩回收和新的崩溃窗口; 已知更大的一项空间损失来自两级块目录, 可以单独消除.

- A (建议): 现在不打包; 先确认目录损失 (只看元数据) 并把块目录改为一级; 按 6.4 的测量结果再决定打包.
- B: 与写入控制一起做打包.
- C: 永不打包, 也不改目录.

### D7: 独占范围在非独占设备上的改动是否可以自动丢弃

背景: 在非独占设备上运行 `git status` 会重写 `.git/index`, 每次都产生待处理改动和推送 (2.8).

- A (建议): 第一版不加, 文档写明 "独占的仓库只在独占设备上运行 git"; dogfood 中噪音大再加.
- B: 第一版就给独占范围加一个选项 "非独占设备的改动自动丢弃 (按 D2 保存)", 约 30 行, 多一个配置项.
