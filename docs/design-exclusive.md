# 设计增补草稿: 子文件夹独占写

状态: 已并入 `docs/design.md` 2.8 并实现 (此文件保留为原始草稿, 以 design.md 为准); 原状态: 草稿 (任务 `kaze-sync/exclusive-d`). 依据用户 2026-11-05 网页聊天 #45, #46, #47 的原话 (见 `~/projects/.tasks/kaze-sync/exclusive.md`).

## 0. 需求与已定的点

- #45: 某个子文件夹由一台设备独占, 其他设备只能同步 (接收) 不能改写, 以免 `.git` 之类两边都写而产生冲突. 独占是全局配置, 一个路径只能由一台设备独占, 独占后其他设备改不了, 直到取消.
- #46: 其他设备改了独占目录里的文件, 服务端直接拒绝, Web UI 通知栏出现严重警告 (错误级). Web UI 中的恢复照常作用于独占目录 (管理员权限最高). 管理员可以强制解除独占.
- #47: 不做客户端通知 (违反 "Web UI 是唯一通知渠道"). 非独占设备把独占目录设为本地只读: 用户自己改不了, 只有同步服务能改.

"用户" 指设备 (kaze-sync 只有一个管理员). 设备没有本地界面和命令 (1 节非目标), 所以设立, 转移, 取消都在 Web UI 中由管理员完成; 用户说的 "该用户主动取消" 与 "管理员强制解除" 是同一个操作, 设备端不能取消或抢占独占.

轻量原则: 在 "轻量原则" 列表加第 9 项 "子文件夹独占写 (用户 2026-11-05)". 首要目标不受影响: 服务端只多一张很小的表和内存中的一张表, 提交时每个操作多做几次前缀比较; 客户端只在独占范围内做额外的 chmod, 空闲时没有任何开销.

## 1. 数据模型

- 独占对象: (文件夹, 路径, 设备). 路径相对文件夹根, 指目录 (也可以是文件, 匹配规则相同), 空路径表示整个文件夹. 覆盖范围是 "该路径本身或其下", 与恢复范围的说法一致 (4.5).
- 存储: 全局库 `meta.db` 新表 `locks(folder_id, path, key, device_id, created_at)`, 主键 `(folder_id, key)`; `key` 为 `pp.Key(path)` (NFC 加大小写折叠), 匹配一律按 `key` 比较, 与服务端不区分大小写的命名空间一致, 与设备系统无关. 全局库架构版本 2 -> 3 (只是 `CREATE TABLE`, 按 9.3 的迁移流程自动执行, 迁移前备份). 不放进 `folders` 或 `meta`: 要按设备删除和按路径查重叠, 单独的表最直接.
- 服务端启动时把全部行读入内存 (每个文件夹一个小切片, 通常 0 到几条), 修改时在同一事务里改库和内存. 提交检查只读内存.
- 嵌套与重叠: 任何路径至多被一条独占覆盖. 新建独占时, 若同一文件夹中已有它的祖先或后代 (含相同路径) 的独占, 无论属于哪台设备都拒绝, 错误写明已有的那一条 ("{path} 已由 {device} 独占, 独占范围不能重叠"); 要扩大或缩小范围, 先解除再设立. 不做自动合并: 罕见操作, 一条规则比合并语义容易理解.
- 设备: 只能选映射了该文件夹的设备 (对话框的下拉框只列它们). 设备被吊销, 或它在该文件夹的映射被删除时, 它在该文件夹的独占在同一事务中自动解除 (否则那里成为谁都改不了的冻结区); 吊销和删除映射的确认框列出将解除的独占. 修改映射的本机路径不影响独占. 删除文件夹时一并删除其独占行.
- 改名: 独占记的是路径字符串. 独占设备把该目录改名或移走后, 独占仍在旧路径上 (此时为空), 新位置不受保护; 文档写明, 不跟踪改名.
- 与排除规则的关系: 两者独立. 被排除的路径不同步, 独占对它们没有意义, 客户端也不对它们做只读处理 (3 节). 独占不改变下发的规则. 在被排除的路径上设立独占不报错 (规则以后可能改), 对话框不另提示.

## 2. 强制点

### 2.1 服务端: 提交时拒绝

- `commitOp` 在 base 检查之前先查独占: 操作路径的 `key` 等于某条独占的 `key` 或以 `key + "/"` 开头 (空路径的独占覆盖全部), 而提交的设备 id 不是独占设备时, 返回 `rejected`, 原因 `locked` (`proto.ReasonLocked`). 放在 base 检查之前, 是为了不让客户端走冲突流程, 在独占目录里再生成冲突副本.
- 覆盖全部写入: 新增, 修改, 删除都是 `commit` 的操作; 协议没有改名, 改名是删除加新增, 各自检查 (跨越独占边界的改名因此只有一半被拒, 见 4 节). 大文件的 `/stage` 不带路径, 不能提前拒绝, 在引用暂存的那次提交被拒; 新客户端事先知道独占, 不会为独占路径上传 (2.2).
- Web UI 的写入 (`web`, `web:rules`, 不是设备) 不受独占限制 (用户 #46: 管理员权限最高):
  - 版本恢复和恢复到某一时刻照常作用于独占子树, 作为服务端写入同步到所有设备, 包括独占设备. 恢复对话框在范围内有独占时多一行说明 "范围内有 {device} 独占的目录; 恢复照常进行并同步到所有设备; 若 {device} 同时在改同一文件, 它那边按冲突规则处理".
  - 保存排除规则造成的删除 (`web:rules`, 8.3) 同样照常; 这类删除带 `excluded`, 各设备 (含独占设备) 保留本地文件, 不会造成冲突. 预览中命中独占子树的路径不另标注.
- 事务与时序: 设立独占与提交分在两个库中; 提交在检查时读内存中的独占表 (读写锁保护), 设立前已通过检查的提交照常生效, 这些是独占之前的合法写入.

### 2.2 客户端: 事先知道

- 下发配置的每个文件夹多一个字段 `readonly`: 对本设备只读的路径列表 (别的设备独占的路径; 本设备自己独占的不列出). 示例 `{"id": 3, "name": "Code", "path": "D:\\Code", "adopt": false, "rules": [...], "readonly": ["kaze-sync/.git", "notes"]}`.
- 设立, 转移, 解除独占都与其他配置修改一样, 在同一事务中把 `config_version` 加一并广播 (3.3), 在线设备 1 秒内收到.
- 客户端据此: 扫描时不为只读范围内的改动发起提交 (省掉请求和块上传, 结果与服务端拒绝相同); 拉取时照常应用服务端的变更 (只读只针对本机的写入); 并把只读范围在本机设为只读 (3 节). 配置过时 (例如刚设立的独占还没收到) 时, 服务端的 `locked` 拒绝兜底, 客户端按同样的方式处理 (4 节).

## 3. 非独占设备上的本地只读 (用户 #47)

### 3.1 做法

只读是护栏, 不是强制: 用户在本机仍可手动解除 (他是文件的所有者), 强制靠服务端拒绝 (2.1), 收场见 4 节.

- Linux: 去掉只读范围内文件和目录的全部写权限位 (`chmod a-w`, 保留读与可执行位). 目录也要去掉: 目录没有写权限才不能在其中新建, 删除, 改名条目, 只改文件权限挡不住 `rm` 和 "写临时文件再 rename" 的保存方式 (git 和多数编辑器都这样写). 符号链接本身没有权限位, 不处理 (它所在的目录只读, 已不能被替换或删除). `git` 在只读的 `.git` 中仍能做只读操作: `git status` 在拿不到 `index.lock` 时跳过索引刷新, 不报错; 写入类命令 (`commit`, `fetch`) 失败, 这正是目的.
- Windows: 文件设只读属性 (`FILE_ATTRIBUTE_READONLY`). Go 的 `os.Chmod` 在 Windows 上去掉 `0200` 位即设置该属性, 所以两端用同一段代码 (`FS.SetWritable(path, bool)`). 目录的只读属性在 Windows 上不阻止任何操作 (资源管理器拿它表示 "自定义文件夹"), 不设. 效果: 已有文件不能被覆盖, 追加或删除 (资源管理器删除时会先询问; 编辑器保存时提示只读), 替换式保存 (`MoveFileEx` 覆盖只读目标) 失败; 但能在其中新建文件和目录. 新建的文件由 4 节兜底. ACL 方案的比较见待用户决定 D1.
- 被排除的路径 (8 节) 不处理: 它们不同步, 改了也不冲突. 但它们所在的目录若在只读范围内 (Linux), 其中不能新建条目 (例如在只读的仓库里构建会失败); 文档写明.

### 3.2 只读状态不会被当作改动

- 只同步可执行位 (6.7). 写权限位和 Windows 只读属性不进提交, 也不进本地状态库. 扫描判断 "未改" 只比较 `size`, `mtime_ns` 和 `link`, `chmod` 和改属性只改变 ctime (Windows 的 ChangeTime), 不改变 mtime (LastWriteTime), 所以扫描看不到它们; 内容有变化时才读取的可执行位不受 `a-w` 影响. Windows 客户端本来就不读可执行位.
- 因此独占设备和其他设备上的写权限可以不同, 互不影响; 只读的文件同步到别处后照常可写 (下载时按可执行位决定 mode, 3.4).

### 3.3 状态切换

客户端从配置的 `readonly` 列表和上一次的配置 (缓存在 `config.json`) 算出变化, 只在两个同步步骤之间应用 (3.3):

| 事件 | 本设备 | 本地动作 |
|---|---|---|
| 设立独占 | 非独占设备 | 保护: 先按 4 节处理范围内现有的本地改动, 再把范围内的文件 (Windows) 或文件和目录 (Linux) 设为只读 |
| 设立独占 | 独占设备 | 无 |
| 转移 (改由另一台设备独占, 一个事务) | 原独占设备 | 保护 (同上) |
| 转移 | 新独占设备 | 解除保护: 范围内的文件和目录加回所有者写权限 (`u+w`; Windows 清除只读属性) |
| 解除独占 (含管理员强制解除, 二者是同一操作) | 非独占设备 | 解除保护 (同上) |
| 删除本设备在该文件夹的映射 | 非独占设备 | 先解除保护, 再按 3.5 停止同步 (本地文件原样保留, 不能留下一棵只读的树) |
| 设备令牌被拒 (401, 吊销) | 任何 | 解除本机全部保护 (设备再也收不到配置, 不能让文件一直只读); 重新注册后按新配置再保护 |
| agent 启动; 每小时的全量扫描 | 非独占设备 | 修复: 范围内仍可写的条目重新设为只读 (崩溃在 "临时可写" 期间, 或用户手动解除过). 全量扫描本来就 lstat 每个条目, 只多比较一个权限位, 不多读盘 |

- 解除保护只加回所有者写权限, 不记录原来的权限: 独占前就只读的文件 (例如 git 的对象文件, 但它们由 kaze-sync 下载时本来就按 mode 规则写成可写) 解除后变成可写. 不为此增加状态; 文档写明.
- 客户端被卸载时没有机会解除保护: 文档给出手动命令 (Linux `chmod -R u+w <目录>`, Windows `attrib -r <目录>\* /s /d`).
- 保护与解除逐个条目进行, 范围为本地状态库中该前缀下的行加上其目录; 大目录 (几万个文件) 一次约需数秒, 只在状态切换时做.

### 3.4 客户端自己写入只读范围

拉取 (5.5) 照常把服务端的变更写入只读范围, 写入前后临时解除: 

- 写入, 替换, 删除一个文件之前, 把它所在的目录 (Linux) 和目标文件 (Windows 的替换与删除; Linux 的 rename 覆盖不需要目标可写) 设为可写; 写完后新文件和目录设为只读, 再恢复目录. 新建的目录在其内容写完后设为只读. 一批下载 (5.5 成批下载) 内同一目录只解除一次, 整批结束后恢复.
- 删除时自下而上删除变空的父目录 (5.5), 每个父目录的父目录同样临时可写.
- 崩溃在临时可写期间: 目录或文件留在可写状态, 下次 agent 启动或全量扫描修复 (3.3 末行). 原子落地 (12.3) 的复查只看 size 与 mtime, 不受权限变化影响.
- `FS` 接口加 `SetWritable(path string, w bool) error`; 内存替身记录权限并在只读目录中拒绝新建, 删除, 改名, 测试因此能发现漏掉的临时解除.

## 4. 被拒的本地改动如何收场

只读挡住了大多数改动, 剩下的来源: 用户手动解除只读后修改; Windows 上在只读范围内新建文件 (属性挡不住); 设立独占时本机已有的未上传改动; 独占刚设立而本机配置还没更新时被服务端以 `locked` 拒绝的改动; 旧客户端 (6 节).

建议做法 (待用户决定 D2 的选项 A): 拒绝, 另存, 恢复服务端版本, 严重警告一直保留到用户处理.

- 扫描在只读范围内发现与本地状态库不一致的条目 (修改, 新增, 删除, 文件与目录互换), 照常等待 5 秒稳定期 (5.2), 然后不提交, 而是:
  1. 有服务端版本的路径 (修改, 删除): 先按本地状态库中的 base (`hash`, `blocks`) 把服务端版本下载到临时文件 (12.3; 块大多就在本地文件里, 按 5.5 复用); 下载失败 (离线, 服务端不可达) 就什么都不动, 下次再试, 期间照样上报.
  2. 把本地那份移到同步根下的 `.syncsaved/<YYYYMMDD-HHMMSS>/<原路径>` (同一卷上的 rename, 不复制; 一次扫描内的所有条目共用一个时间戳目录, 一次 git 操作改动的一组文件因此在一起, 可以整体拷回).
  3. 把临时文件 rename 到原路径 (修改, 删除的情形), 设为只读; 新增的条目只移走.
  文件被占用 (Windows 锁定) 时上报 `in_use` 并按 5.7 重试, 不移动.
- `.syncsaved` 加入内置排除 (8.1, 与 `.syncroot`, `.syncpart-*` 同类, 不可覆盖), 不同步, 不受只读处理. 不自动清理: 里面的内容只有用户能判断要不要, 删除即处理完毕.
- 服务端以 `locked` 拒绝的提交 (配置过时) 走同样的流程.
- 拉取: 只读范围内服务端有新版本, 而本地文件与 base 不一致 (改动还没被扫描处理, 例如在 5 秒稳定期内) 时, 不再像普通路径那样跳过等待扫描 (5.5), 而是同样先把本地那份移入 `.syncsaved`, 再写入服务端版本. 只读范围内服务端始终胜出, 不生成冲突副本.
- 严重警告 (用户 #46): 客户端为每个只读范围上报一条错误 `{path: <独占路径>, kind: "rejected", message: "locked: ...", n: N}`, N 为该范围在 `.syncsaved` 中的条目数加上尚未处理完的改动数; 只要 N 大于 0 就一直上报. Web UI 中它是错误级通知 (红色, 4.3), 消息 "{device} 上有 {n} 个对 {path} 的改动被拒绝 ({owner} 独占), 已移到 .syncsaved", 处理说明 "这些改动没有上传, 保存在该设备的 <code>.syncsaved</code> 中; 不需要就删除它们; 需要时在 {owner} 上做同样的修改, 或先解除独占再拷回". 用户删除 `.syncsaved` 中对应的内容后, 下次扫描不再上报, 通知按 4.3 自动消失. 文件列表中独占路径那一行带红色标签 "被拒绝 · {device}". 只用一条汇总而不是逐个文件上报: 一次 git 操作可能改动数百个文件, 逐个上报会挤满每个文件夹 100 条的上报上限 (3.6), 盖住别的错误.
- 统计 `.syncsaved` 的条目: 全量扫描时顺带遍历它 (通常为空, 只读一次目录); 部分扫描不碰它.
- 结果: 不静默丢失 (本地那份在 `.syncsaved`, 服务端从未收到的内容不会消失), 不长期分叉 (本地树在下一次扫描后就回到服务端状态), 也不会和工具互相改写 (只读挡住了 git 刷新索引一类的自动写入; 即使用户解除了只读, 每次改动只多一份另存, 不上传, 不产生流量).

## 5. Web UI

### 5.1 入口与显示

- 设立: 文件夹页目录行的上下文菜单加 "设为独占…"; 标题行的 "⋯" 菜单加 "设为独占…" (作用于当前目录, 顶层时为整个文件夹). 对话框: 范围 (只读显示), 设备下拉框 (映射了该文件夹的设备, 带在线标记), 说明, 主按钮 "设为独占". 没有映射的设备时按钮禁用并说明. 重叠时表单校验失败, 错误显示在范围下方 (4.6).
- 已独占的目录行: 名称后一个锁图标加标签 "独占 · {device}"; 它的上下文菜单把 "设为独占…" 换成 "改由其他设备独占…" (同一对话框, 预选当前设备以外的第一台) 和 "解除独占…" (确认框, 红色按钮: "解除 {device} 对 {path} 的独占? 之后所有设备都能改写这里, 其他设备上的本地只读随之取消."). 不区分 "主动取消" 和 "强制解除": 设备没有界面, 两者都是管理员在这里点. 
- 在独占范围之内浏览时, 概况行 (4.5) 多一句 "此目录由 {device} 独占 (自 {time} 起), 其他设备上只读", 带链接到独占路径.
- 设备页: 映射行的状态列在该设备独占了该文件夹中的路径时注明 "独占 {n} 处"; 吊销确认框与删除映射确认框列出将自动解除的独占.
- 通知: 4 节的汇总错误; 旧客户端被 `locked` 拒绝时按普通 `rejected` 显示, 原因文字 "此路径由 {owner} 独占".
- 没有新的页面. 新增端点 `POST /folders/{id}/lock` (字段 `path`, `device`; `device` 为空表示解除), 一个处理函数覆盖设立, 转移, 解除, 走 `configChange`.

## 6. 协议兼容

- 新增的线上字段: 配置 `FolderConfig.readonly` (可省略), 拒绝原因 `locked`, 上报 `FileError.n` (可省略, 只用于 4 节的汇总). 都是可选的追加, 不改变已有字段的含义.
- 版本: 按 9.3 "设备 API 每次改动加一". 若在下次发布 (`kaze-sync/release`, 不早于 2026-11-11) 之前实现, 沿用 `AgentVersion` 5 (与符号链接, 大文件共用一次升级, 同 2.4 的先例); 否则升为 6. `MinAgentVersion` 都不变: 旧客户端仍能正常工作, 只是没有只读保护.
- 旧客户端遇到独占: 不认识 `readonly` (JSON 忽略未知字段), 照常提交, 被服务端以 `locked` 拒绝, 记为普通 `rejected` 错误 (逐个文件, Web UI 显示 "此路径由 {owner} 独占"), 按 5.4 等文件再变化才重试 (删除每次扫描重试一次, 只是一条 JSON 操作); 拉取时本地已改的路径照旧跳过, 本地那份一直保留并持续报错, 直到升级. 不丢数据, 不污染服务端; 升级后按 4 节收场. 版本列 (9.3) 让管理员看到哪些设备需要升级.
- 新客户端对旧服务端: 配置里没有 `readonly`, 行为不变.

## 9. 待用户决定

### D1: Windows 上的只读用只读属性还是 ACL

背景: Linux 去掉目录写权限即可挡住新建, 删除和改名. Windows 目录的只读属性无效, 文件的只读属性挡住覆盖与删除, 挡不住在目录中新建文件. 要在 Windows 上也挡住新建, 只能用 ACL.

- A. 只读属性 (建议): 与 Linux 共用 `os.Chmod`, Windows 专用代码约 10 行; 资源管理器, 编辑器, git 都认得; 被卸载时用 `attrib -r` 一条命令清除. 新建文件挡不住, 由 4 节兜底 (移入 `.syncsaved`, 红色警告).
- B. 当前用户的 ACL 拒绝项: 对范围内每个文件和目录加一条显式 (不继承) 的 Deny ACE, 拒绝写数据, 追加, 写属性, 删除, 删除子项, 新建文件和子目录. 同一账户下可行: agent 与用户是同一账户, 拒绝项同样作用于 agent, 但文件所有者始终有 `WRITE_DAC` (我们也不拒绝它), agent 每次写入前去掉相应对象的拒绝项, 写完再加回; 用户同样可以在 "属性 / 安全" 中去掉, 所以仍只是护栏. 不用可继承的 ACE: 继承项在每次临时解除时都要沿整棵子树传播, 几千个文件的 `.git` 每次下载都要改写几千个 ACL. 代价: Windows 专用代码约 150 行 (`x/sys/windows` 已是依赖, 不加新依赖); 每次写入多 2 到 4 次 ACL 调用; 全量扫描不能顺带检查 (读 ACL 要逐个打开文件), 修复只在启动和状态切换时做; 卸载后残留的拒绝项让用户看到无法解释的 "拒绝访问", 清除要用 `icacls <目录> /remove:d <用户> /t`; 被别的账户 (如管理员) 创建的文件, 所有者不是当前用户时, 仍靠现有的允许项保留 `WRITE_DAC`, 一般可行但要在真机上测.

建议 A: 只读是护栏, 强制和兜底已由服务端拒绝与 4 节完成; B 多 140 行和残留风险, 只换来 "Windows 上新建文件也被挡住".

### D2: 被拒的本地改动怎么收场

背景: 用户已定 "服务端拒绝 + 严重警告"; 剩下的是客户端本地那份怎么办. 只读之后这种情况很少 (见 4 节开头).

- A. 立即另存并恢复 (建议, 4 节): 稳定 5 秒后把本地那份移到 `.syncsaved/<时间>/`, 恢复服务端版本; 红色警告一直保留到用户删除 `.syncsaved` 中的内容. 不分叉, 不丢数据, 不上传, 不需要额外的按钮或配置字段.
- B. 保留本地, 直到独占设备改到同一文件或解除独占: 本地那份留在原处, 红色警告一直在; 独占设备再改它时服务端版本胜出, 本地那份移入 `.syncsaved`. 分叉可能持续很久 (独占设备不再改的文件), 用户在本机也没法自己回到服务端版本 (删掉文件又是一次被拒的改动), 所以还要加 Web UI 的 "以服务端版本还原该设备" 按钮和下发它的配置字段 (约多 60 行).
- C. 在原处生成冲突副本 (不上传): 不需要 `.syncsaved`, 但副本留在独占目录里; 对 `.git` 会留下 `refs/heads/main.conflict-...` 一类文件, git 会把它当作一个分支.

建议 A.
