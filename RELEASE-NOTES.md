# kaze-sync v0.1.0 release notes

[English](RELEASE-NOTES.md) | [简体中文](RELEASE-NOTES.zh-CN.md)

## What this release is

`v0.1.0` (released on 2026-11-14) is the first public version of kaze-sync, a self-hosted file sync service with version history for Linux and Windows computers. A small server (`kaze-syncd`) runs on OpenWrt or on an x86-64 Linux machine with systemd or OpenRC, and lightweight clients (`kaze-syncc`) on Linux and Windows keep your local folders in sync through it while you configure everything centrally in the server's Web UI.

This is a source-only release: there are no prebuilt binary downloads. Instead, you build the static binaries from source with Go on any machine as described in [section 2.1 of the user manual](docs/manuals/user-manual.md#21-build-the-binaries). Because the binaries do not print a version string, identify a build by the Git tag `v0.1.0`.

## Highlights

### Sync and storage

- **Block-based two-way sync across folders.** Each enrolled device can sync any number of folders mapped to local paths ([manual section 5](docs/manuals/user-manual.md#5-folders-and-mappings)). Files are split into 256 KiB blocks and only changed blocks are transferred over the network, so large files such as a 1 GB SQLite database sync efficiently. On the server, each synced folder has its own SQLite database and shares deduplicated block storage. Single files up to 128 GiB (`2^19` blocks) are supported; larger files are refused by the server.
- **Symbolic links.** Symbolic links are synced as links (introduced in protocol version 5) and are never followed ([manual section 8](docs/manuals/user-manual.md#8-simultaneous-writes-and-the-decision-dialog)). When a receiving device cannot create symbolic links—most commonly Windows when Developer Mode is turned off—the links remain safely on the server while the client leaves them uncreated locally and shows a single folded warning line per device in the Web UI. In the maintainer's deployment, the Windows client shows 8 such warnings; this is expected behaviour, not a fault.
- **Locked files and SQLite databases.** To avoid uploading half-written files or corrupting active databases, clients wait until a modified file is at least 5 seconds quiet, defer locked files on Windows (`in_use`) with slow automatic retries (after 30 seconds, 2 minutes, 10 minutes, and on subsequent scans), and pause syncing any SQLite database whose `-wal` or `-journal` side file is non-empty until the database closes cleanly ([manual section 10](docs/manuals/user-manual.md#10-files-in-use-and-sqlite-databases)).
- **Central exclusion rules.** Exclusion rules use `.gitignore` syntax in two layers—global and per folder—and are edited centrally in the Web UI ([manual section 7](docs/manuals/user-manual.md#7-exclusion-rules)). Because saving new rules deletes matching files from the server (moving them into version history while leaving local files untouched), the Web UI previews all matching server files before you save. Factory default global rules exclude common OS, editor, browser, and sync-tool clutter, including Nextcloud system files.
- **Low resource use and fast propagation.** Built for a 512 MB server with low CPU, low memory, and low traffic as its primary goal, `kaze-syncd` uses about 24 MB of RAM on a small data set and 35 to 65 MB on the maintainer's deployment of about 37,000 files. On clients, the Linux agent uses 36 to 40 MB of resident memory and about 0.3% CPU over a day, and the Windows agent uses a 74 to 79 MB working set; when idle, both server and clients use almost no CPU. During the observation period between a Linux client and a Windows client, a created or edited file reached the other computer in about 5 seconds (measured 5.1 to 5.2 seconds in both directions), and deletions in 2.2 to 7.9 seconds.

### Safety and restore

- **Version history on every overwrite or delete.** Whenever a file is overwritten or deleted, the server keeps the previous version for 30 days by default (configurable from 1 to 3650 days under **Version retention** (`版本保留`) in Settings; [manual section 13](docs/manuals/user-manual.md#13-retention-and-garbage-collection)).
- **File, deleted-file, and point-in-time directory restore.** From the Web UI, you can restore a single historical version of a file, bring back a deleted file, or restore a directory or entire folder as of a chosen moment using a restore dialog with a day axis and a time-of-day axis and a preview of affected files ([manual section 11](docs/manuals/user-manual.md#11-restoring-old-content)). Point-in-time restore writes back historical content without deleting files created after the chosen time, and every restore is recorded as a new version so it can itself be undone.
- **Bounded-memory garbage collection.** Daily garbage collection removes expired versions and unreferenced blocks in the background under a fixed 64 MB memory ceiling ([manual section 13](docs/manuals/user-manual.md#13-retention-and-garbage-collection)). A 512 MB server can collect up to about 512 GB of data in a single scan pass; larger data sets simply take additional passes without using more memory.
- **Plain-file export.** Because the server stores deduplicated blocks rather than a plain directory tree, `kaze-syncd export` writes out the current files (or the state as of a chosen UTC timestamp) as ordinary files on disk while verifying every file's cryptographic hash ([manual section 12](docs/manuals/user-manual.md#12-export-to-plain-files)).

### Write control

- **No duplicate conflict copies.** Write control (protocol version 6) replaces conflict copies—there are no conflict copies in this release. When two devices write to the same place at the same time, the first device to reach the server wins, and the second device freezes that part of the folder and holds its local edits as pending items until you decide what to do with them ([manual section 5.1](docs/manuals/user-manual.md#51-write-control-who-may-write-where)).
- **Three write modes per directory or file.** Every directory or file uses one of three rules ([manual section 5.1](docs/manuals/user-manual.md#51-write-control-who-may-write-where)): **Any writer** (`不限`, `free`), **Single writer** (`单端`, `single`), or **Exclusive** (`独占`, `exclusive`) for one specific device (a file inside an any-writer directory inherits **Single writer**, and the server refuses **Any writer** on an individual file). When the server creates a new folder, a reminder in the notification bar prompts you to choose its root write rule or confirm the `single` default.
- **Write window and pending decisions.** When two devices write to the same single-writer area within the write window (60 seconds by default, configurable in the Web UI under **Single-writer time window** (`单端写入时间窗`)) or when a device writes on out-of-date content, the later device freezes that scope and holds its changes as pending items; if both devices add or modify a file with identical content, it is accepted without freezing. In the decision dialog ([manual section 8](docs/manuals/user-manual.md#8-simultaneous-writes-and-the-decision-dialog)), you choose per item or per frozen group whether to upload (**Upload** `上传` / **Upload and overwrite** `上传并覆盖`) or discard (**Discard** `丢弃`, which saves the local copy under `.syncsaved/` by default).
- **Visual status in the Web UI.** The Web UI displays write control with icons and tooltips on every folder, directory, and file row, shows the root mode on the overview page and in the folder title row, and links directly from notifications to the affected device's decision dialog.

### Web UI

- **Five languages and live updates.** The dark-theme Web UI supports Simplified Chinese, Traditional Chinese, English, Japanese, and Korean, following your browser language by default or locked via a browser cookie ([manual section 4](docs/manuals/user-manual.md#4-the-web-ui)). It provides pages for Overview (`总览`), Folders, Devices, and Settings (`设置`), live status updates on the overview tables and notification bell, and context menus on rows and headers. Throughout the user manual, every button and label is named in English with its Simplified Chinese on-screen text next to it.
- **Optional ntfy push alerts.** Both the server and clients can send rate-limited push notifications for persistent errors and long-offline devices to an [ntfy](https://ntfy.sh) server via `ntfy.json` (off by default, without exposing filenames or secrets; [manual section 9.1](docs/manuals/user-manual.md#91-push-messages-with-ntfy)).
- **Safe to expose without a VPN.** `install` picks a random high TCP port (20000 to 59999) by default, `admin-password` generates a random administrator password, failed logins lock out the client IP after 10 attempts within an hour, and devices enroll using single-use codes valid for 15 minutes shown as copyable Linux and Windows commands ([manual section 2.4](docs/manuals/user-manual.md#24-port-certificate-and-firewall), [section 2.5](docs/manuals/user-manual.md#25-first-login-and-the-admin-password), and [section 3](docs/manuals/user-manual.md#3-installing-and-enrolling-clients)).

### Platforms and installation

- **Server and client platforms.** `kaze-syncd` (x86-64 only) runs on OpenWrt (`procd`) or plain Linux with systemd or OpenRC (tested on Ubuntu 24.04, Alpine Linux 3.24 with OpenRC, and an OpenWrt VM; [manual section 2](docs/manuals/user-manual.md#2-installing-the-server)). `kaze-syncc` runs on x86-64 Linux (as a systemd user service) and x86-64 Windows (`kaze-syncc.exe` for enrollment and the windowless `kaze-syncc-agent.exe` started at sign-in; [manual section 3](docs/manuals/user-manual.md#3-installing-and-enrolling-clients)). There is no Windows server, and no macOS or mobile clients.
- **Root install, unprivileged service execution.** You install and upgrade the server as root with `kaze-syncd install --data <dir>`, which creates the unprivileged user `kaze-sync` and keeps the binary and data directory owned by root so a compromised service cannot replace its own binary ([manual section 2.3](docs/manuals/user-manual.md#23-plain-linux-systemd-or-openrc)). On systemd, the generated unit is hardened (`NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, capability and syscall limits, with only `var/` writable). Non-root server deployment is not supported (decided 2026-11-08).
- **Three TLS certificate modes.** By default, `install` generates a self-signed certificate pinned by SHA-256 fingerprint. You can instead pass `--cert` and `--key` to use your own certificate, or pass `install --ca [--san]` to run a local CA whose certificate browsers can trust for password autofill while clients pin the CA fingerprint ([manual section 2.4](docs/manuals/user-manual.md#24-port-certificate-and-firewall)). In local CA mode, the CA private key in `<data>/ca/` is readable only by root, so the running service cannot renew the certificate itself; root renews and exports it with `install` or `kaze-syncd ca` (which can be placed in a monthly cron job), and the running server reloads a renewed `server.pem` within a minute without a restart.

## Requirements and compatibility

| Component | Requirement |
|---|---|
| Build toolchain | Go `1.27.3` (as in `go.mod`), building static binaries with `CGO_ENABLED=0` ([manual section 2.1](docs/manuals/user-manual.md#21-build-the-binaries)) |
| Server (`kaze-syncd`) | x86-64 Linux with OpenWrt (`procd`, requiring a mounted data disk), systemd, or OpenRC; root access required for installation and maintenance; targets machines with 512 MB RAM |
| Linux client (`kaze-syncc`) | x86-64 Linux with a systemd user session |
| Windows client (`kaze-syncc.exe`, `kaze-syncc-agent.exe`) | x86-64 Windows; both `.exe` files placed in the same permanent directory |
| Web UI browsers | Chrome or Edge 114+, Firefox 125+, or Safari 17+ with JavaScript enabled |
| Protocol and database versions | Sync protocol version 6 (server requires client protocol 6); client state database schema version 3 |

## How it was tested

- **Automated test suites.** Unit, simulation, and end-to-end tests, including an end-to-end driver for the 8 write-control scenarios running against a real Linux client and a real Windows client; Windows NTFS behaviour was tested on Windows.
- **Real-world deployment.** Starting on 2026-11-04, the maintainer synced their own working tree (about 37,000 files, a few GB) between a Linux (WSL) client and a Windows client; on 2026-11-11 the server was moved to a dedicated Alpine Linux machine running OpenRC. Following that move, three consecutive days of daily checks (2026-11-12, 2026-11-13, and 2026-11-14) passed: all write-control scenarios passed, the restore check passed, and there were no sync errors in the logs, no conflict copies, and no unexpected freezes. The deployed binaries at the end of the observation period were server `36cae68` and clients `f66140c`; the tagged `v0.1.0` commit differs from these only in documentation.

## Known limitations

**Important — custom `--cert` and `--key` permissions are not checked by `install`:** When you install the server with your own TLS certificate (`--cert` and `--key`), `install` runs as root and does not verify that the unprivileged service user `kaze-sync` can read those files. If `kaze-sync` cannot read them, `install` succeeds, but the service immediately exits at every start with `permission denied` in its log. To fix this, give the service user `kaze-sync` read access to both files and to every parent directory above them (for example, `chgrp kaze-sync key.pem && chmod 640 key.pem`), then restart the service; see [manual section 2.4](docs/manuals/user-manual.md#24-port-certificate-and-firewall) and the troubleshooting table in [section 17](docs/manuals/user-manual.md#17-troubleshooting). A check in `install` is planned for the next version.

Other limitations in `v0.1.0`:

- **Root-only server installation and CA renewal.** Server installation and local CA certificate renewal require root; non-root server deployment is not supported.
- **Source-only, no version output, no auto-update.** There are no prebuilt binary downloads, the binaries do not print a version string, and there are no automatic self-updates.
- **Scope boundaries ([manual section 18](docs/manuals/user-manual.md#18-what-kaze-sync-does-not-do)).** There is no file sharing, multi-user account system, or collaborative editing; no file preview or file download in the Web UI; no syncing of empty directories, Windows directory junctions, file permissions other than the executable bit, file owners, or extended attributes; no end-to-end encryption, transfer compression, or bandwidth rate limiting; no per-device exclusion rules; no two-factor authentication for the Web UI; no desktop tray icons or pop-up notifications on clients; no macOS or mobile clients; no server architectures other than x86-64; and single files larger than 128 GiB are refused by the server.
- **Not a backup.** Historical versions live on the same disk as the server's data; back up the server data directory to another disk or machine ([manual section 14](docs/manuals/user-manual.md#14-backup-and-restore-of-the-server)).
- **Symbolic links on Windows without Developer Mode.** A Windows client without Developer Mode enabled cannot create synced symbolic links locally; the links stay on the server and appear as a single folded warning line per device in the Web UI.
- **High-frequency files.** Files rewritten every few seconds (such as live status or telemetry files) create a new historical version on every write until retention removes them; exclude such paths if that matters ([manual section 7](docs/manuals/user-manual.md#7-exclusion-rules) and [section 13](docs/manuals/user-manual.md#13-retention-and-garbage-collection)).
- **Server storage format.** Server data is stored as deduplicated blocks and SQLite databases rather than plain files; run `kaze-syncd export` as root when you need plain files directly from the server ([manual section 12](docs/manuals/user-manual.md#12-export-to-plain-files)).
- **Server rollback after database migration.** Rolling the server binary back to an older version after a database schema migration requires restoring the pre-upgrade database backup from `<data>/var/backups/` and running `install --new-epoch` ([manual section 15](docs/manuals/user-manual.md#15-upgrading)).

## Upgrading

Because `v0.1.0` is the first public release, there is no earlier version to upgrade from.

This release freezes sync protocol version 6. The server requires client protocol version 6: if an older client connects to a protocol-6 server, the server pauses it with HTTP 426 and the client logs `client too old` without losing any local data until its binary is upgraded. When upgrading to future releases, always upgrade the server first (by running `kaze-syncd install --data <dir>` again with the new binary) and then upgrade your clients, following [section 15 of the user manual](docs/manuals/user-manual.md#15-upgrading).
