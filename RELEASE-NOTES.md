# kaze-sync v0.3.5 release notes

[English](RELEASE-NOTES.md) | [简体中文](RELEASE-NOTES.zh-CN.md)

## What this release is

`v0.3.5` (released on 2026-11-18) is a feature and maintenance release of kaze-sync, a self-hosted file sync service with version history for Linux and Windows computers. The device pages now show each client's release version, the server sizes its garbage-collection memory from the machine's memory instead of a fixed 64 MB, both programs keep a small in-memory summary of their own memory and CPU use, and, for the first time, the release comes with prebuilt packages. For the full overview of kaze-sync's sync, write-control, and restore features, see the [user manual](docs/manuals/user-manual.md), the [changelog](CHANGELOG.md), or the `v0.1.0` release notes in the Git tag `v0.1.0`.

**Prebuilt packages.** Earlier releases were source-only. From this release on, the [GitHub Releases](https://github.com/pellorao/kaze-sync/releases) page offers, for x86-64 (`amd64`) only, `kaze-sync-0.3.5-linux-amd64.tar.gz` (the server `kaze-syncd` and the Linux client `kaze-syncc`), `kaze-sync-0.3.5-windows-amd64.zip` (`kaze-syncc.exe` and the windowless `kaze-syncc-agent.exe`) and `SHA256SUMS`. Check the download with `sha256sum -c SHA256SUMS` (or `Get-FileHash` on Windows) as described in [section 2.1 of the user manual](docs/manuals/user-manual.md#21-download-and-verify-the-server-package). The packages are built reproducibly with `go run ./tools/release`. Other CPU architectures, such as most OpenWrt routers, still build from source ([Appendix A of the user manual](docs/manuals/user-manual.md#appendix-a-building-from-source)). Identify a build with `kaze-syncd --version` and `kaze-syncc --version` (or in the top-left of the Web UI after signing in) and by the Git tag `v0.3.5`.

## Highlights

- **Client version on the device pages.** The device list and the device page show the client's release version (`x.y.z`), which the client reports with every poll, instead of the integer protocol version. A client older than this release does not report one and shows `-` until you upgrade it. The protocol version stays 6.
- **Garbage-collection memory follows the machine.** At startup the server computes the memory budget for the garbage-collection reference array once, as 3/8 of the smaller of the machine's physical memory and its container or service memory limit, with a minimum of 64 MB (also used when the physical memory cannot be read). A 512 MB machine gets 192 MB, about 6 million block references in one pass, where the old fixed 64 MB cap needed several passes. Small data sets still allocate only what they need, there is no new setting, and the `msg=gc` log line now carries `budget` in bytes. The user manual's new "Memory sizing" section (section 13) shows how many files need how much memory and how `keep_days` changes it.
- **Daily resource summaries.** Both programs sample their own memory and CPU once a minute and keep the summaries of today and yesterday in memory only. Clients send theirs with the poll request, and the signed-in administrator can read the server's and every device's figures at `GET /resources` as JSON: median resident memory, CPU time, garbage-collection time and CPU, reference counts, the memory budget and the observed memory peak, with flags that say how much of the day is covered and whether the peak is exact. Nothing is written to files or databases, and there is no new dependency or Web UI control. The summaries are lost when a process restarts.
- **Documentation.** The user manual installs from the prebuilt packages by default and keeps building from source as an appendix; the README quick start downloads the packages; the operations notes describe the new memory model.
- **Release tooling.** `go run ./tools/release` builds the packages and `go run ./tools/pubcheck` checks the tree for personal notes and local paths before publishing.

## Upgrading

The sync protocol remains at version 6 and the minimum client version is unchanged. The database schemas are unchanged, so no data migration runs. The new fields in the poll request are optional: an older client keeps syncing with the new server, and a new client works with an older server. Still, upgrade the server first and then the clients, as the user manual recommends (for the full procedure, see [section 15 of the user manual](docs/manuals/user-manual.md#15-upgrading)):

- **Server (`kaze-syncd`)**: download and verify the Linux package ([manual section 2.1](docs/manuals/user-manual.md#21-download-and-verify-the-server-package)), copy `kaze-syncd` to the server, and run `./kaze-syncd install --data <same dir>` as root. Your listening port, TLS certificate, and admin password remain unchanged, and `install` copies the new binary into `<data>/` and restarts the service.
- **Clients (`kaze-syncc`)**: on each Linux or Windows computer, stop the running agent, replace the binaries (`kaze-syncc` on Linux; both `kaze-syncc.exe` and `kaze-syncc-agent.exe` on Windows), and start the agent again. The device page shows `0.3.5` for a client once it has restarted and polled.

## Known limitations

- **Root-only server installation and CA renewal.** Server installation and local CA certificate renewal require root; non-root server deployment is not supported.
- **Prebuilt packages for x86-64 only, no auto-update.** Other architectures build from source, and there are no automatic self-updates.
- **Scope boundaries ([manual section 18](docs/manuals/user-manual.md#18-what-kaze-sync-does-not-do)).** There is no file sharing, multi-user account system, or collaborative editing; no file preview or file download in the Web UI; no syncing of empty directories, Windows directory junctions, file permissions other than the executable bit, file owners, or extended attributes; no end-to-end encryption, transfer compression, or bandwidth rate limiting; no per-device exclusion rules; no two-factor authentication for the Web UI; no desktop tray icons or pop-up notifications on clients; no macOS or mobile clients; no server architectures other than x86-64; and single files larger than 128 GiB are refused by the server.
- **Not a backup.** Historical versions live on the same disk as the server's data; back up the server data directory to another disk or machine ([manual section 14](docs/manuals/user-manual.md#14-backup-and-restore-of-the-server)).
- **Symbolic links on Windows without Developer Mode.** A Windows client without Developer Mode enabled cannot create synced symbolic links locally; the links stay on the server and appear as a single folded warning line per device in the Web UI.
- **High-frequency files.** Files rewritten every few seconds (such as live status or telemetry files) create a new historical version on every write until retention removes them; exclude such paths if that matters ([manual section 7](docs/manuals/user-manual.md#7-exclusion-rules) and [section 13](docs/manuals/user-manual.md#13-retention-and-garbage-collection)).
- **Server storage format.** Server data is stored as deduplicated blocks and SQLite databases rather than plain files; run `kaze-syncd export` as root when you need plain files directly from the server ([manual section 12](docs/manuals/user-manual.md#12-export-to-plain-files)).
- **Server rollback after database migration.** Rolling the server binary back to an older version after a database schema migration requires restoring the pre-upgrade database backup from `<data>/var/backups/` and running `install --new-epoch` ([manual section 15](docs/manuals/user-manual.md#15-upgrading)).
