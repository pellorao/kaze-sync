# kaze-sync v0.3.0 release notes

[English](RELEASE-NOTES.md) | [简体中文](RELEASE-NOTES.zh-CN.md)

## What this release is

`v0.3.0` (released on 2026-11-15) is a Web UI update to kaze-sync, a self-hosted file sync service with version history for Linux and Windows computers (`kaze-syncd` on OpenWrt or x86-64 Linux with systemd or OpenRC, and `kaze-syncc` clients on Linux and Windows configured centrally in the Web UI). Because machines without suitable CJK system fonts rendered the Web UI poorly—and some had no Korean font at all—`kaze-syncd` now ships its own self-hosted fonts with per-language CJK subsets, renders each language name in the Settings language list from a tiny font file, and fixes a narrow-screen overflow on the Settings page. For the full overview of kaze-sync's sync, write-control, and restore features, see the [user manual](docs/manuals/user-manual.md), the [changelog](CHANGELOG.md), or the `v0.1.0` release notes in the Git tag `v0.1.0`.

Like earlier releases, this is a source-only release with no prebuilt binary downloads: build the static binaries from source with Go on any machine as described in [section 2.1 of the user manual](docs/manuals/user-manual.md#21-build-the-binaries). Identify a build with `kaze-syncd --version` and `kaze-syncc --version` (or in the top-left of the Web UI after signing in) and by the Git tag `v0.3.0`.

## Highlights

- **Self-hosted Web UI fonts.** The Web UI previously used the system font stack; on machines without suitable CJK fonts the text looked poor, and Korean had no font at all on some machines. `kaze-syncd` now ships its own fonts from the Adobe Source family alongside `JetBrains Mono`: `Source Sans 3` for Latin, Greek, and Cyrillic text, `Source Han Sans` in the regional version matching the page language (Simplified Chinese, Traditional Chinese, Japanese, and Korean) for Han, kana, and hangul, and `JetBrains Mono` for paths, rules, commands, and fingerprints. All fonts are under the SIL Open Font License 1.1, with licenses and sources in `internal/server/web/fonts/` (`SOURCE.md`), and the page requests nothing from other sites.
- **Per-language subsets to keep traffic low.** Latin fonts are embedded in full (`Source Sans 3` about 94 KB, and `JetBrains Mono` about 77 KB for two weights), while the Han, kana, and hangul fonts are subsets per language covering the common characters of each region (GB 2312 level 1, Big5 common, JIS X 0208 level 1 kanji plus all kana, and the 2350 common KS X 1001 hangul syllables) plus every character of the interface texts; each regular and bold file is about 630 KB (Simplified Chinese), 955 KB (Traditional Chinese), 513 KB (Japanese), and 195 KB (Korean), with bold a little larger. A browser downloads only the files of the page language and only when the page has characters in that range—English pages embed no Han font—so first opening a page costs about 94 KB (English), 0.5 MB (Korean), 1.1 MB (Japanese), 1.4 MB (Simplified Chinese), or 2.0 MB (Traditional Chinese) in total, and font files are cached for one week. A character outside the subset, such as a rare Han character in a file name, falls back to a `Source Han Sans` or `Noto Sans CJK` installed on the machine and then to a system font.
- **Tiny fonts for the Settings language list.** Language names in the Settings language list are each shown in their own language's font using four tiny font files (about 2 KB each), so opening Settings does not download the large regional subsets.
- **Server binary size and subset tooling.** Embedding the fonts adds about 4.8 MB to the server binary (from 22.8 MB to 27.7 MB for x86-64 `kaze-syncd`), while the client binary does not change in behavior. The repository includes `tools/fontsubset/subset.py` (needing `fonttools` and `brotli`) to rebuild the subsets and lists the characters each subset holds in `tools/fontsubset/coverage/`; a test fails if new interface text uses a character outside the subsets.
- **Narrow-screen Settings layout fix.** At 400 px width, the time zone list on the Settings page overflowed its card by about 19 px; it now shrinks to the card.

## Upgrading

The sync protocol remains at version 6, and database schemas and client behavior have not changed. No data migration runs during this upgrade, and you can upgrade the server and clients in any order; because clients have no Web UI, only the server binary shows the visual changes (for the full upgrade procedure, see [section 15 of the user manual](docs/manuals/user-manual.md#15-upgrading)):

- **Server (`kaze-syncd`)**: build the `v0.3.0` binary ([manual section 2.1](docs/manuals/user-manual.md#21-build-the-binaries)), copy it to the server, and run `./kaze-syncd install --data <same dir>` as root. Your listening port, TLS certificate, and admin password remain unchanged, and `install` copies the new binary into `<data>/` and restarts the service.
- **Clients (`kaze-syncc`)**: on each Linux or Windows computer, stop the running agent, replace the binary (`kaze-syncc` on Linux; both `kaze-syncc.exe` and the `-H=windowsgui` `kaze-syncc-agent.exe` on Windows), and start the agent again.

## Known limitations

- **Root-only server installation and CA renewal.** Server installation and local CA certificate renewal require root; non-root server deployment is not supported.
- **Source-only, no auto-update.** There are no prebuilt binary downloads and no automatic self-updates.
- **Scope boundaries ([manual section 18](docs/manuals/user-manual.md#18-what-kaze-sync-does-not-do)).** There is no file sharing, multi-user account system, or collaborative editing; no file preview or file download in the Web UI; no syncing of empty directories, Windows directory junctions, file permissions other than the executable bit, file owners, or extended attributes; no end-to-end encryption, transfer compression, or bandwidth rate limiting; no per-device exclusion rules; no two-factor authentication for the Web UI; no desktop tray icons or pop-up notifications on clients; no macOS or mobile clients; no server architectures other than x86-64; and single files larger than 128 GiB are refused by the server.
- **Not a backup.** Historical versions live on the same disk as the server's data; back up the server data directory to another disk or machine ([manual section 14](docs/manuals/user-manual.md#14-backup-and-restore-of-the-server)).
- **Symbolic links on Windows without Developer Mode.** A Windows client without Developer Mode enabled cannot create synced symbolic links locally; the links stay on the server and appear as a single folded warning line per device in the Web UI.
- **High-frequency files.** Files rewritten every few seconds (such as live status or telemetry files) create a new historical version on every write until retention removes them; exclude such paths if that matters ([manual section 7](docs/manuals/user-manual.md#7-exclusion-rules) and [section 13](docs/manuals/user-manual.md#13-retention-and-garbage-collection)).
- **Server storage format.** Server data is stored as deduplicated blocks and SQLite databases rather than plain files; run `kaze-syncd export` as root when you need plain files directly from the server ([manual section 12](docs/manuals/user-manual.md#12-export-to-plain-files)).
- **Server rollback after database migration.** Rolling the server binary back to an older version after a database schema migration requires restoring the pre-upgrade database backup from `<data>/var/backups/` and running `install --new-epoch` ([manual section 15](docs/manuals/user-manual.md#15-upgrading)).
